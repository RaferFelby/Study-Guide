## 这讲把各环节连起来

训练样本至少有三个视角：人能读的消息结构、模型输入整数 `input_ids`、与输入逐位置对齐的 `labels`。打成 batch 后再有 `attention_mask`。检查样本时，要来回比对这四层，而不能只看打印出来的一串对话。

本单元示例选择如下：

- UTF-8 字节回退，只为解释编码，不是 BPE/Unigram；
- 通用教学模板：BOS + 每条消息的 start/header/separator/content/end + 最后一条 assistant 的 EOS；
- assistant 正文和结束符监督；system/user/tool 消息及头部不监督；
- attention mask 负责标出有效输入位置，label 的 `-100` 负责屏蔽 loss；
- 训练示例测试右 padding，生成输入测试左 padding；位置 ID 等真实模型行为仍需实际验证。

## 从零检查一条记录

以 `demo.py` 的四条消息为例，按顺序检查：

1. 人类消息：user 提问、assistant 工具调用、tool 返回、assistant 最终答复。
2. 模板消息边界：每条消息有一个 IM_START，header 与正文由 IM_SEP 分开，消息以 IM_END 结束；序列开头只有一个 BOS，末尾 assistant 后有 EOS。
3. 编码长度：`input_ids` 与 `labels` 等长；角色名称/路由字段也被编码进输入。
4. 监督目标：user 和 tool 仍在 input 中；assistant 工具请求和最终答复受监督；assistant 最终 EOS 受监督；其他 label 为 -100。
5. batch：attention mask 对真实 input 为 1、PAD 为 0；PAD 标签一定是 -100；有效监督 token 数按每条样本计算，不应为 0。
6. shift：如果外部自定义 loss，就将 `logits[:, :-1]` 对齐到 `labels[:, 1:]`；如果把 labels 传给内部实现 loss 的因果模型，先核对该 API 的移位方式。

运行端到端演示和测试：

```powershell
..\..\..\.venv\Scripts\python.exe demo.py
..\..\..\.venv\Scripts\python.exe -m pytest -q
```

演示会打印可读对话、输入 token 数、有效监督 token 数和 mask 长度。token 数按 UTF-8 字节计算，所以显著大于真实子词 tokenizer 的 token 数是正常现象。测试结果显示断言数而非模型训练效果；本单元没有训练模型。

## 原模块验收清单

- [ ] **C09-01** 编码并解释单轮、多轮、工具调用消息；能从 header/content/end 区分片段。
- [ ] **C09-02** 按训练目标生成 labels；user/system/tool mask 规则说得清。
- [ ] **C09-03** 分别运行并查看训练右 padding 和生成左 padding；说明真实模型还要核对 position IDs。
- [ ] **C09-04** 测试阻止模板变化导致重复特殊 token 或 labels 错位。
- [ ] **C09-05** 独立复述 `[BOS,A,B,EOS]` 中三个有效 logit 目标；能分辨内部 shift 与自定义 shift。
- [ ] **C09-06** 至少检查三条样本逐条有效监督数大于零，padding mask 与监督 mask 各自符合目标。

完成标准：每一项都有个人运行或手算证据，可写在 [[02_学习记录/00 我的学习记录|学习记录]]。作者测试通过不表示学习者已完成这些项目。

## 综合练习

**跟做：** 运行 `demo.py`，数清 assistant 监督了哪些片段，再检查 `test_chat_data.py` 中 tool case 的 token/label 断言。

**独立：** 新增第三个样本（只含 system + user + assistant），把它和另两条长度不同的样本组成 batch，打印左右 padding 并逐条报告监督 token 数。

**迁移：** 准备一个真实模型的 2 条对话样本。在不下载权重的前提下，列出对 tokenizer、chat template、special token ID、有效 labels、左/右 padding、loss shift 必须核实的项目；使用该 checkpoint 文档或本地 tokenizer 配置，不用本工程 IDs。

> [!example]- 参考答案与解析
> 第三个样本每条应先调用 `encode_messages`，再交给 `pad_batch`；不要先把它的 labels 和 input 分别拼接。逐条监督数在 padding 前统计，batch 后也可统计不等于 -100 的标签；两者应相等，因为 PAD label 被忽略。
>
> 左右 padding 的 attention mask 中 1 的数量应等于原序列长度，0 的数量等于补齐长度；对应 labels 的补齐位置全是 -100。右 padding 时有效序列从索引 0 开始；左 padding 时有效序列在右侧连续。
>
> 真实模型核对清单：checkpoint ID/版本与 tokenizer 对应；查看 chat template 和 special token map；确认 tokenize 时不会重复加 tokens；查看模型 labels loss 是否内部 shift；逐条计算非 -100 label 数；明确 tool 与 system/user 监督目标；真实调用 tokenizer 构造两种 padding 并检查 position IDs/生成输出。
