## 本讲任务与前置

同一时刻Alice和Bob都来请求，服务怎样处理？客户端关掉窗口，任务会停止吗？先复习单元16协程超时/取消。现在学习线程及网络连接的不同边界；不要求掌握操作系统全部机制。

## 进程、线程、协程

进程是操作系统管理程序资源和隔离的基本单位。运行server.py与client.py通常是两个进程。线程在同一进程内共享内存；本服务用请求线程处理HTTP，用一个工作线程执行数据库任务。共享cache需要Lock，避免两个线程交错修改同一结构。

协程是可暂停/恢复的程序任务，asyncio在等待点切换；通常不会为每个协程创建系统线程。线程不等于协程，async函数里同步阻塞也不会自动变快。CPython常规构建下计算密集Python代码在线程间受GIL影响，线程主要用于IO等待和组织并发；实际GPU库/原生库行为需另查。

阻塞IO是当前执行位置等到读写完成才往后走，例如rfile.read、SQLite调用。我们使用线程让一份请求等待时其他请求还能处理，但ThreadingHTTPServer没有生产级的有界请求工作池，不能用它宣称无限并发容量。

## 最小示例：Event使等待可唤醒

在示例工程新建`lesson_thread.py`：

```python
import threading

wake_event = threading.Event()

def worker():
    print("工作线程等待")
    wake_event.wait()
    print("工作线程收到信号")

thread = threading.Thread(target=worker)
thread.start()
print("主线程发送信号")
wake_event.set()
thread.join()
print("已收拢工作线程")
```

预期前两条的顺序可以交换，但“收到信号”在工作线程等待之后，“已收拢”最后。Event是线程间的信号，不是装任务正文的队列；set使wait可通过；join等待线程结束，不是强制杀线程。

本服务wake_event通知“数据库可能有任务”，即使通知合并，数据库pending仍存在；空队列时wait(0.1)定期复查，避免永远睡眠。stop_event告诉工作循环退出，close设置两个信号再join，检查2秒后是否仍活着。

## 四种停止行为逐个区分

1. 客户端等待超时：客户端不再等这个响应；不能据此证明服务没执行。
2. 客户端连接断开：服务写回时可能遇到BrokenPipe/ConnectionReset；已提交数据库任务依然存在。
3. 上游超时：业务等待的检索服务超预算；应记录并转换为明确错误。本例simulate_timeout只模拟这个报告。
4. 取消任务：服务收到明确取消请求，数据库状态变cancelled；执行中的代码仍需合作检查才能停止计算。

本示例只在任务状态层实现取消，finish不能覆盖cancelled；并不强行打断正在执行的同步retrieve。因为retrieve很短，通常无明显等待；换成真实长函数后需要工具层取消检查或可取消的调用机制。不要用“状态取消了”声称外部支付/写入被撤销。

## 动手：观察取消与迟到结果

新建`lesson_cancel.py`：

```python
from pathlib import Path
from tempfile import TemporaryDirectory
from service import QueryService
from storage import JobStore

with TemporaryDirectory(dir=Path(__file__).parent) as directory:
    service = QueryService(JobStore(Path(directory) / "jobs.sqlite"))
    job, _ = service.submit("alice", "cancel-test", "refund")
    service.store.claim_next()
    print(service.store.get("alice", job["job_id"])["status"])
    service.store.cancel("alice", job["job_id"])
    service.store.finish(job["job_id"], "completed", {"answer": "迟到结果"})
    print(service.store.get("alice", job["job_id"])["status"])
```

预期running、cancelled。我们手动控制顺序，稳定复现“取消先到，完成后到”，不用靠sleep碰运气。这个实验验证数据库条件更新，不验证同步函数被抢占。

再运行：

```powershell
..\..\..\.venv\Scripts\python.exe -m pytest -q tests/test_http.py -k disconnect
```

`-k disconnect`选名称含disconnect的测试。测试在本机创建连接，提交后用Event暂停写回，关闭客户端连接再释放；服务记录一次断开，原任务仍为pending，健康接口仍200。RST为测试明确制造连接重置，并非推荐业务客户端行为。

## 超时应放在哪些位置

客户端open timeout=3、服务连接读取timeout=2、SQLite连接锁等待timeout=2、工作线程退出join timeout=2分别约束不同操作。它们不是自动相加的统一请求期限，也不是系统硬抢占。业务服务若调用模型/外部HTTP还需自己的连接/读取/整体预算，及长任务截止时间。

本工程模拟上游超时并测错误转换，但未接真实慢网络；不应把504测试写成真实检索延迟实验。断开处理只捕获预期连接错误，其余异常仍记日志；线程join超时会明确抛错误。

## 常见错误

- 认为thread.join(timeout)会杀线程：它仅停止等待，要检查is_alive并处理剩余工作。
- 用Lock围住整个慢检索：其他用户会一起等。当前cache锁只保护查/写字典；检索在锁外。
- 关闭终端B想撤销任务：显式POST取消才改变任务状态；请求丢响应可用幂等键找回。
- 测试偶尔卡住：Event等待也要带测试预算，清理服务器/线程要在finally或fixture收尾执行。

## 练习与答案

跟做：复现迟到结果仍cancelled，并指出SQL条件。完成判断：删除条件会导致错误覆盖，你能解释原因。

独立：客户端3秒超时但4秒后服务完成，给出安全下一步。提示：先查任务或以原幂等键重试，不能直接新建不同键。

迁移：把retrieve换成30秒外部写操作，画出取消检查位置与无法撤销边界。

> [!example]- 参考答案与解析
> finish只更新running行；取消已改状态，所以影响行数0。客户端先用job_id查；提交响应丢失时用同owner/key/内容取回，不更换key。
>
> 外部写之前检查取消，调用中按上游能力超时/取消，调用后核实结果。若上游已完成副作用，本地取消不能回滚；应标明结果未知或另走补偿流程，不能自动重试非幂等写。
