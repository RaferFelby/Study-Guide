## 本讲任务与前置

接口能工作后，要回答三件事：输入符合约定吗、调用者是谁、他有权看此资源吗？复习单元15的Schema/权限、单元17的参数绑定。本讲新增HTTP错误码、Bearer头和请求ID。

## 从输入到权限的机制

验证是检查数据形状和值，例如question必须是非空字符串，最长100字符。认证是确认身份；授权是判断该身份能否访问某资源。两者不能互相替代。持有一个有效令牌，只能说明系统识别这个演示用户，不能允许他读所有任务。

Bearer的直觉是“持有者可以使用的凭据”，服务读取Authorization头而非正文owner。这里`demo-alice`映射alice、`demo-bob`映射bob，是故意公开的教学映射。它不具备签名、过期、撤销、TLS和真实登录流程。不要把这些令牌用到真实业务。

会话是跨多次请求保留的身份/交互关联，可由服务端会话ID或其他机制实现。HTTP请求本身不会自动记住上次是谁。本示例每次请求都带令牌，没有额外登录会话。

任务查找的SQL同时绑定owner和job_id。Bob即使知道Alice任务ID，也查不到行；返回404避免向无权限用户确认任务存在。对公开管理接口，也可能选择403表示已知资源无权访问；应按产品约定使用，不能靠隐藏按钮替代服务检查。

## 最小示例：先在业务层练验证

在示例工程新建`lesson_validation.py`：

```python
from service import ServiceError, validate_question

for value in ["refund", "  support  ", "", 3]:
    try:
        print("通过", validate_question(value))
    except ServiceError as error:
        print(error.status, error.code)
```

运行共享解释器。预期前两条通过，第二条去除两端空格；后两条400 invalid_question。try只围住预期边界；这里捕获ServiceError，不吞掉所有编程错误。error.status是HTTP适配需要的状态，code是客户端可以稳定判断的短标识，message是人看的说明。

## 动手：制造并解释错误

先按第01讲启动server。新建`lesson_errors.py`：

```python
from client import request

base_url = "http://127.0.0.1:8765"
cases = [
    ({"question": ""}, "demo-alice"),
    ({"question": "refund"}, "wrong"),
    ({"question": "refund", "owner": "bob"}, "demo-alice"),
    ({"question": "simulate_timeout"}, "demo-alice"),
]
for body, token in cases:
    status, result = request(base_url, "POST", "/query", body, token)
    print(status, result["error"]["code"], result["request_id"])
```

预期400 invalid_question、401 unauthorized、400 invalid_fields、504 upstream_timeout。最后是本机函数主动抛出模拟超时，不是真实外部API变慢。每次request_id应不同；不需要记下随机值，只需学会从客户端响应到服务日志找同一个ID。

## 逐层阅读源码

`handle_api`先分配服务生成的请求ID；health允许匿名，不展示业务数据；其他路由校验Bearer。`read_json`检查分块请求、Content-Type、长度和JSON对象；只接收1～4096字节正文。fields集合严格等于接口所需字段，因此传owner并不能覆盖可信用户。

`validate_question`检查字符串并strip；业务异常被转换为带error.code/message的JSON。409代表同一幂等键提交不同内容；415代表Content-Type不支持；413代表正文超上限。状态码告诉大类，业务code区分更具体原因。

未知异常在HTTP边界记录完整日志，客户端得到500 internal_error和请求ID。不能把异常堆栈和数据库路径直接返回给学习者之外的用户。这里的宽泛捕获是协议边界日志处理，并非静默吞掉错误；业务函数和测试仍能发现异常。

> [!note] 当前简化
> 标准JSON解析尚未把重复字段作为独立安全策略；生产接口应统一解析规则并覆盖重复键/非有限数等输入。工具协议单元15已有严格JSON示例。本接口question/request_key类型与字段白名单仍逐项校验，未把输入当SQL执行。

## 常见错误

- 认为200一定有答案：未知问题可以200且answer=null、code=no_evidence，表示请求处理成功但无证据；业务成功需另看正文。
- 客户端把所有HTTPError当网络不通：HTTPError通常已有响应，可读取JSON；连接拒绝/超时属于不同异常。
- 将token放question或owner字段：服务认证看Authorization头。用client.request的token参数。
- 用返回404宣称已做认证：必须检查server的令牌映射和storage的owner过滤；单一响应值不能证明完整权限链。

## 练习与答案

跟做：把四种错误记录成“输入→状态→code→修复动作”。完成判断：修复空question后能得到退款答案，而不是把服务器所有异常改成200。

独立：解释为什么不接收客户端owner。提示：任何人都能修改自己的请求正文。

迁移：给一个仅管理者能查看的统计接口设计401、403、400和500行为。要求说明身份来源和服务端角色检查位置；不必实现真实登录。

> [!example]- 参考答案与解析
> 空值改为refund；wrong改演示令牌；去掉owner字段；模拟超时不能靠换合法类型修复，实际需检查上游/预算。身份由服务可信认证映射获得，正文owner是未经验证的自我声明。
>
> 管理接口：无有效凭据401；有身份但无管理角色403；筛选参数非法400；意外服务故障500并记录请求ID。角色检查在服务处理路径中，客户端显示菜单只改善体验。
