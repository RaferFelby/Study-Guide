## 要解决的问题与前置

相同问题重复检索浪费时间；提交请求丢了响应又重试，可能重复执行。它们看似都叫“重复”，处理目标不同。复习单元15幂等键、单元17事务和本单元Lock，本讲分别做缓存与持久任务去重。

## 缓存和幂等各自保证什么

缓存保存计算结果，希望下次省计算，可以过期或清空。幂等记录保存“这次业务意图已经创建了哪个任务”，重试须回同一个任务，即使结果缓存已清空。不能用短TTL缓存代替支付或任务提交的幂等记录。

缓存键是(owner, 知识版本, question)。owner防跨用户复用；知识版本防新政策仍用旧结果；question区分问题。当前示例政策对所有人相同，仍保留owner是为了练隔离。真实缓存还可能需要租户、权限版本、模型/提示词版本；键缺少这些维度会混淆结果。

TTL是保存多久才算过期，本例0.2秒用于快速观察。用monotonic计时比较持续时间，避免系统墙上时钟调整。最多32项，满时移除最早插入项；这是简单容量策略，不是LRU。缓存命中不自动延长TTL。

## 最小示例：用可控时钟验证过期

新建`lesson_cache.py`：

```python
from pathlib import Path
from tempfile import TemporaryDirectory
from service import QueryService
from storage import JobStore

now = [0.0]
with TemporaryDirectory(dir=Path(__file__).parent) as directory:
    service = QueryService(
        JobStore(Path(directory) / "jobs.sqlite"),
        ttl_seconds=1,
        clock=lambda: now[0],
    )
    print(service.query("alice", "refund")["cache_hit"])
    print(service.query("alice", "refund")["cache_hit"])
    print(service.query("bob", "refund")["cache_hit"])
    now[0] = 1.0
    print(service.query("alice", "refund")["cache_hit"])
```

预期False、True、False、False。lambda: now[0]是无参数小函数，QueryService调用clock()时获得当前值；列表仅为了此教学函数可读取我们更新的数值，不是推荐全局状态。真正运行默认time.monotonic。等于截止时间已经过期，因此用`>`而非`>=`。

## 源码逐步解释

query先验证并标准化问题；拿锁查缓存；命中返回deepcopy，防调用者改动缓存内对象；过期移除；释放锁后检索；再次拿锁限容量并写结果。锁没有覆盖retrieve，所以不同请求不用因慢检索互等。

这里没有实现同键正在计算时合并等待，两个同时未命中的请求可能各检索一次。它们结果都是纯查询，功能仍正确，但不能宣称缓存防止所有重复计算。遇到昂贵并发同问再设计in-flight合并；单元16已有同批安全查询共享的局部示例。

Redis是常用的外部键值服务，可让多进程共享缓存、过期和部分原子操作；增加网络、可用性和部署成本。本工程只有单进程内存缓存，不安装Redis，也不把Python字典称Redis。多进程后字典彼此独立，启动第二实例不会自动共享缓存。

## 动手：持久幂等与冲突

新建`lesson_idempotency.py`：

```python
from pathlib import Path
from tempfile import TemporaryDirectory
from service import QueryService
from storage import ConflictError, JobStore

with TemporaryDirectory(dir=Path(__file__).parent) as directory:
    service = QueryService(JobStore(Path(directory) / "jobs.sqlite"))
    first, created = service.submit("alice", "purchase-report-1", "refund")
    again, created_again = service.submit("alice", "purchase-report-1", "refund")
    print(created, created_again, first["job_id"] == again["job_id"])
    try:
        service.submit("alice", "purchase-report-1", "support")
    except ConflictError as error:
        print(type(error).__name__)
```

预期True False True，再ConflictError。名称purchase-report只是键字符串，不发生购买。同owner/key不同问题必须拒绝，不能悄悄返回另一意图的结果。不同用户可以使用相同key，由UNIQUE(owner, request_key)区分。

存储create的BEGIN IMMEDIATE把查重和插入放入同一写事务，防两线程同时发现不存在后插两份。唯一约束是数据库最后一层保障。本机测试8次并发同提交，只有一次created=True且只有一个job_id；不等同于跨数据库/外部副作用严格一次。

运行选定测试：

```powershell
..\..\..\.venv\Scripts\python.exe -m pytest -q tests/test_service.py -k 'cache or idempotency or concurrent'
```

`-k`用布尔表达式选择名称，引号把表达式作为一个参数。完成后记录选中了多少测试，而非把它说成全部测试。

## 常见错误与设计边界

- 重试时随机生成新key：服务视为新意图，无法去重；同次操作应稳定key。
- 永远复用一个key处理所有问题：不同内容409冲突；为不同意图创建不同key。
- 假定缓存保存后就无需数据库：服务重启字典消失，但任务/幂等记录仍在SQLite。
- 缓存包括敏感结果却只有question键：测试公开政策看不出泄漏，必须用不同用户不同内容的测试验证权限。
- TTL到期就立即从字典删除：本实现惰性失效，访问时删，且容量有界；TTL不是后台定时清理器。

## 练习与答案

跟做：重复提交相同key，保存两个created与ID比较。完成判断：数据库只创建一个任务。

独立：知识库从v1变v2而问题不变，缓存键应改什么？如何验证没有用旧结果？

迁移：外部订票完成后、本地保存结果前程序崩溃，幂等任务记录能否证明没有重复订票？写出所需上游能力。

> [!example]- 参考答案与解析
> 新知识版本加入键，或发布时明确失效旧缓存；测试先缓存v1，再换版本并断言检索重新发生且引用来源为v2。只改回答显示文字无法证明失效。
>
> 本地任务记录无法跨崩溃证明外部副作用。需要上游接受稳定幂等键、能按操作ID查结果，或业务补偿/人工核实。未知结果时盲重试可重复订票。本例只读查询，因此不展示外部写的严格一次保证。
