## 要解决的问题

检索或模型推理可能耗时较长。把所有工作放进一次HTTP请求，客户端必须持续等着，还难以跨刷新查看结果。我们把“接受任务”和“任务完成”分开。本讲需要字典、循环、单元14状态和单元17事务；线程细节留到下一讲。

## 任务资源与状态直觉

POST /jobs收下问题，把一行pending写进数据库，返回job_id和202。202表示已接受，不能解读为答案已生成。工作线程随后认领任务，改为running，再保存completed或failed。客户端GET /jobs/{id}重复查状态，这叫轮询。

排队取号的类比帮助理解job_id，但数据库行实际还包含owner、request_key、question、status、result；job_id不是身份凭证。即使任务很快完成，第一次响应仍可显示pending，因为提交和处理不是同一时刻。

本示例状态路径：pending→running→completed/failed；pending或running可取消为cancelled。终态不被取消覆盖；取消后的迟到结果也不能改回completed。没有模型重规划，只有合成查询工作。

## 最小示例：不启动网络也能观察状态

在示例工程新建`lesson_jobs.py`：

```python
from pathlib import Path
from tempfile import TemporaryDirectory
from service import QueryService
from storage import JobStore

with TemporaryDirectory(dir=Path(__file__).parent) as directory:
    service = QueryService(JobStore(Path(directory) / "jobs.sqlite"))
    job, created = service.submit("alice", "first-job", "refund")
    print(created, job["status"])
    service.run_one()
    saved = service.store.get("alice", job["job_id"])
    print(saved["status"])
    print(service.store.get("bob", job["job_id"]))
```

运行后预期True pending、completed、None。TemporaryDirectory确保本练习自有数据库退出清理；JobStore每次使用短连接并关闭；run_one同步处理一份任务，便于初次阅读，不需要猜线程何时执行。

逐步看：submit先验证问题和幂等键，再事务创建；返回值第二项说明是否新建；get使用owner和ID；run_one调用claim_next把pending改running，query成功后finish。finish的WHERE status='running'是防止迟到结果覆盖取消的关键条件。

## 动手：网络提交、轮询、权限验证

启动server后新建`lesson_poll.py`：

```python
import time
from client import request

base_url = "http://127.0.0.1:8765"
status, job = request(base_url, "POST", "/jobs", {
    "question": "refund", "request_key": "lesson-poll-1"
})
print("提交", status, job["job_id"])
path = "/jobs/" + job["job_id"]
for attempt in range(20):
    status, saved = request(base_url, "GET", path)
    print(attempt, status, saved["status"])
    if saved["status"] in {"completed", "failed", "cancelled"}:
        break
    time.sleep(0.1)
else:
    print("本次观察预算已用完，任务不一定停止")
print("Bob查看", request(base_url, "GET", path, token="demo-bob")[0])
```

第一次通常202，重复运行相同键可能200并取回旧任务；最终应completed且Bob为404。循环最多20次，每次请求还有客户端等待，因此这并非精确2秒硬时限。`else`属于for：没有break时执行，表示停止观察，不能表述为任务取消。

## 数据库队列怎样避免重复认领

本单元用SQLite中的pending行作教学任务队列，不再另存内存Queue造成“库里有但队列里丢失”两套状态。claim_next在BEGIN IMMEDIATE事务中查最早pending并更新running；两个本机调用不能同时认领同一行。数据库队列更容易观察持久化，但轮询、锁竞争和单机吞吐有限。

public_job只返回job_id/status/result，不返回内部owner和幂等键。存储结果是JSON文本，读取后loads还原字典。接口字段应稳定，数据库未来增加列不应自动泄漏所有列。

列表分页在单元17已经讲过游标与稳定排序。若扩展GET /jobs列表，需要限定owner、page_size上限并定义游标；本工程只有按ID读取，不声称已提供任务列表分页。

## 轮询、SSE与WebSocket的选择

轮询适合目前只有最终结果的低频状态查看，容易重试；间隔太短会制造无意义请求。SSE由服务器持续向客户端发送事件，适合单向进度/文本流；要处理断开后的续传/事件ID。WebSocket适合双方持续发送消息，但要额外设计消息类型、心跳和连接权限。

不要因为“Agent”就立即引入长连接。本机示例未实现SSE/WebSocket；等产品确实需要逐字输出或双向交互时再扩展，同样不能让连接取代持久任务状态。

## 常见错误

- 把202正文当最终答案：读status并GET任务，直到终态。
- 用request_id代替job_id查询：前者对应一次HTTP尝试，后者对应跨多次请求的任务。
- 任务已完成仍想看running：合成任务很快；用最小业务脚本逐步调用claim_next观察，不要凭运行时机推断状态跳过。
- 每次轮询重新POST：这会创建任务或触发幂等，查看用GET；request_key不应该每次随机更新。

## 练习与答案

跟做：记录POST接受码、job_id、最终状态、Bob读取结果。完成判断是同一个job_id能从提交追踪到终态。

独立：给pending/running/completed/failed/cancelled写一句中文解释，并标出终态。

迁移：假设模型任务需要30秒，设计页面刷新后继续查看的最小数据。提示：浏览器可保留job_id，但服务仍验证登录身份。

> [!example]- 参考答案与解析
> pending已存储未认领；running已认领正在执行；completed结果成功持久化；failed已知失败；cancelled接受取消。后三者为本示例终态。
>
> 页面保存job_id，恢复后向服务GET状态；服务按可信用户和job_id查找。不能只在浏览器内存保存最终结果，也不能让知道ID的人直接读取。若采用流式输出，刷新仍先查持久状态，再从已确认事件位置恢复流。
