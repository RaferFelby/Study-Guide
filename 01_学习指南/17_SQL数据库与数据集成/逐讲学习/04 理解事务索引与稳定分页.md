## 要解决什么问题

导入一批工单，第一个成功、第二个非法，不能留下半批却报告完成。查询越来越慢，需要知道是否扫描全表。工单列表翻页时新增资料，也不能随意重复或漏记录。本讲分别处理一致性、访问效率和分页顺序。

## 事务让一组改动一起提交

**事务**把一组数据库操作作为整体：成功commit提交，异常rollback撤销未提交改动。不是所有外部系统都能进入同一事务；数据库rollback不能自动撤销邮件或API写入。

在示例工程创建 `inspect_transaction.py`：

```python
import sqlite3

connection = sqlite3.connect(":memory:")
try:
    connection.execute("CREATE TABLE items(id INTEGER PRIMARY KEY, value INTEGER CHECK(value >= 0))")
    try:
        with connection:
            connection.execute("INSERT INTO items VALUES(?, ?)", (1, 10))
            connection.execute("INSERT INTO items VALUES(?, ?)", (2, -1))
    except sqlite3.IntegrityError:
        print("批次失败，回滚")
    print(connection.execute("SELECT COUNT(*) FROM items").fetchone()[0])
finally:
    connection.close()
```

预期回滚说明和0。CHECK约束阻止-1，with connection在当前默认事务模式下异常回滚。**连接的with管理提交/回滚，不自动close连接**，所以finally仍需close。生产按Python版本明确事务配置，不盲目依赖未来默认值。

import_rows同样把整批放with connection，任何冲突/外键失败会回滚整批。本例单写连接，没有并发“先查后写”原子去重设计，唯一约束可防重但并发冲突仍需处理；别把单进程测试当分布式恰好一次。

## 索引像额外检索目录

**索引**保存按字段组织的查找结构，帮助跳到目标行，减少扫描；代价是占空间、插入/更新时维护。类比书后索引，但实际结构和优化计划由数据库实现，不是手工行号字典。

工程复合索引 `(tenant_id,status,created_at DESC,ticket_id DESC)`服务当前租户、指定状态、时间倒序查询。等值过滤前两列后，后两列可支持排序。索引列顺序影响适用范围；不能把所有列都建一遍就叫优化。

查看计划：

```sql
EXPLAIN QUERY PLAN
SELECT external_id
FROM tickets
WHERE tenant_id = ? AND status = ?
ORDER BY created_at DESC, ticket_id DESC;
```

demo应包含 `SEARCH tickets USING INDEX idx_tickets_tenant_status_created`。SEARCH表示按索引查范围；SCAN可能遍历表或索引，需看完整语境。计划输出字段/文字可能随SQLite版本变化，不能当稳定接口全文匹配，见[SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)。

小库7行即使索引被选也不能证明显著变快。真实性能需足够数据、固定查询/缓存条件、多次测量、看排序和访问行量；本实验验证计划与用途，不声称生产性能提升。

## OFFSET和游标分页

OFFSET分页是先跳过N条再取一页；页数大时可能扫描很多，期间新增行也会改变位置。**游标/键集分页**用上一页末尾稳定排序键作为下一页起点。

当前示例按ticket_id升序：

```sql
SELECT ticket_id, external_id
FROM tickets
WHERE tenant_id = :tenant_id AND ticket_id > :after_id
ORDER BY ticket_id;
```

只读服务加行数限制。先after_id=0取前两项，再用最后ticket_id作为游标，下一页不重复。若按日期排序，游标要包含created_at和ticket_id，比较要匹配倒序，不能只用日期漏掉同时间记录。

键集分页也不自动提供固定快照；数据更新删除可能改变内容。严格导出需要快照/一致时间点及完整性核对；用户浏览通常允许变化，但要说明。

## 连接池先理解生命周期

连接池复用少量连接，减少网络服务器数据库反复建连接的成本，并限制资源。连接不是随意跨线程共享的对象：sqlite3默认check_same_thread=True；把它改False不等于自动线程安全。

当前ReadOnlyService每次开独立只读连接，finally关闭，没有实现池。SQLite嵌入式小例子无需新增池框架；服务部署到PostgreSQL时再选择成熟驱动/池，明确容量、等待、事务清理和连接归还。不要把活跃事务连接直接还池给另一个任务。

## 常见错误与练习

程序退出数据没保存：核对commit/事务。with之后文件仍占用：with不close。计划用索引仍慢：数据/选择性/排序/结果传输都可能影响。分页重复：检查排序键是否唯一稳定、游标比较是否同方向。

**跟做：** 运行事务脚本和demo计划，解释0和索引名称。

**独立：** 给同created_at的两条工单设计日期倒序分页条件。提示：日期小于上一页日期，或日期相同且ticket_id更小。

**迁移：** 为持续项目高频查询选一个复合索引，先写过滤/排序模式，再用EXPLAIN核验；设计池容量和超时但不安装未批准依赖。

> 下一页条件：`created_at < :last_time OR (created_at=:last_time AND ticket_id<:last_id)`，再与tenant条件用括号AND连接；排序同样created_at DESC,ticket_id DESC。事务原子性只覆盖同库操作，外部未知写仍需幂等/对账。
