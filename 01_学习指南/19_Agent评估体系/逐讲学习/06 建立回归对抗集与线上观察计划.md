## 本讲任务与前置

一次评估不够。改提示词、工具Schema、模型或检索配置后，要确认旧能力没坏，并观察真实使用的失败。复习前五讲，最后把数据、指标、裁判和报告写成一套可执行检查流程。

## 三类集合的用途

回归集保存已确认的重要行为，修改后重复运行，发现退步。对抗集专门挑战权限、证据、输入边界和异常，不能只收正常查询。线上观察样本来自真实使用，反映分布变化，但不能直接把全部原始对话塞进开发集。

工程60条包含待批准写、未知、超时、注入、冲突；它们是合成边界集。真实对抗还可能包括批准参数被换、跨用户缓存、工具响应伪造、预算耗尽、错误后写工具重试；现有规则未实现这些全部能力，新增题应暴露失败而不是改gold迎合系统。

回归集要版本化；线上难例经允许使用、去标识化、审核后进入待补充集。加入test后就应避免反复用它调参；必要时维护更长期保留的新测试组。

## 最小示例：明确门槛

新建`lesson_gate.py`：

```python
from pathlib import Path
from evaluate import build_report

path = Path(__file__).parent / "fixtures" / "cases.json"
report = build_report(path)
print("数据版本", report["dataset_sha256"][:12])
print("退步ID", report["regressions"])
print("门槛", report["gate"]["passed"])
print("限制", report["limitations"])
```

预期退步[]、门槛True，限制列出合成数据/五组/无真实裁判与人工/模拟成本。显示摘要前12位方便阅读，完整摘要仍在报告。门槛通过仅表示本规则评估集符合所选条件，不是允许部署真实写操作。

## 动手：修改前后完整流程

先保存report-test-01.json，列出想改的行为和可能影响。改代码后在示例工程运行：

```powershell
..\..\..\.venv\Scripts\python.exe -m ruff check .
..\..\..\.venv\Scripts\python.exe -m ruff format --check .
..\..\..\.venv\Scripts\python.exe -m pytest -q tests
..\..\..\.venv\Scripts\python.exe evaluate.py --split test --output report-test-02.json
```

格式/静态检查检查源码规范，pytest检查指标与行为约定，evaluate输出任务和成本回归；它们回答不同问题，不能互相替代。无需修改时也可先运行完整命令熟悉流程，不应为制造改动破坏现有安全规则。

对比数据SHA、版本、各n、场景分项、逐ID退步、安全、成本和限制。若集或gold变了，单列变化，不把所有分数变化归因于系统改进。真实LLM还需要多次运行并记录随机/供应商版本，不能复制规则100%结论。

## 线上看什么及怎样解释

任务完成率应由业务结果确认，不能只看用户没再发消息；工具错误率需分权限拒绝/非法输入/上游故障；用户反馈需留意不满意用户更愿意点反馈的选择偏差。还可看拒绝率、人工接管率、p50/p95延迟、调用/重试次数、每成功任务成本、异常终止和恢复率。

延迟p95指约95%的任务耗时不超过该值，不是平均；一次极慢任务可能拉高平均，而分位展示分布另一面。小样本分位也不稳定，报告数量和时间窗口。实际计费要使用有效价格版本，不能沿用本例cost_units。

线上指标下降可能来自新用户/新知识/上游故障/模型变更，先按版本、场景和时间分组，沿request_id/run_id到轨迹找证据。日志要最小必要数据和脱敏；不把完整用户秘密作为“可观测性越多越好”的依据。

## 发布判断报告模板

在Obsidian自己的笔记写：目标与适用范围、系统/数据版本、样本来源与审核、切分/分母、各层指标、关键难例、裁判校准、配对变化、实际/模拟成本、未测项目、结论与下一步。

当前合理结论是“离线规则机制测试符合夹具契约，可继续学习和扩展真实评估”，不是“Agent已达生产100%完成率”。尚缺真实多样任务、独立人工标注、真实模型裁判校准、上游与线上数据；这些明确留为学习实践任务，作者不替你勾选。

## 常见错误

- 测试全绿却没执行评估报告：pytest覆盖指标函数/固定行为，报告是本次数据与版本的证据。
- 新模型只测正常十题：沿权限/异常/冲突/未知场景重跑。
- 线上发现失败马上自动改提示词：先确认来源、权限和可复现，保留难例并经评审修改。
- 将外部基准分数直接当业务验收：[SWE-bench](https://arxiv.org/abs/2310.06770)等基准针对其任务与执行环境，自己的退款/权限任务要另建标准。

## 单元验收练习与答案

跟做：完整运行检查并保存新报告，列出任务成功、安全、工具总数、成本单位与限制。完成判断：别人可用固定数据重算。

独立：新增一个“批准目标不一致”样本草案，并说明为何现系统没覆盖。先保留预期契约，不改成系统当前能做的答案。

迁移：完成一页真实业务评估计划，包含50～100条独立审核任务的来源、gold/轨迹标准、dev/test分组、Judge校准和上线观察授权。当前只有计划时明确写待执行。

> [!example]- 参考答案与解析
> 批准目标不一致应拒绝执行或重新确认；现approved只是布尔，没绑定service/参数，因此不能支持该安全声明。下一步扩展可信批准记录并加执行前匹配测试。
>
> 真实评估计划先确定业务与数据权限，再收多样题、独立审核、固定切分、结构化过程检查，开放输出用盲测/Judge校准。报告明确样本数、争议和未测项，线上监控不能绕过隐私/权限。
