## 要解决的问题

真实回答可能有多种正确表达，字符串比较不足。可以请人工评审或LLM裁判，但裁判也会出错。前置是布尔值/列表和gold；本讲先手算一致率，再设计独立标注流程。没有调用付费模型或请他人标注。

## Judge与rubric

LLM-as-Judge是让模型按评分规则判断另一份输出。它适合语义/表达等程序难判的维度，不能替代确定的权限、实际工具结果和数据库条件。裁判看到候选文字时还可能被其中指令影响，因此评审上下文也要把候选当不可信数据。

写清rubric：事实是否支持、是否对应问题、引用是否有效、缺证据时是否承认；每项0/1及失败理由，允许“不确定”。对写操作另核对工具轨迹，不让华丽答案抵消越权。

位置偏差是更倾向某个展示位置；冗长偏差是偏爱更长文本；自我偏好是偏爱与裁判自身风格/来源相近的答案。这些在[LLM裁判研究](https://arxiv.org/abs/2306.05685)中被讨论，不能默认任一模型裁判在本业务已可靠。应打乱候选、交换位置、隐藏系统名并抽查。

## 最小一致率示例

在示例工程新建`lesson_agreement.py`：

```python
from metrics import judge_agreement

reference = [True, False, True, False]
judge = [True, True, True, False]
print(judge_agreement(reference, judge))
```

预期agreement0.75、kappa0.5、disputed_indices[1]、n4。四条中3条一致，所以3/4。第二条参考False、裁判True，保留它用于核查，而不是删掉争议提高一致率。

reference只是示例标签，不能称人工标准。实际参考应由独立评审根据证据形成，并保留争议仲裁结果。Judge与人一致不意味着人没有错误。

## Kappa一步步手算

参考正例2/4，裁判正例3/4；若按两组各自正负比例随机给标签，碰巧一致概率为(2/4×3/4)+(2/4×1/4)=0.5。观察一致0.75，Kappa=(0.75−0.5)/(1−0.5)=0.5，扣除了这种随机比例的一致。

全部标签同一种时chance可能1，分母0，工程返回None而非除零。Kappa受类别比例和样本量影响，不是唯一质量分；还要看正/负误判、争议类型。它不适合直接评价开放多等级分而不改公式。

## 动手：看偏差模拟与争议

运行：

```powershell

```

8份示例标签一致6/8=0.75，Kappa0.5，争议下标1与6。随后故意总选左侧，候选交换后从answer-a变answer-b，所以“仍选同一答案”为False。这个小程序展示检测逻辑，不是LLM真实位置偏差实验。

在笔记记录争议1/6的两方标签，写“需要查什么证据”。因为夹具没有真实回答/证据，不能仲裁出真实业务对错；这也说明单有布尔标签不足以完成评审。

## 如何进行真实盲测

先冻结一批dev样本和rubric，隐藏系统版本名字，随机候选顺序。让评审独立看问题、证据、输出、实际轨迹，记录维度分、理由、不确定与标注时间。身份信息和不必要秘密应删去；需要对外发送时必须取得明确授权，本轮没有进行发送。

裁判使用同样输入与rubric，记录模型/提示词/温度/版本以及结构化标签；解析失败单独记录不能当False。抽查全部安全失败、所有争议，加随机一致样本，防双方一致但都错。修订rubric后用新版本复测，不能静默覆盖历史标签。

评审自身参与开发也会产生偏差；尽量用独立审核。没有第二人时可隔时自查并标明同一作者，不能写“独立人工盲测通过”。

## 常见错误

- 用一个Judge评另一个系统直接作为真值：需校准与争议抽查。
- 输出更长就更高分：rubric按事实/任务，不奖励无关篇幅；交换位置检查偏差。
- Kappa无法计算改成1：明确None和原因，同时报告原一致率及类分布。
- 只抽分歧样本：一致双方也可能共错，要随机检查一致样本。

## 练习与答案

跟做：手算4条样本3/4和Kappa0.5。完成判断：解释chance来自两组标签分布。

独立：四条都True且两边一致，为什么不能仅说裁判优秀？

迁移：写一个真实裁判评审表，至少包含case_id、证据版本、维度标签、理由、系统匿名名、候选顺序、裁判版本和人工审核状态。

> [!example]- 参考答案与解析
> 没有负例，不能发现误接受；chance=1使Kappa未定义。增加有明确失败与安全边界的负例，并观察不同类别错误。
>
> 评审表应让另一个人能复查分数依据，解析失败与不确定单列，争议不删除。实际标注前写“计划/待审”，不要把作者示例标签当真人结果。
