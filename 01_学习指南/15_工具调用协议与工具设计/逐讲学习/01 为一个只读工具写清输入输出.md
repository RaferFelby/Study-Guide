# 第 1 讲：为一个只读工具写清输入输出

> [!nav] 页面导航
> [[01_学习指南/15_工具调用协议与工具设计/00 工具调用协议与工具设计学习地图#学习顺序|单元 15：工具调用协议与工具设计]] · [[01_学习指南/15_工具调用协议与工具设计/逐讲学习/02 用 Schema 拦住错误参数|下一讲]]

## 要解决什么问题

Agent想查资料，执行器却不知道传什么参数、返回结果里哪个字段是证据。一个工具必须有明确的**契约**：名称、职责、输入类型与约束、执行前提、成功/失败返回、副作用。

契约像订单表格：填哪一栏、允许哪些值、提交后收到什么。但实际机制是代码和数据校验，模型读了描述并不保证遵守，也不保证拥有权限。

前置是JSON对象和函数。本讲先完成一个只读MVP工具，不需要凑多个工具。第二个写工具只为之后演示确认/幂等，不是数量验收。

## 给工具一个清晰职责

`search_policies`做“按关键词查询当前身份可见的政策片段”。它返回原文和定位，不生成自然语言答案、不创建工单。读与写分开，能分别安排权限、重试和确认。

名称用英文snake_case，与Python函数习惯一致。描述写“查什么、何时用、返回什么、不能保证什么”；query说明英文服务/政策关键词；top_k说明最多返回几个片段。

不好的描述“万能搜索，帮你处理问题”没有明确输入和边界，容易选错工具。反过来把每个小字段做成一个工具，也会让模型面对过多相似选择。工具粒度应匹配有意义的任务操作，保持契约可读。

## 看一个完整最小调用

在示例工程新建 `inspect_read_tool.py`：

```python
from contracts import ToolCall, ToolContext
from runtime import ToolRuntime

runtime = ToolRuntime()
call = ToolCall("query-1", "search_policies", '{"query":"storage retention","top_k":1}')
context = ToolContext("learner", "public")
result = runtime.execute(call, context)
print(result["ok"])
print(result["data"]["evidence"][0])
```

运行共享解释器，预期True，首条id=storage-retention、text包含30 days、locator=storage.md#retention。英文storage是存储，retention是保留；来源是虚构内存语料，定位不是当前磁盘文件。

`ToolCall`包含call_id、name和arguments_json。外层调用ID关联本次结果，参数JSON字符串描述工具输入。`ToolContext`来自执行侧，提供可信actor_id和role，不能放在模型可随意填写的参数中。

## 成功不一定有证据

统一成功结构：

```json
{"ok": true, "data": {"evidence": [], "matched_count": 0, "truncated": false}, "error": null}
```

无匹配是一次成功完成的空查询，回答层应据此说明无依据；不同于查询系统异常。成功data里有evidence列表，每项保留id/text/locator；matched_count是当前权限下匹配总数；truncated指出是否只返回部分候选。

统一失败结构：

```json
{"ok": false, "data": null, "error": {"code": "invalid_arguments", "message": "参数不符合契约", "retryable": false}}
```

code是稳定机器错误码，message供阅读，retryable表示是否有安全重试依据。参数错误不是暂时网络故障，原样重复通常不会成功。执行器不能把异常文本全抄给用户，尤其可能带秘密或内部路径。

本地示例不主动重试；之后可靠性单元会先判断只读/幂等和错误类型，再限制次数。

## 看执行顺序

`ToolRuntime.execute`先校验调用ID、身份和名称，再解析/校验参数；合法后选择工具处理器。search处理器先过滤隐藏文档，再计算词面重叠、排序、截断并组织结果。

这仍是词面教学基线，没有复用单元13神经模型（上一单元本来也只有LSA）。返回格式可以接其他检索器；更换算法后不要丢证据ID与定位。

`matched_count`不能包含当前用户无权看见的匹配，否则会泄露隐藏资料存在。只给模型需要的摘要，也应在服务端先完成权限过滤。

## 动手变化与排错

把query改unknown，预期ok=True但evidence为空。把top_k改0，预期ok=False和invalid_arguments，不会执行查询。把role设public查database retention，结果不包含database-retention；可能仍返回其他有retention的公开段，所以答案层不能据任何命中就答数据库政策。

若KeyError: data，先看ok是否False；失败data是None。若ModuleNotFoundError contracts，确认脚本在示例工程并从该目录运行；不要把不同单元同名模块同时加入全局PYTHONPATH。

## 练习与答案解析

**跟做：** 运行有命中、无命中、参数越界三次，记录ok/data/error。完成标准：不会把空检索视为程序异常。

**独立：** 为“按订单号读取状态”写工具名称、参数、成功结构、错误码和副作用等级。提示：订单不存在与无权限要分别设计，但对外信息可能需避免暴露存在性。

**迁移：** 给上一单元RAG检索写统一evidence契约，保留版本、权限来源和定位。完成标准：模型可依据返回回答，执行器仍掌握授权。

> [!example]- 参考答案与解析
> `get_order_status(order_id)`只读，输入非空订单号，成功含status/updated_at；非法参数不可重试，暂时故障可在幂等前提下限次重试。不要让模型传customer_role=admin自己提权。证据必须来自执行结果；工具说明与Schema只是契约的一部分，不是认证机制。
