# 第 4 讲：把权限与确认放在执行边界

> [!nav] 页面导航

## 要解决什么问题

参数通过Schema，模型又说“用户允许了”，工具能执行吗？还需要服务端确认是谁、具有什么权限、这次动作是否已获授权。**身份认证**确认是谁，**授权**判断这个身份能做什么；它们不由模型参数自己决定。

本单元只模拟可信上下文，没有实现登录认证。`ToolContext(actor_id, role, approved_fingerprints)`由示例程序构造；生产应从可信会话/服务端规则推导，不能让客户端或模型任意选staff。

前置是单元14人工确认，必要时回看[[01_学习指南/14_Agent运行原理与状态机/逐讲学习/05 在副作用前等待人工确认|批准绑定动作]]。

## 四种检查分别负责什么

| 检查 | 回答的问题 | 不能替代 |
|---|---|---|
| Schema | 参数形状/类型/范围正确吗 | 当前用户有权吗 |
| 权限 | 当前身份能读/写目标吗 | 用户同意这次动作了吗 |
| 确认 | 具体动作是否已获批准 | 操作会不会被重复执行 |
| 幂等/前提 | 重复与资源变化如何处理 | 数据来源是否可靠 |

public可读公开政策，staff可读全部演示政策并有创建权限。create_ticket仍需该动作fingerprint被批准。工具返回permission_denied和confirmation_required，原因不同，后续策略应该不同处理。

## 副作用分级先从简单例子理解

只读：查询政策、读取订单。低影响可逆写：草稿、演示工单。高影响或难撤销写：退款、删除数据、发送外部消息。副作用等级影响确认、重试、幂等、日志和恢复；具体等级由业务决定，不是一个工具名能永远确定。

本工程search_policies是read_only；create_ticket是local_write，只写当前内存，进程结束数据消失。它没有发消息或创建真实工单。真实接入后等级与权限可能变高，要重新设计执行前提。

## 动手看权限先于确认

在示例工程新建 `inspect_permission.py`：

```python
import json
from contracts import ToolCall, ToolContext
from runtime import ToolRuntime

call = ToolCall("w1", "create_ticket", json.dumps({"title": "演示", "idempotency_key": "k1"}))
runtime = ToolRuntime()
for role in ["public", "staff"]:
    result = runtime.execute(call, ToolContext("learner", role))
    print(role, result["error"]["code"])
print(len(runtime.tickets))
```

预期public permission_denied、staff confirmation_required、工单数0。拥有staff身份不自动表示这次动作已经批准；public即使伪造同意也不能绕过权限。

模型参数里多加role=staff会在Schema层拒绝，避免让工具描述暗示模型可以控制授权。读取结果也先过滤permission，matched_count只统计可见资料。

## 批准绑定名称、参数与身份

call_fingerprint将name、arguments、actor_id排序序列化后计算SHA256。批准集合中必须有同指纹，才开始第一次写入。字段变化或不同身份得到不同指纹。

指纹用于绑定对象，不是数字签名：知道算法的人能计算它，不能据此证明真实用户批准。示例的批准集合来自可信调用代码；生产批准记录应有真实用户、时间、授权范围、版本和过期检查。

工具名称与参数的快照应先展示给用户，再由确认入口建立批准记录。不要从模型的一句“用户同意”直接创建approved_fingerprints。用户在会话中已经明确授权的同范围动作可沿用该授权，不必设计无意义重复弹窗。

## 执行边界还要检查资源前提

真实写入常有资源版本、当前状态和数额限制。用户批准退款时订单已改变，执行器应再次核对；否则确认的是旧条件，写入发生在新状态。

本工程没有订单和版本前提，仅演示title/角色/批准。扩展时把“可以创建”“可以退款”的业务条件写在执行器，而不是Prompt里只提醒模型。Prompt帮助选择，执行边界保障可执行范围。

## 常见错误与练习

把staff写在参数就成功：说明授权读错来源。权限题仍返回隐藏数目：检查matched_count和日志是否过滤。批准后参数改动还能执行：检查指纹绑定和执行时重校验。权限已撤销却读到幂等缓存：授权必须在缓存回读之前。

**跟做：** 运行两种role，解释为什么没有写入。

**独立：** 写出三例：Schema失败、权限失败、需确认；给每例下一步，不能都用“再试一次”。

**迁移：** 为订单退款工具列参数、可信上下文、资源前提、确认内容、审计字段。完成标准：不能由模型传管理员身份或决定授权，已授权动作仍核对最新订单状态。

> [!example]- 参考答案与解析
> Schema错要修改参数；权限不足要说明限制或走正式授权流程；需确认要展示具体动作并等待有效批准。退款前提可能是订单属于当前用户、未退过、金额不超已支付、币种一致、资源版本未变。不能依赖模型自报满足条件，也不能自动重复写入。
