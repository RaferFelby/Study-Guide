# 第 3 讲：关联工具调用与结果回传

> [!nav] 页面导航

## 要解决什么问题

一次模型响应可能提出两个工具调用，执行器怎样把结果正确交回？只回一段“成功了”无法知道成功的是哪次请求。**call_id**是本次调用关联编号，把模型请求与工具结果配对。

本工程用assistant.tool_calls和role=tool展示内部消息机制。不同供应商字段、内容块、结束原因和约束不同；本地格式不能直接替代真实API适配器。当前没有外部模型请求。

前置是上一讲ToolCall和JSON字符串。注意两个层级：外层消息是dict，内层arguments/content在本协议里是JSON字符串，需要再次解析。

## 一轮消息顺序

```text
用户任务
→ assistant 提出 tool_calls（call-1、名称、参数JSON）
→ 控制器检查并执行
→ tool 返回 tool_call_id=call-1 和结构化结果JSON
→ 决策器读取观察，提出新动作或最终答复
```

工具结果由执行器产生，不能让模型在assistant文本里写“工具返回成功”就作为真实执行证据。上一单元policy直接读tool_records，本单元解释如何序列化为可关联消息。

工具调用不是final：工具数据可能为空、权限不足或需要确认，下一次决策必须根据实际返回处理。

## 完整最小示例

在示例工程新建 `inspect_messages.py`：

```python
from contracts import ToolCall, ToolContext
from messages import execute_calls, make_assistant_message, validate_tool_message
from runtime import ToolRuntime

calls = [ToolCall("q1", "search_policies", '{"query":"storage","top_k":1}')]
print(make_assistant_message(calls)["tool_calls"][0]["id"])
pending = {"q1"}
messages = execute_calls(calls, ToolRuntime(), ToolContext("learner", "public"))
validate_tool_message(messages[0], pending)
print(messages[0]["role"], messages[0]["tool_call_id"])
print(pending)
```

预期q1、tool q1、set()。pending保存尚未收到结果的ID；验证成功后删除对应ID。若相同消息回传第二次，ID已经不在pending，拒绝重复消费。

`execute_calls`先检查整批ID唯一，再逐个调用runtime.execute，把返回转成UTF-8友好的JSON字符串。整批先验ID避免执行第一个写操作后才发现第二个重号。

## 调用ID不是幂等键

call_id标识本轮协议调用，新的重试可能有另一个call_id；幂等键标识同一个业务操作，重试应保持同键。它们解决不同问题。

两个不同ID的create_ticket仍可能是同一业务请求；两个相同ID也可能参数被改变。协议相关性、动作批准和幂等冲突要分别检查，不能只靠一个字符串完成所有控制。

本工程验证每批ID唯一，但没有跨整段长期对话的持久ID仓库。真实适配器应跟踪pending、已消费结果、模型响应编号和可能重试，避免将旧结果关联新请求。

## 返回结构再检查

`validate_tool_message`检查role=tool、ID在pending、结果恰好含ok/data/error；成功有dict data且error为空；失败有error.code/message/retryable且data为空。它验证通用外壳，不验证每个工具data全部业务字段；生产应为每种成功payload维护输出Schema。

如果工具调用失败，仍应按原call_id返回结构化错误，让后续决策知道发生什么。不要缺一条结果而让模型以为仍在等待；也不要把错误伪装成空成功。

## 多调用与顺序边界

当前execute_calls顺序执行，返回列表顺序与请求相同。下一单元将并行，但仍必须保留call_id，不能按完成先后位置配对。依赖关系也要先判断：第二个工具需要第一个的订单号，就不能一起盲并行。

全批返回不表示全批事务：第一个写已成功，第二个可能失败。真实系统需报告部分成功、不要自动撤销未授权资源。当前只有本地演示工具，没实现跨工具事务。

## 动手排错与练习

把result的tool_call_id改成missing，validate会ValueError，不执行未知结果。把两次ToolCall的ID都设q1，make_assistant_message在执行前拒绝。把content改普通文本，JSON解析失败，应排查工具返回协议。

**跟做：** 跑最小脚本，对照外层消息ID与工具返回ID。完成标准：知道JSON字符串需要解析后才能读ok。

**独立：** 有q1/q2两次调用、结果先q2后q1，说明怎样关联，为什么不能用列表下标配对。

**迁移：** 为具体供应商API写适配检查表：调用字段、参数编码、关联ID、允许消息顺序、错误回传、流式拼接和结束原因。需要真实调用时核对官方接口并明确费用/秘密处理，本工程没有替你验证它。

> [!example]- 参考答案与解析
> 用tool_call_id查询pending记录，完成顺序不影响关联；q2先返回也不能给q1当观察。call_id不防止重复业务写入。真实流式参数可能分片，必须拼完并校验再执行，不能收到半截JSON就启动工具。
