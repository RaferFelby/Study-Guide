## 要解决什么问题

工具名选对、参数合法、工具执行ok=True，用户任务仍可能没完成。比如用户要求两条资料，模型传top_k=1；Schema允许1，却没有遵守请求。本讲把工具选择、参数语义和最终任务结果分开评估。

前置是前五讲。回忆：无匹配成功与系统错误不同，call_id与幂等键不同，权限与确认不同。若混淆先回对应最小实验。

## 三层指标与分母

**工具选择准确率**：测试任务中，选择的工具符合gold职责的比例。允许多个正确工具时应标可接受集合，不能强行唯一。

**参数准确率**：测试任务中，工具名称正确且关键参数符合任务要求的比例。本工程用精确字典匹配；真实query语义等价时应规范化或人工判断。Schema合法率可另外统计，不等同于参数正确率。

**最终任务完成率**：测试任务中，实际结果满足业务完成标准的比例。要看真实结果和副作用，不能只看模型说“已完成”。本探针要求正确工具/参数、返回所需证据且预算字段符合需求。

如果四题工具名全对，第四题参数少返回一条，则选择率1.0、参数率0.75、任务完成率0.75。三个指标分母本工程都用全部四题，不用“工具名正确题中的参数率”偷偷换分母。

## 运行固定规则探针

在示例工程运行demo，最后一段evaluate_selector输出上述结果。打开 `evaluation.py`：CASES有task、gold_tool、gold_arguments和gold_evidence；choose_call只读取task，不接gold。

它通过“计算/数据库”关键词选择服务，故意没有支持“两条”。这是假设明确的规则选择器，未使用真实模型，因此不能把75%称为LLM工具能力。

想单独查看，在示例工程创建 `inspect_evaluation.py`：

```python
from evaluation import evaluate_selector

report = evaluate_selector()
print(report["tool_selection_accuracy"])
print(report["argument_accuracy"])
for row in report["rows"]:
    if not row["completed"]:
        print(row)
```

预期1.0、0.75，失败任务“查询存储，返回两条”。独立练习先预测，再修规则；修过这题后它已成为开发题，需新保留题检验泛化。

## 工具粒度怎样影响选择

过细：每个字段一个工具，描述相似、选择困难、调用次数多。过粗：一个万能工具同时读/写/发消息，权限和重试难清楚。可发现性指模型或调用方能从名称、描述、输入示例理解什么时候使用它。

当前search_policies负责查询证据，create_ticket负责写工单。它们按任务责任与副作用分开。MVP先完成只读工具后再扩写，不为了数量增加无关能力。

生产工具说明宜包含正例和不适用场景、返回预算、错误处理。长描述也会占上下文和增加歧义，应让核心责任优先，而不是堆所有工程细节给模型。

## 返回摘要和截断

search返回有限evidence，每项保留原文、ID、定位；matched_count说明当前可见匹配数；truncated说明是否省略候选。省略内容不能默认为不存在，模型也不能假称已读完整库。

生产长文本可先保存完整结果，再给摘要/片段和可回查ID；截断还要考虑token数、字符边界、JSON完整性和证据句完整性。不能先把JSON字符串截一半当结果。下一单元会加入超长返回实验。

摘要应区分事实、错误与未获取部分；来自检索的文本是数据，不能让其中的指令修改工具权限。当前没有专门提示注入防护，后续安全单元继续。

## 验收步骤

运行：

```powershell
..\..\..\.venv\Scripts\python.exe -m pytest -q tests
..\..\..\.venv\Scripts\python.exe -m ruff check .
..\..\..\.venv\Scripts\python.exe -m ruff format --check .
```

保存一轮assistant/tool消息，检查每个call_id；记录合法、缺字段、类型错误、无权限、需确认、同键重复、同键冲突和无匹配案例。对每种失败写下一步：重规划/修参数/等待确认/明确说明不可做，而不是全都无条件重试。

## 持续项目接入

企业知识与工单数据助理可先暴露一个查询证据工具；接RAG后保持同样错误外壳和来源字段。添加真实工单工具时先设计可信上下文、确认、持久幂等和业务完成核验；当前内存演示不能替代真实系统验收。

模型适配器只把provider调用转成ToolCall，再把结构结果关联回去；runtime仍决定可执行范围。别把供应商字段散落进每个业务工具，接口迁移才更容易。

## 练习与答案解析

**跟做：** 找出四题探针的唯一失败，并说明Schema为何没挡住它。

**独立：** 在个人副本修choose_call，看到“两条”时设top_k=2；另写两条未见任务检查，不改gold凑分。完成标准：三层指标分别报告，保留原基线结果。

**迁移：** 设计真实Agent工具评估集，含不应调用、多个可接受工具、错误参数、权限不足、部分成功和重复写入。完成标准：业务完成依据实际证据/资源状态，不只看模型文本。

> [!example]- 参考答案与解析
> top_k=1是合法范围，却违背“两条”要求，需语义评估。修规则可令 `top_k = 2 if "两条" in task else 1`；这只支持一个词形，新的“给两个结果”仍可能失败。至少记录基线/修正/新保留题，不把已看过题的满分当泛化结论。
