# 第 5 讲：用幂等键处理重复写入

## 要解决什么问题

创建工单请求发出后网络超时，是没成功还是成功但回应丢了？直接再发可能创建两条。**幂等性**指重复执行同一操作不会继续增加预期效果；**幂等键**用来识别“同一个业务请求”，便于返回已有结果。

读政策通常没有额外写入效果；创建工单天然会每次新增，需明确去重机制。幂等与上一单元的动作循环检测不同：循环检测终止策略重复，幂等解决允许重试时如何避免重复业务效果。

前置是字典键、动作指纹和确认。这里用内存演示，不保证并发或进程重启后仍幂等。

## 键的范围与冲突

工程用 `(actor_id, "create_ticket", idempotency_key)`作缓存键。tuple包含身份、工具和业务键，避免不同用户或不同工具碰撞。参数指纹另外存储，检查同键是否仍同参数。

同身份同工具同键同参数：返回第一次结果，不新增。相同键不同标题：idempotency_conflict，不写。新身份同键：不同作用域，但仍需自己的权限与确认。

call_id只是一次协议关联，可以变化；幂等键在同一次业务操作重试时保持不变。每次重试生成随机新幂等键就失去去重意义；把所有任务固定同键又会冲突。

## 完整最小实验

在示例工程新建 `inspect_idempotency.py`：

```python
import json
from contracts import ToolCall, ToolContext
from runtime import ToolRuntime, call_fingerprint

runtime = ToolRuntime()
arguments = {"title": "演示工单", "idempotency_key": "request-1"}
fingerprint = call_fingerprint("create_ticket", arguments, "learner")
context = ToolContext("learner", "staff", frozenset({fingerprint}))
for call_id in ["w1", "w2"]:
    call = ToolCall(call_id, "create_ticket", json.dumps(arguments))
    print(runtime.execute(call, context)["data"]["ticket_id"])
print("工单数：", len(runtime.tickets))
```

预期两次都DEMO-1，工单数1。frozenset是不可变集合，本例表示批准指纹集合；可以判断成员，却不能用add修改。它减少意外改批准，不是权限隔离技术。

执行顺序：检查staff权限 → 查幂等记录 → 同键不同参数报冲突 → 同键同参数回已有结果 → 新键核验批准 → 创建工单 → 保存结果。重复回读不是新的写动作，所以同参数已有结果不再次要求确认；但权限仍先检查，撤权用户不能靠缓存获取结果。

## 对照冲突

继续在个人脚本中把title改“另一工单”，保留request-1，重新发一次。预期idempotency_conflict且工单仍1。它提示调用方业务键使用不当，不能直接自动换新键绕过去重；先确认是否确实是新的用户请求。

runtime返回deepcopy，调用者修改返回标题不会改变内存工单或缓存结果。复制保证记录对象不被意外共享污染，但不是数据库事务，也不能防止恶意同进程代码。

## 为什么内存不能保证线上恰好一次

两个并发请求可能同时查“键不存在”，再各写一条。进程重启后内存记录消失；写成功后保存幂等记录之前崩溃，会留下未知结果。真实幂等通常需要持久唯一键、原子事务、状态记录和对账。

若调用外部服务，应优先使用它支持的幂等键/查询接口，并记录外部请求ID。不能把内存dictionary加一段if就宣称“恰好一次”。外部写入与本地记录难以共享事务，需要明确中间状态和恢复流程。

**超时不等于失败**：可能请求尚未提交，也可能已成功；状态unknown应回查或人工处理，不应直接重复危险写入。下一单元的重试只针对已知安全可重试操作。

## 恢复与取消的关系

用户取消后，如果工具已创建工单，取消不会自动删除。可以向用户展示已完成记录，再在有授权且有补偿能力时撤销。补偿也是新业务动作，要有自己的契约、权限和幂等键。

没有真实外部操作的本地demo不会证明这些恢复机制，只帮你看清“查询已有结果”“重试原请求”“发新请求”“补偿”四种不同动作。

## 常见错误与练习

重复出现两条：查是否同键、是否同作用域、是否并发或重启。同键回错用户结果：检查actor/tenant作用域。参数变化仍回旧结果：必须比较指纹，不能只查键。缓存泄露权限：先授权，再回读。

**跟做：** 执行两次同键同参数，核对两次ID与工单数。

**独立：** 解释同键换标题、新键同标题、另一个身份同键三种情况。完成标准：知道标题相同不自动意味着同一业务请求。

**迁移：** 为持久数据库设计幂等表字段，写创建中、成功、失败、未知四态以及唯一约束和事务顺序。完成标准：说明并发/崩溃窗口，不把未来设计记成已实现。

> [!example]- 参考答案与解析
> 同键换标题冲突；新键同标题若有新批准会创建另一条；另一身份同键是新作用域，需要独立授权/确认。幂等表应至少有actor/tenant、工具、键、参数摘要、状态、结果ID、时间/过期；业务写和结果记录若同库应事务原子提交。外部未知结果要查状态，不盲目重写。
