# 第 4 讲：处理冲突并安全撤销

> [!nav] 页面导航
> [[01_学习指南/03_Linux_Git_Docker/00 Linux Git Docker 学习地图#学习顺序|单元 03：Linux Git Docker]] · [[01_学习指南/03_Linux_Git_Docker/逐讲学习/03 用 Git 保存可理解的历史|上一讲]] · [[01_学习指南/03_Linux_Git_Docker/逐讲学习/05 读懂 Dockerfile 和镜像|下一讲]]

## 学完后你会做到什么

你会知道冲突为什么产生，能按步骤解决并继续合并；能用 stash 暂存未完成工作；能解释 merge、rebase、reset 和 revert 的边界。涉及共享分支或已经推送的历史时，安全性比命令短更重要。

## 1. 冲突是什么

当两个分支从共同祖先出发，修改了同一个文件的同一段内容，Git 无法替你决定保留哪一版，就会标记冲突。冲突不是 Git 损坏，也不表示两边都错；它表示需要人理解业务后做选择。

文件中可能出现：

~~~text
<<<<<<< HEAD
当前分支的内容
=======
另一个分支的内容
>>>>>>> feature
~~~

<<<<<<< 到 ======= 是当前分支版本，======= 到 >>>>>>> 是要合并的分支版本。解决时要删除这些标记，留下真正应该存在的最终内容，然后检查全文，而不是只删掉标记。

## 2. 解决冲突的固定流程

~~~bash
git status
# 编辑冲突文件，删除标记并保留正确内容
git diff
git add path/to/conflicted-file
git commit
~~~

status 会列出 unmerged paths；编辑后用 diff 检查上下文；add 告诉 Git“这个文件已经解决”；最后完成合并提交。不要在还没理解内容时直接选择编辑器的“接受全部当前”或“接受全部传入”。

如果发现冲突太复杂，可以取消本次合并：

~~~bash
git merge --abort
~~~

这会回到合并开始前的状态，但前提是 Git 当前确实处于 merge 过程。运行前看 status，不要把它当作普通撤销命令。

## 3. merge 与 rebase 的差异

merge 保留两条分支的分叉和合并关系，可能生成一个合并提交；它适合把已经形成的分支历史合到目标分支。

rebase 把当前分支的提交重新播放到另一个基准上：

~~~bash
git switch feature
git fetch origin
git rebase origin/main
~~~

这样历史看起来更直，但提交 ID 会改变，因为提交的父节点改变了。rebase 适合整理自己尚未共享的分支；不要随意 rebase 别人正在使用的公共分支。遇到冲突时：

~~~bash
git status
# 编辑并解决文件
git add path/to/file
git rebase --continue
# 如果决定放弃
git rebase --abort
~~~

## 4. stash：暂存还没准备提交的工作

你正在修改功能，却需要切换分支处理紧急问题，可以用：

~~~bash
git stash push -m "wip: draft service change"
git switch main
# 处理完紧急工作
git switch feature
git stash list
git stash pop
~~~

stash 是临时存放，不是长期版本记录。重要工作应尽早提交到自己的分支；stash 可能被清理，也不如提交容易审阅。pop 如果产生冲突，按普通冲突流程处理，并确认临时修改没有丢失。

## 5. reset 与 revert 的边界

| 命令 | 作用 | 适合场景 | 主要风险 |
|---|---|---|---|
| git reset --soft | 移动分支指针，保留改动在暂存区 | 私人分支整理最近提交 | 已共享历史会改变 |
| git reset --mixed | 移动指针，改动回工作区 | 私人分支拆分提交 | 容易忘记重新暂存 |
| git reset --hard | 移动指针并丢弃未提交改动 | 明确确认、可恢复的本地练习 | 可能永久丢失工作 |
| git revert | 新建一个反向提交 | 撤销已共享或已推送提交 | 历史保留，需处理后续冲突 |

最重要的判断是：这段历史是否已经被别人拉取或用于部署？已共享历史优先用 revert，不要强行 reset 后 push。reset --hard 具有破坏性，执行前必须确认目标提交、工作区内容和备份。

## 6. 用 reflog 找回错误移动的指针

Git 通常会记录本地 HEAD 移动：

~~~bash
git reflog
git switch -c recovery HEAD@{1}
~~~

reflog 不是远程备份，保留时间和清理策略受本地配置影响；它只是错误 reset 或 rebase 后的恢复线索。先创建恢复分支，再决定如何整理，不要继续执行更多覆盖性命令。

## 7. 动手操作

1. 在一个临时练习目录初始化 Git，不要在重要项目中故意制造冲突。
2. 创建两个分支，让它们修改同一行，合并并按流程解决。
3. 在未完成修改时使用 stash，切换分支后恢复。
4. 比较一个本地未共享提交用 reset 整理、一个已共享提交用 revert 撤销的差异。
5. 写一张表，说明 merge、rebase、reset、revert 各自是否改写已有历史。

## 8. 常见错误

- **只删除冲突标记不读上下文：** 可能留下语法正确但业务错误的内容。
- **对公共分支 rebase：** 会改变别人已经看到的提交 ID。
- **把 stash 当备份：** 临时保存不等于长期可追溯版本。
- **遇到问题就 reset --hard：** 先保存现场，优先使用 abort、revert 或恢复分支。

## 9. 练习与答案解析

**跟做：** 在临时仓库制造一个文本冲突，完成 status、编辑、add、提交全过程。

**独立：** 给出三个场景：私人分支最后一个提交写错、公共分支已经部署、工作区有未完成修改但要切换分支；分别选择 reset、revert、stash，并解释理由。

**迁移：** 设计一次远程训练代码更新：如何用提交号、分支和 revert 保证出问题时能回到上一个版本？

> [!example]- 参考思路（先完成再展开）
> 私人且未共享的历史可以整理；已经共享的历史优先追加反向提交；未完成工作需要临时离开时可 stash，但最终应落成正式提交。远程任务更新前记录旧提交号，出问题时先停止或隔离任务，再 revert 或切回已验证版本。

完成标准：能解决一个冲突，能解释四个核心命令的适用范围，并能说出 reset --hard 为什么必须谨慎。

## 本讲小结

Git 的安全边界取决于历史是否共享。merge 保留分叉，rebase 重排自己的历史，reset 移动指针，revert 用新提交撤销，stash 临时保存未完成改动。下一讲把应用放进 Docker 镜像，观察构建上下文和镜像层。
