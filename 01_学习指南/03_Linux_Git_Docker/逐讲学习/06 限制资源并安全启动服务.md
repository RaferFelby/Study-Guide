## 1. 为什么需要资源限制

没有限制的程序可能使用过多内存、CPU 或临时文件空间，影响同一台机器上的其他任务。资源限制把“最多允许使用多少”写成运行配置，让超出边界时出现可观察、可排查的失败。

示例命令：

~~~powershell
docker run --rm --name linux-git-docker-demo -p 8000:8000 --memory=256m --cpus=1 linux-git-docker-demo:local
~~~

memory 限制内存，cpus 限制 CPU 配额。限制太小会导致服务被终止或变慢，所以应根据测量设定，不要把任意数字当作性能优化。

## 2. 只读根文件系统和临时目录

如果服务不需要修改镜像中的文件，可以让根文件系统只读：

~~~powershell
docker run --rm --read-only --tmpfs /tmp:rw,noexec,nosuid,size=16m -p 8000:8000 linux-git-docker-demo:local
~~~

read-only 阻止进程修改容器根文件系统；tmpfs 在内存中提供临时目录，容器停止后消失。noexec、nosuid 是额外的限制选项，但不是绝对安全保证。若程序需要写日志或上传文件，应明确挂载专用目录或卷，并限制写入范围。

示例服务只把日志写到标准输出，所以可以使用只读根文件系统。观察日志用 docker logs，不需要在容器里创建日志文件。

## 3. 使用 Compose 固定启动配置

打开 compose.yaml：

~~~yaml
services:
  demo:
    build: .
    ports:
      - "8000:8000"
    read_only: true
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=16m
    mem_limit: 256m
    cpus: 1.0
    restart: "no"
~~~

Compose 把镜像构建、端口、资源、卷、网络和重启策略集中记录。请在示例工程目录打开 VS Code 终端，按下面三步操作。

### 步骤一：构建并启动

~~~powershell
docker compose up --build -d
~~~

`-d` 是 detach（分离运行）的缩写：服务留在后台运行，终端会返回提示符。

> [!warning] 为什么这里要加 `-d`
> 不加 `-d` 时，Compose 会在前台持续显示日志并占用终端。按 `Ctrl+C` 会停止服务，因此无法在同一个终端继续检查。

### 步骤二：检查服务

~~~powershell
docker compose ps
docker compose logs demo
curl http://127.0.0.1:8000/health
~~~

- `docker compose ps`：查看 `demo` 服务的运行和健康状态。
- `docker compose logs demo`：查看服务输出。
- `curl .../health`：访问健康接口，正常时返回包含 `"status": "ok"` 的 JSON。

### 步骤三：停止并清理

~~~powershell
docker compose down
~~~

这会停止并移除本次编排创建的容器和网络。卷是否删除取决于命令和配置；执行清理前先确认数据边界。

## 4. 健康检查和进程状态

Docker 的健康检查是一个周期性命令，不等于服务业务完全正确。下面这条命令适用于使用 `docker run --name linux-git-docker-demo ...` 启动的容器。因为 `docker run` 会占用当前终端，启动后请另开一个 VS Code 集成终端执行检查；停止容器后，命令中的 `--rm` 会删除容器，届时就不能再 inspect 它。如果你使用 Compose 启动，请运行 `docker compose ps` 查看 `demo` 服务的健康状态：

~~~powershell
docker inspect --format="{{.State.Health.Status}}" linux-git-docker-demo
~~~

可能看到 starting、healthy 或 unhealthy。若 unhealthy，按顺序检查：

1. docker ps 是否显示容器仍在运行。
2. docker logs 是否有启动异常。
3. docker inspect 查看端口、环境和健康检查失败记录。
4. 在容器内确认进程和监听端口。
5. 检查宿主机端口是否已被其他程序占用。

健康检查只提供一个信号；真正的业务指标、错误率和延迟仍需要日志与监控。

## 5. 密钥、配置和镜像边界

配置可以分成三类：

- 可以进入镜像的默认值，例如服务端口和非敏感模式。
- 应在运行时注入的环境配置，例如外部服务地址。
- 必须由密钥管理器或 secrets 注入的密码、token 和证书。

检查镜像构建上下文时，应确认 .dockerignore 排除了 .env、私钥、模型缓存和本地配置。即使某个文件没有被 COPY，构建脚本和日志也不应打印密钥。提交前可运行：

~~~powershell
rg -n "API_KEY|TOKEN|PASSWORD|BEGIN .* PRIVATE KEY" --glob '!*.pyc'
~~~

这只是线索搜索，不是完整秘密扫描；真正项目还应使用专门扫描工具和密钥轮换流程。

## 6. 从 Git 到容器启动的完整流程

一个可追踪的部署动作应记录提交号：

~~~powershell
git status
git rev-parse --short HEAD
docker build --pull -t linux-git-docker-demo:local .
docker run --rm --name linux-git-docker-demo -p 8000:8000 --memory=256m --cpus=1 --read-only --tmpfs /tmp:rw,noexec,nosuid,size=16m linux-git-docker-demo:local
~~~

先确认工作区状态和提交号，再构建镜像；启动参数包含端口和资源限制；最后用 /health、日志和进程状态确认结果。若启动失败，保存构建输出、镜像标签、提交号和启动命令，不要只说“容器起不来”。

## 7. 远程服务器上的恢复现场

在远程机器上，通常组合使用：

~~~text
SSH 登录
  → tmux attach 恢复长任务
  → git rev-parse 记录代码版本
  → docker ps / logs 检查容器
  → nvidia-smi 或 ps 检查资源
  → 保存结果和失败日志
~~~

远程训练任务和 Docker 服务都要有明确的输出目录、日志位置、配置版本和停止方式。不要用 root 账号运行所有操作；不要把云平台 token 写入 compose 文件。

## 8. 动手操作

1. 阅读 compose.yaml，指出端口、资源、只读和临时目录设置。
2. 若 Docker 可用，用 README 的构建命令启动服务，再访问 /health。
3. 加上 memory、cpus、read-only 和 tmpfs 参数，确认健康检查仍通过。
4. 查看容器日志和状态，停止服务后确认容器是否按 --rm 清理。
5. 写一份“远程服务器性能异常”的排查报告模板，包含提交号、容器状态、日志、CPU、内存、磁盘和 GPU。

## 9. 常见错误

- **把资源限制当成性能优化：** 限制只规定上限，可能让程序更早失败。
- **只看容器是否 running：** 进程活着不代表健康接口和业务正常。
- **使用 read-only 后程序报权限错误：** 先确认程序真正需要写入的目录，再挂载最小范围的 tmpfs 或卷。
- **将 secrets 放在 compose 文件：** 配置文件会进入 Git 历史和备份，使用运行时密钥注入。
- **远程失败后直接重启：** 先保存现场和版本，否则无法分析原因。

## 10. 练习与答案解析

**跟做：** 用 Docker 启动示例服务，记录镜像标签、容器状态、健康状态和 /health 输出。

**独立：** 设计一个 512 MB 内存、2 个 CPU 的服务启动命令，并说明为什么仍要观察日志和实际资源使用。

**迁移：** 为一个 GPU 训练容器写出恢复现场清单，至少包括 Git 提交、镜像标签、tmux 会话、GPU 进程、日志和 checkpoint 路径。

> [!example]- 参考思路（先完成再展开）
> 先记录版本，再检查容器和资源，最后决定重启或回滚。启动配置中的资源上限、只读根文件系统和 tmpfs 需要与程序写入需求匹配；密钥由运行时注入，绝不进入 Dockerfile、镜像层或 Git 历史。

完成标准：能从 Git 提交号追踪到镜像和容器，能解释 CPU/内存限制、只读根目录、tmpfs、健康检查和密钥注入的作用。
