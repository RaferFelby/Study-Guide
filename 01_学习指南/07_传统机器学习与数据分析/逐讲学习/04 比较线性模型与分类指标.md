## 这一讲要解决什么问题

分类模型可能给出类别，也可以给出“属于正类的概率”。只看一个正确率会遮住重要错误。本讲用多数类基线、逻辑回归和混淆矩阵，理解不同指标回答的问题。

## 先建立一个基线

**基线**（baseline）是一个简单、可解释的参照。`DummyClassifier(strategy="most_frequent")` 永远预测训练集中数量最多的类别。复杂模型必须比这个参照提供额外价值；如果不能，先检查数据、标签和评估方式，而不是盲目堆模型。

## 逻辑回归为何能做分类

逻辑回归（Logistic Regression）名字里有“回归”，但常用来做分类。它先将特征加权得到分数，再通过逻辑函数把分数压到 0 到 1，作为正类概率。阈值默认为 0.5：概率达到阈值就预测正类。参数 `C` 控制正则化强度的反向量级：较小的 `C` 通常约束更强，防止系数过大。

示例 Pipeline 已把标准化放在逻辑回归前，因此不同量纲的数值特征不会只因单位很大就天然拥有更大影响。运行 `train.py` 会在 dev 上并列打印基线和候选模型的 AP、ROC-AUC；模型参数与数据划分固定，输出即可复现。

## 混淆矩阵：四种结果

对正类“续费”而言，矩阵通常按 `[[TN, FP], [FN, TP]]` 排列：

| 结果 | 意思 | 本例 |
|---|---|---|
| TN 真负例 | 真实为 0，预测也为 0 | 没续费，模型判断没续费 |
| FP 假正例 | 真实为 0，却预测为 1 | 没续费，模型认为会续费 |
| FN 假负例 | 真实为 1，却预测为 0 | 续费了，模型没识别出来 |
| TP 真正例 | 真实为 1，预测也为 1 | 续费了，模型判断会续费 |

**Precision（精确率）** = TP / (TP + FP)：模型说“正类”的样本中有多少是真的。**Recall（召回率）** = TP / (TP + FN)：所有真实正类中找到了多少。**F1** 是 Precision 与 Recall 的调和平均，只有当两者同等重要时才适合作为单一折中指标。

## AP、PR-AUC 与 ROC-AUC

PR 曲线关注 Precision 与 Recall 的关系。**AP（Average Precision，平均精确率）**按召回率的增量对各点精确率加权；**PR-AUC**表示PR曲线下的面积，必须说明插值／积分方式，梯形积分的值不一定等于AP。本工程实际调用`average_precision_score`计算AP，应按AP报告，不能当作梯形PR-AUC。定义见 [scikit-learn官方AP文档](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.average_precision_score.html)。

ROC 曲线关注真正例率与假正例率；ROC-AUC衡量随机正例分数高于随机负例的倾向，并对平分计半。AP与ROC-AUC都是跨阈值的排序指标，不直接告诉你某个业务阈值下有多少错误。

类别明显不平衡时，即使假正例率低，大量负例乘以这个比例仍可能产生很多假正例，使Precision很低。单纯增加同分布负例的数量不会自动提高ROC-AUC；ROC使用类内比例，不直接表达正类稀少带来的精确率问题。因此要结合AP、混淆矩阵、正类比例和具体阈值阅读。`evaluate_probabilities`现在返回`average_precision`，旧字段`pr_auc`作为兼容别名保留且仍存AP；读取旧报告时也应按AP解释。

### 回归任务的 MAE 与 RMSE

分类预测的是类别；回归预测的是数值，例如维修时间或月收入。常见回归误差指标包括：

- **MAE**（平均绝对误差）先算每个样本 `|预测值 - 真实值|`，再取平均。真实值 `[10, 12]`、预测值 `[8, 15]` 时误差是 `[2, 3]`，MAE 为 2.5。它比较直观，单位与目标值一致。
- **RMSE**（均方根误差）先把误差平方，取平均后再开平方。同一例子 RMSE = `sqrt((2² + 3²) / 2)`，约为 2.55。平方会让较大的错误影响更明显，单位仍与目标一致。

两者都依赖目标量纲，不能直接比较不同单位任务。若业务特别在意少数巨大偏差，RMSE 会更敏感；若想让每个样本的绝对偏差比较容易解释，可从 MAE 开始。分类问题不能把正类/负类直接拿 MAE 当首要指标。

## 动手操作

1. 在示例工程目录运行 `..\..\..\.venv\Scripts\python.exe train.py`。
2. 对比 `baseline` 与 `logistic_regression` 的 dev AP。模型数据固定，但结果并不保证每种模型都大幅改善；如有不改善，记录这个事实。
3. 打开 `results/report.json`，查看最终测试集 `confusion_matrix`，按上表将四个格子解释成续费场景。
4. 不看答案，计算某个输出的 Precision、Recall。例如 TP=18、FP=12、FN=6：Precision=18/30=0.6，Recall=18/24=0.75。
5. `accuracy_score` 看所有预测中正确的比例。若 95% 是负类，永远预测负类也有 95% accuracy，所以一定要和基线及任务需求一起解读。

## 常见错误

- **把 ROC-AUC 当成“阈值为 0.5 时的准确率”。** ROC-AUC 衡量排序，和单一阈值的分类结果不同。
- **Precision 与 Recall 分母记反。** Precision 的分母是预测正类；Recall 的分母是真实正类。
- **看到 F1 高就不看矩阵。** 两组不同错误分布可以有相近 F1；业务可能更在意 FP 或 FN 其中之一。
- **拿开发集最高分说成测试成绩。** dev 参与模型选择，报告要清楚区分开发和最终测试。
- **把概率说成已校准概率。** 排序更好不表示预测 0.8 的样本恰好 80% 为正类；校准要单独验证。

## 练习与答案解析

### 跟做练习

若 TP=18、FP=12、FN=6，求 Precision、Recall，并用一句话分别解释。

> [!example]- 参考答案
> Precision=18/(18+12)=0.60，表示模型报为正类的样本中 60% 真正为正；Recall=18/(18+6)=0.75，表示所有正类中模型找到了 75%。

### 独立练习

对比 `accuracy` 与 `balanced_accuracy`。完成标准：能说明类别不均衡时为什么平均每类召回率有参考价值，并在报告中同时列出基线。

### 迁移练习

把任务改成预测罕见故障，漏报比误报贵 20 倍。你会先看哪些指标和混淆矩阵格子？为什么 accuracy 不是首选？

> [!example]- 参考思路
> 重点看 Recall/FN（漏报）及在可接受误报量下的 Precision，观察 PR 曲线和 AP；用业务成本比较阈值。accuracy 被大量正常样本支配，可能掩盖几乎找不到故障的模型。

## 本讲小结

基线回答“复杂模型是否带来增益”；指标回答不同问题。先讲明正类和错误代价，再解释 Precision、Recall、AP、ROC-AUC 与混淆矩阵，不能只报一个分数。
