# 第 2 讲：保留来源页码版本与权限

## 为什么每块文字都要带“来处”

只存正文会失去回答的证据。用户问“这句话来自哪一页、哪个版本？”如果数据库只有文字，就很难核实或删除旧内容。因此，来源路径、来源 ID、页码/段落、版本、权限标签必须在切块时一路带到检索结果。

元数据就是描述内容的数据。本例中一条检索结果包含 `source_id`、`source_path`、`version`、`locator`（定位）、`permission`（权限标签）和 `text`。它们像图书的书名、版次、页码与借阅范围；类比只帮助记忆，实际是数据库中与正文一起保存的字段。

## 读懂源码里的两张表

在 VS Code 查看 [knowledge_base.py](../示例工程/knowledge_base.py)。SQLite 是 Python 自带的轻量关系数据库，本例用 `sources` 保存来源版本和内容摘要，用 `chunks` 保存每条文字与引用位置。`PRIMARY KEY`（主键）要求每行有唯一身份；`FOREIGN KEY`（外键）要求 chunk 对应一个存在的来源。

`source_id` 由工程指定且跨版本稳定，例如 `handbook`；`version` 则区分内容快照，例如 `v1`、`v2`；`locator` 可以是 PDF 页码、Markdown 段落、网页标题或 CSV 行号。版本变化时要生成新 chunk ID，避免旧版本结果混入新版本。相同 source/version/内容用 SHA-256 摘要做快速去重判断；摘要相同不代表你可以忽略权限字段变化，因此代码也比较权限。

访问控制列表（ACL）是“谁能读什么”的规则。本例用小标签 `public` 和 `staff` 示范，CSV 行可分别带权限，切块时会保留该标签，查询时先过滤不允许的块。真实系统要由可信服务端根据已验证身份提供权限，不能让用户任意传入 `{ "staff" }` 就获得员工内容。还要考虑权限继承、撤权延迟、日志和备份中的敏感内容。

## 动手操作

运行 demo，观察引用打印为 `compute / v1 / 段落…`。首次 `replace_source` 返回 `True`；同内容同版本重复运行返回 `False`；更新为 `v2` 会先在同一事务中删除旧来源及 chunk，再写入新版本。事务（transaction）是一组要么一起提交、要么一起撤销的数据库变更，防止只删成功却插入失败。

随后 demo 把权限由 `public` 改为 `staff`，公开查询不再命中；删除来源后 chunk 数归零。测试文件 [test_knowledge_base.py](../示例工程/tests/test_knowledge_base.py) 对这些行为做自动检查。

## 常见错误与练习

- 引用只写文件名：同一文件改版后不能辨别旧内容；增加稳定来源 ID 和显式版本。
- 先清库再解析新文档：解析失败会丢掉可用索引；先完整解析和校验，再在事务中替换。
- 删除源文件但保留向量/缓存：检索仍可能返回已删除内容；删除要传播到所有索引与缓存层。
- 把权限标签当身份认证：标签只是过滤字段，身份必须由可信认证逻辑产生。

**跟做：** 将 demo 的 `v2` 改成 `v3`，观察旧版本不再返回。

**独立：** 把 permission 改为 `staff`，对比 public 和 staff 查询结果。

**迁移：** 设计一个包含 `source_id/version/locator/permission/content_hash` 的会议知识库表结构，画出更新与删除步骤。完成标准：可以解释每个字段用途，且说清“索引返回了一条文字”如何验证回原文。

> [!example]- 参考答案与解析
> 最小方案是在更新前完成读取、清洗、切块；随后开启数据库事务，按 `source_id` 删除旧 chunks 和来源记录，插入新来源及全部 chunks，成功后提交。向量库若是单独服务，还需记录更新任务状态并设计可重试/对账流程；SQLite 事务不能自动覆盖外部向量库。
