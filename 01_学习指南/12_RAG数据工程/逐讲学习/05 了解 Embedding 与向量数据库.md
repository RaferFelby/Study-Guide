## 从词面匹配走向语义向量

目前 demo 按共有词项数排结果。例如“显存”对“显存”能匹配，但如果用户问“GPU 可用内存”，词面不同就可能漏掉。Embedding（嵌入）模型将文字编码成固定长度的数字向量；训练目标使相关文本的向量更接近。检索时把问题与每段文档编码，再按 cosine similarity（余弦相似度）或模型支持的其他相似度排序。

向量是带有顺序的一串数，例如 `[0.8, 0.1, 0.0]`。维度是数字的个数；同一索引中的查询和文档向量必须来自兼容的模型与维度。向量的含义不是人能直接逐个数字解释的标签；示意向量只用于讲计算，不能代替训练好的 Embedding。

先看一个完全手工的二维例子：向量 A=`[1, 0]`，向量 B=`[0.8, 0.6]`。余弦相似度是“点积 ÷ 两向量长度的乘积”：A·B=`1×0.8 + 0×0.6 = 0.8`；A 长度=`√(1²+0²)=1`，B 长度=`√(0.8²+0.6²)=1`；所以 cosine=`0.8÷(1×1)=0.8`。它表示方向比较接近。若 C=`[0,1]`，A·C=0，因此余弦为 0，方向互相垂直。这个玩具坐标不是模型输出，只说明排序时可能用到的数学量；真实模型的每一维没有这种直观含义，且有些模型训练目标更适配点积等其他相似度。

Embedding 模型选型要看语言与领域、查询/文档任务类型、效果、维度、速度、内存/显存、商业许可、部署位置和数据能否外发。用自己的已标注问题集比较，不要只凭通用榜单。Sentence Transformers 文档介绍 `encode_query` / `encode_document`，某些模型会为 query 和 document 使用不同提示或任务模式；详见[官方使用说明](https://sbert.net/docs/sentence_transformer/usage/usage.html)与[语义检索说明](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)。

## 向量数据库解决哪类工程问题

向量数据库保存向量、正文 ID 和元数据，并提供近邻检索及过滤接口。有的库还内置 embedding 函数；有的只接收外部算好的向量。Chroma 的[官方文档](https://docs.trychroma.com/docs/overview/introduction)可作为具体产品例子。数据库选型要核实持久化、过滤、备份、并发、访问控制、向量更新/删除和版本兼容性；“能存向量”不等于已处理权限和来源引用。

生产检索通常至少携带 `(embedding, chunk_id, source_id, version, locator, permission)`。先依据权限过滤，再按相似度取候选，最后用 chunk_id 回查正文与可见引用。Embedding 模型或切块版本改变时，向量也要重算，不能把新模型的 query 向量和旧模型的文档向量直接比较。

## 现在为什么不运行真实模型

共享环境尚无 Sentence Transformers、PyTorch CUDA 配套的句向量模型，也没有 Chroma。安装框架和下载模型会改变环境并产生额外下载，因此这单元不做未经批准的依赖安装。前面讲过的 PyTorch CPU/GPU 可作为本地 embedding 推理可能使用的后端，但“能把模型放 GPU”不会自动决定模型质量；小模型 CPU 也可先验证流程，后续再按设备与成本选择。

当前程序做的是词面重叠基线与引用/更新逻辑，不执行神经网络、不生成真实向量、不构建向量索引。本单元验收证明的是数据管道原型，不是已完成生产语义搜索。后续 RAG 检索单元再用有版本记录的真实 Embedding/向量后端比较。

## 练习

**跟做：** 给“GPU 可用内存”与“GPU 显存”画两个二维玩具向量，手算点积或余弦相似度；明确坐标只是示例。

**独立：** 列出三个 Embedding 候选方案应检查的字段：模型、维度、语言、授权、运行设备、评估集结果与延迟。

**迁移：** 为含有客户姓名和内部政策的文档选本地或托管模型。完成标准：说明数据出境/访问控制、成本、质量测试以及模型升级后如何重建向量。

> [!example]- 参考答案与解析
> 选型不能只有“向量维度更大”或“榜单排名更高”。应在自己的 query/document 标注集上比较 Recall@K/MRR，再查看吞吐、延迟、显存/内存、部署和许可证。托管模型还要核查数据处理约定和服务区域；本地模型则要管理权重来源、版本、设备和更新成本。
