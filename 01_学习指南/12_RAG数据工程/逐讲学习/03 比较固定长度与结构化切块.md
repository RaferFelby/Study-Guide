# 第 3 讲：比较固定长度与结构化切块

> [!nav] 页面导航

## chunk 是什么，为什么需要它

chunk（文本块）是把一份长资料拆成适合检索和送入模型的小片段。整本手册作为一条记录太长，问题可能只与其中几句话有关；切得太短又会丢掉上下文。切块策略决定了“片段多大、边界放在哪里、引用如何定位”。

本单元先认识三种策略：固定长度按字符/token 数切；结构切块按标题、段落、表格行、页面等既有边界切；语义切块根据相邻句子的语义变化来判断边界，通常要有 embedding 模型或其他语义算法。比如“可以申请重置密码”和“系统会发送验证链接”主题相近，常会留在一块；接着说“GPU 显存由激活占用”时主题变了，可以考虑在前面断开。真实机制是模型计算句向量相似度，低于经验证的数据阈值时切分；类比“同一话题放同一段”不是边界判定的实际算法。注意，示例中的 `structure_chunks` 是结构切块；它没有模型，不应称为语义切块。

## 从两个最小策略开始

打开 [chunking.py](../示例工程/chunking.py)。`fixed_length_chunks` 按字符数取窗口，`overlap` 表示相邻窗口重复多少字符；重叠可缓和边界处上下文断裂，但会增加存储和重复命中。`structure_chunks` 则把上一讲解析出的每个段落/表格行保留为一块，并保留原定位。

字符数不等于 token 数。中文、英文、数字和代码的 tokenizer 分词数量不同，因此字符窗口只适合本机教学比较。接入模型后应按模型 tokenizer 的 token 数控制长度，并给检索片段、Prompt 和生成输出共同留上下文预算。

运行 demo 会分别建立 fixed 和 structure 两个临时索引，在相同的三条问题和人工标注来源定位上计算教学探针 Recall@3。Recall@K（K 位内召回率）表示标注相关片段是否出现在前 K 条结果里；demo 打印三题中命中 gold 段落/行的题数。夹具很小，使用词面检索且只有三题，因此不能据此宣布某策略普遍更好；它只示范固定问题、标注答案和指标的实验方法。固定窗口为每条结构段落切 32 字符、重叠 6 字符；结构策略保留段落/行。

## 怎么设计更可靠的对比

固定同一批文档、同一批 query、同一 embedding 模型、相同权限、相同 Top-K，只改变切块策略。逐个标出哪些 chunk 能回答每个 query，然后计算 Recall@K，并抽查引用上下文是否完整。记录 chunk 数和平均长度，因为只看召回率可能偏好过大的块；也记录索引规模和检索时延。语义切块的模型/阈值也要版本化，否则结果不可复现。

## 动手操作与排错

1. 在示例工程目录运行 `..\..\..\.venv\Scripts\python.exe demo.py`。
2. 打开打印结果，核对 fixed 与 structure 使用相同 `QUERY` 和 `GOLD_SOURCE_IDS`。
3. 把 `chunk_size` 改小到 40，再运行，观察块数和引用片段变化；不要改评估 query 或 gold 标签。
4. 运行 `..\..\..\.venv\Scripts\python.exe -m pytest -q tests`，确认 overlap 边界仍成立。

如检索结果把句子从中间切断，先看字符上限和重叠；如果结果正确但引用定位只有字符区间，固定窗口确实没有原始页/段落的自然边界，需要增加字符区间到源位置的映射或采用结构切块。

## 练习

**跟做：** 运行两个策略并记录块数量与 Recall@3。

**独立：** 给 fixtures 增加第三段 CPU 内容，新增 query 并标明正确来源，仍保持两个策略实验条件一致。

**迁移：** 为一份有标题、列表和表格的内部手册提出固定长度、结构、语义切块三个候选方案；写出质量、成本和引用完整性判断标准。完成标准：明确哪些指标可以计算、哪些结论必须靠真实 embedding 和已标注问题集验证。

> [!example]- 参考答案与解析
> 固定长度容易控制最大 token 数，但可能断开标题和句子；结构切块能保留标题、列表和表格行的关系，但可能产生长度悬殊的块；语义切块试图在主题变化处断开，但依赖模型、阈值和计算成本。可以先结构切块，再将超长结构块按句子/token 上限拆分。
