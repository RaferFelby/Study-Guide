## 从用户输入到可用结果

一个可检查的模型 API 流程是：准备输入与版本化 Prompt → 组装模型请求 → 限时调用 → 分析 HTTP/响应状态 → 提取模型内容与 usage → 解析 JSON → 校验 Schema → 校验业务语义 → 记录指标 → 返回预测或明确降级。

把每一步拆开，出错时就能知道应该重试网络、修改请求、重新组织 Prompt、拒绝格式错误，还是交人工处理。不要把“API 返回 200”误当作“业务结果正确”。

## 本工程操作清单

从 VS Code 的 `示例工程` 目录运行：

```powershell
..\..\..\.venv\Scripts\python.exe demo.py
..\..\..\.venv\Scripts\python.exe -m pytest -q
```

先看 demo 打印结构化结果、cache hit、429 后重试次数和三版 Prompt 夹具指标。再打开 [api_client.py](../示例工程/api_client.py)、[structured_output.py](../示例工程/structured_output.py)、[evaluation.py](../示例工程/evaluation.py) 阅读对应实现。假服务所有回答固定规则生成，不是语言模型。

## 原模块 C12 验收

- [ ] **C12-01** 对同一任务设计三个 Prompt，在相同固定评估集和环境条件下比较；记录版本与错误案例。
- [ ] **C12-02** 结构化输出先做 Schema 校验，再做语义校验；坏 JSON、漏字段、错类型与伪造证据均应失败。
- [ ] **C12-03** 报告格式成功率、任务成功率、延迟、输入/输出 token 和按有效报价计算的费用。
- [ ] **C12-04** 解析失败或暂时 API 错误有最大重试次数、错误可观测和安全降级；不能无上限重试或把降级伪装成成功。

示例的 pytest 证明客户端/validator/evaluator 的约定被测试，并不等同于真实模型 Prompt 的效能评估。要把 C12-01/03 标为完成，需选定一个服务和模型，在获得 API 权限及确认成本后，真实跑固定评估集，并另记模型快照、采样参数、时间与usage。当前不需要为了学习这一单元而安装 API SDK 或调用付费接口。

## 综合迁移练习

**跟做：** 给 `demo.py` 的输入增加一句与分类无关的背景，观察请求 hash 改变并绕过缓存。然后把完全相同请求再次发送，确认命中缓存。

**独立：** 为一个客服分类服务写失败矩阵，覆盖 400、401、429、500、超时、无效 JSON、Schema 错误、语义错误和缓存命中；给每项标出重试次数、日志字段和用户看到的结果。

**迁移：** 设计“会议纪要行动项提取” Prompt/API：至少 8 个固定样本，包含没有行动项与日期缺失；定义 Schema、来源证据语义检查、三版本比较指标和隐私安全的日志字段。完成标准是他人能按说明重跑并解释失败案例。

> [!example]- 参考答案与解析
> 请求 hash 覆盖 model 和输入正文，加入背景后 body 变化，所以 key 变化；重复相同请求才会命中这次进程内缓存。
>
> 400 修参数不重试；401/403 检查密钥和权限，不输出密钥；429/部分 5xx 可按服务商要求有限退避；超时需要考虑服务端可能已处理；JSON/Schema/语义错误一般先记录错误并有限修复或进入人工/unknown，重复相同请求不保证变好；缓存命中也要注明数据版本与 TTL。
>
> 会议行动项 Schema 可要求任务描述、负责人、截止日期、证据原句；日期缺失允许 null/unknown。证据需是原文片段，不得从日期常识推测。Prompt 版本只改 Prompt，其余环境固定。日志保存 case ID、版本、状态、usage、耗时和脱敏 request ID，不写 API key 或未脱敏会议正文。
