# 第 4 讲：为超时限流与缓存设置边界

## 为什么 API 调用需要失败处理

远程服务可能因为网络断开、等待超时、速率限制或暂时内部故障而无法按时回应。一次请求失败后，程序不能无限重试：这会增加费用、放大服务压力，也可能造成重复副作用。

- **timeout（超时）**：客户端最多等待多久。超时不一定表示服务器没收到请求；服务器可能已处理但回复没到。
- **rate limit（速率限制）**：服务商限制单位时间的请求数或 token 数；HTTP 429 常用于表示限流。
- **retry（重试）**：对可恢复错误再请求一次；应有最大尝试次数和等待间隔。
- **idempotency（幂等）**：相同操作重复执行时，结果不额外改变。客户端可为同一次逻辑请求生成稳定 key；只有服务端承诺识别该 key 时，才能依赖它防止重复处理/计费。
- **cache（缓存）**：保存成功响应，完全相同的后续请求可在短期内复用结果。缓存需要考虑敏感内容、租户边界、Prompt/model 版本和失效策略。

## 本工程的重试规则

打开 `示例工程/api_client.py`。`timeout_seconds` 限制每一次 HTTP 尝试的等待；`max_attempts` 限定总尝试次数，最多 10 次；只有 HTTP 429 和指定 5xx 状态码会重试。400 是参数问题，重复发送同一错误请求通常不会自动修好，所以不重试。

失败后使用指数等待：第 1 次失败等 `backoff_seconds`，第 2 次失败等两倍，以此增长，但本工程把每次等待封顶 5 秒。指数等待能避免失败时紧密轰炸服务；本示例没有加入随机抖动，也没有解析所有服务商的 `Retry-After` 格式。生产客户端应按服务商文档实现 Retry-After、随机抖动、总时限、并发限制和响应头观测。

每一次重发都复用同一个由请求内容计算的 `Idempotency-Key`。本机 fake provider 只用于验证 header 稳定；它并不证明某个真实服务商接受或保证该 header。收到超时后若服务端可能已完成请求，必须查真实提供方支持的幂等约定，避免重复收费或重复副作用。

## 缓存及敏感数据边界

缓存默认关闭，只有调用者传入字典才启用。缓存 key 包含 endpoint、凭证作用域摘要和序列化请求，模型名/消息变化就得到不同 key。密钥原文不会进入 key，但摘要也不是加密。缓存保存的是完整响应，因此可能包含用户文本或个人信息；示例只用内存字典，程序退出后消失。不要把敏感 prompt 或响应写入长期公共缓存。

真实系统还需确认缓存是否允许跨用户共享，是否要加入租户/权限版本、Prompt 版本、model 参数、温度和 Schema 版本，何时过期或清除，以及缓存命中是否可用于审计。API 提供的 prompt cache 与应用自己缓存完整回答不是一回事。

## 运行失败路径

在 `示例工程` 目录运行：

```powershell
..\..\..\.venv\Scripts\python.exe demo.py
```

本地服务对 `retry-once` 先返回 429 再成功；对 `always-rate-limit` 每次都返回 429；对 `bad-request` 返回 400。测试通过注入不等待的 `sleep_function` 来检查重试次数，不需要真的等待。预期演示打印限流后所用尝试次数为 2；重复限流最终抛出 `ApiError`；400 只发一次。

## 降级是什么意思

降级是系统明确退回安全、能力较低但可解释的路径。分类 API 超时后可返回 `unknown` 并标记“需人工处理”，而不是编造一个分类。降级结果必须与正常预测区分，保留错误类型/请求 ID等可观测信息（注意不记录密钥/敏感正文），并由调用方决定是否重试或交给人工。

本工程 `demo.py` 展示了失败后打印原因并生成 `unknown` 结果。注意 `unknown` 不符合成功预测的业务 Schema，正因如此它不会伪装成一个正常模型答案。

## 练习

**跟做：** 把演示的 `retry-once` 改成 `always-rate-limit`，预期在三次尝试后得到错误。不要把 `max_attempts` 调成极大值。

**独立：** 为 HTTP 400、429、503、网络超时分别选择“重试/不重试/交给调用者”，说明理由和上限。

**迁移：** 对会扣款的工具调用设计重试策略。明确网络超时后无法判断扣款是否完成时，系统应该先查询状态、使用服务端 idempotency key，还是直接再扣一次。

> [!example]- 参考答案与解析
> `always-rate-limit` 会连续收到 429，三次尝试后退出；最大尝试限制避免故障时无限循环。
>
> 400 不重试，应修请求；429 可按限流约定延迟后有限重试；503 通常可有限退避重试；网络超时可能是暂时问题，但服务器可能已完成请求，要结合幂等约定和副作用风险决定。
>
> 扣款重试前先用唯一业务操作 ID 查询/去重，优先使用支付服务商明示的幂等能力；超时后不能盲目重复扣款。LLM 生成接口的重复请求与有副作用的工具调用风险不同。
