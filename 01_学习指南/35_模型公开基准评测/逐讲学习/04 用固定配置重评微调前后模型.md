## 本讲任务与前置

重新加载自己的单元 34 权重，在固定任务上生成微调前后结果，核对配置与权重哈希。需要上一单元完成 CPU 实验并保存 base.pt、tool_only.pt；前置入口 [[01_学习指南/34_规划与工具使用微调/00 规划与工具使用微调学习地图|工具微调教程]]。本讲不重新训练，加载推理权重与等价续训不同。

完成标准：生成自己的新报告，能指出模型、任务、评分代码、设备、精度、解码和输出上限；能解释为什么三次贪心运行相同不能证明所有随机性都消失。

## 要解决什么问题：比较时一次改变几个因素

如果微调前用 CPU FP32、旧 Prompt，微调后用 GPU 低精度、新 Prompt、更多生成 token，分数差可能有多个原因。想检查权重变化，先固定其余输入与判定；两份模型权重本身当然不同，但两边都需要能追溯。

本次将上一单元实际权重重新载入，每个模型用相同正常任务、目录与宿主检查，并在同一设备使用贪心输出。它不是读取单元 34 汇总表，而是真正重新前向、生成调用、执行工具、生成答案，报告保存逐题记录。

## 概念：生成配置与模型版本

贪心是每步选最高分 token；采样是按概率随机选。temperature（温度）控制采样分布尖锐程度，top_p 保留累计概率达到指定阈值的候选集合；它们影响随机选择的条件，具体生效方式取决于后端。当前 generate 只有贪心，没有假装支持 temperature/top_p。

最大新 token 数是本轮允许生成的长度，不包含输入。设得太短可能截断 `<eos>`，太长可能改变停止行为与成本；本例固定为 8。precision 是计算精度，FP32 表示 32 位浮点数；quantization 是把权重等数值压缩到较低位表示的量化方案，本例 none。INT4 表示以 4 个二进制位编码整数，实际量化方案还需要缩放等信息，不能仅换一个名字就当已执行量化。GPU 与 CPU 是设备选择，设备不自动等于量化。

模型版本不要只写 Base/After，还保存权重 SHA-256；数据与 Prompt、评分代码也要固定。前后权重不同正是待比较因素，报告中分别记录，不把“可追溯”误解为权重必须一样。

## 动手操作：CPU 实际重评

在 VS Code 的本单元示例工程打开 PowerShell，先确认上一单元自己的目录存在；下面假设你已按它的第 4 讲生成 `report-my-cpu-01`。

```powershell
..\..\..\.venv\Scripts\python.exe local_probe.py --weights-dir '../../34_规划与工具使用微调/示例工程/report-my-cpu-01' --device cpu --output-dir report-my-local-cpu-01
```

`--weights-dir` 是相对当前工程的上一单元结果目录；读取而不改写权重。`--device` 选择推理设备；`--output-dir` 创建本单元的新报告目录，存在则拒绝覆盖。脚本单独运行，在本进程中只导入单元 34 的 data/model，不设置全局 PYTHONPATH，避免同名模块混用。

若权重缺失，先回单元 34 执行其 CPU 实验，再运行本命令。不要给未训练权重随便命名 base.pt 以通过路径检查；加载时还核对词表与用途。

预期打印 Base 正常端到端 0、tool_only 12，波动 spread 都 0，scope 明确为合成任务上的实际重评。不同个人权重可有不同结果；本讲成功标准是运行、保存并解释，而不是手工改成作者数字。

## 最小示例：读取自己的配置与输出

创建 `lesson_04.py`：

```python
import json
from pathlib import Path

with (Path("report-my-local-cpu-01") / "report.json").open(encoding="utf-8") as file:
    report = json.load(file)
print(report["device"], report["precision"], report["decoding"])
print(report["maximum_new_tokens"], report["quantization"])
for name, result in report["runs"][0]["results"].items():
    normal = result["normal"]
    print(name, normal["end_to_end"], normal["n"])
print(report["spread"])
```

```powershell
..\..\..\.venv\Scripts\python.exe lesson_04.py
```

作者预期为 `cpu fp32 greedy`、`8 none`、`base 0 12`、`tool_only 12 12`，最后 `{'base': 0, 'tool_only': 0}`。`runs[0]` 取第一轮，`normal` 是正常任务结果，n 是同一组 12 条分母；不要把这 12 条叫 GSM8K 子集。

## 逐步讲解与 CUDA 对照

打开 [local_probe.py](../示例工程/local_probe.py)。`torch.load(...,weights_only=True)` 读取本工程生成的推理状态；核对 TOKENS 后创建 TinyToolModel、加载 state_dict、移到设备。每次 evaluate_model 实际执行上一单元评估流程；没有给模型待评正确答案，也没有规则填动作。

三轮 seed 为 11、29、47。本模型无 dropout、解码贪心，所以改变这些推理 seed 通常不影响结果；实际 spread=0。没有重新初始化并训练三次，因此不能叫“三个训练种子的微调收益统计”。设备的不同内核仍可能有数值差异，种子也不是跨平台逐位一致承诺。

当共享环境探测 `torch.cuda.is_available()` 为 True 时运行：

```powershell
..\..\..\.venv\Scripts\python.exe local_probe.py --weights-dir '../../34_规划与工具使用微调/示例工程/report-my-cpu-01' --device cuda --output-dir report-my-local-cuda-01
```

两边读取同一份 CPU 保存的权重，避免同时换模型和设备。作者 CPU/CUDA 计数一致，不据此推广所有模型等价。公开归档评分本身只是文本操作，不需要 GPU；GPU 路径用于实际模型前向。

## 固定配置与公开归档的未知项

重放 report.json 中 `archive_generation_config` 的 shots、temperature、top_p、precision、weights_hash 均为 null，表示这份归档不足以恢复完整配置。你新写的 2-shot 提示不能填进这些未知项。公开框架正式评测时应固定框架提交、任务名、数据版本、模型／tokenizer 修订、Prompt／chat template、few-shot 选择、解码、精度、设备、批次与停止条件。

chat template 是把系统／用户／助手消息转换成模型输入的格式；同一段可见文字若角色边界不同，模型收到的 token 也不同。当前固定词表小模型不使用真实 chat template，不能用它验证自然语言模板兼容性。正式引入评测框架或真实模型要先确定依赖、权重、硬件与费用，再按工作区规则获准安装；本次没有安装它们。

## 常见错误与分级练习

权重路径不存在：核对 Get-Location、上一单元结果目录和文件名。词表不符：可能误用了单元 33 的权重，不能强行忽略检查。输出目录已存在：换新名。只读旧 report.json 没有执行 local_probe：那是结果查阅，不能记成本次生成验证。

### 跟做练习：配置卡

从自己的报告抄设备、精度、解码、上限和两份权重摘要前八位。提示：不要把显示前八位当完整存档。

> [!example]- 参考答案
> 作者为 cpu/fp32/greedy/8，quantization=none；完整摘要在 weights_sha256 字段。完成标准：能找到字段并保留完整 report.json，名字不是版本证据。

### 独立练习：三次一样

三次贪心分数都 12/12，可否说训练随机性误差为零？

> [!example]- 参考答案
> 不可。这是相同权重的重复推理，没有三次独立训练，且贪心没有采样随机性。完成标准：区分数据抽样、生成采样、训练 seed 与设备差异。

### 迁移练习：量化对照

准备将权重量化到 INT4，应怎样验证质量变化？提示：先固定其他因素。

> [!example]- 参考答案
> 记录具体量化方案与实现版本，固定任务、Prompt、评分和生成预算，分别实际生成并保存逐题前后结果，再看质量、速度和内存。本次只记录 none，没有运行真实 INT4 对照，不能推断分数必然不变。完成标准：提出可执行比较条件，不把设备变化当量化实验。
