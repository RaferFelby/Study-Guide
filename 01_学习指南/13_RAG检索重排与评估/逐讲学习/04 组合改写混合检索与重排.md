## 要解决什么问题

用户说“保留记录多久”，资料写 retention；关键词法漏掉词，LSA 又可能把相近政策混在一起。可以先改写问题、并用两路检索，再对少量候选仔细排序。本讲先区分每一步的职责，避免把所有改进都归功于一个“更强模型”。

**召回**负责把可能相关的片段找进候选集；**重排**负责对已有候选重新排序。若 gold 从未被召回，重排通常无法创造它。**混合检索**指组合不同召回信号，而不是把任意两种分数直接相加。

前置：前两讲 BM25/LSA、列表和排序。`sorted(..., key=...)` 的 key 是排序依据；负分数使高分排前；第二项 ID 在同分时提供稳定顺序。

## 查询改写保留什么

**Query Rewrite** 是把用户问题转换成更容易检索的表达，通常补术语、消除歧义或结合上下文。本工程识别 `cancel → cancellation`、`keep/records → retention`、`quota → capacity`，再把规范字段附在原 query 后面。

```python
from retrieval import rewrite_query

query = "How early must I cancel compute?"
print(rewrite_query(query))
```

保存为 `inspect_rewrite.py` 并运行，预期输出原问题后加 `cancellation`。代码保留原服务和限定词。若改写删去 premium、日期或否定，就可能搜到语义相反的政策。

这套规则没有生成模型：`identify_query` 用词集找到唯一服务和唯一字段。找到多个或没有找到时返回 `None`，不猜。真实 LLM 改写要检查是否保留主体、日期、否定、权限上下文，并记录原 query 与改写用于诊断；敏感文字不能无授权发送外部模型。

**多查询**指把原问法和另一种问法分别检索，再合并。工程用 `dict.fromkeys([query, rewrite_query(query)])` 保留顺序并去重；若两者一样只检索一次。这个写法只是在同一段中去重复，不是全局缓存。

## 为什么采用排名融合 RRF

BM25 分数可能 5.0，余弦可能 0.8；量纲和分布不同。把它们相加会使一种信号支配结果。**RRF（倒数排名融合）**按名次贡献：

```text
每路贡献 = 1 / (c + rank)
融合分数 = 各路贡献相加
```

`rank` 从 1 开始，`c=60` 是本工程常数，用来减弱第一名与后几名的差距。同一证据在多个列表靠前，会积累更多贡献。原始方法见 [RRF 论文](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)。

手算：A 在第一路第 1、第二路缺席，得 `1/61≈0.01639`；B 在两路均第 2，得 `2/62≈0.03226`，所以 B 排在 A 前。RRF 的优势是避免原始分数尺度；局限是忽略分数差距，低质量或重复的查询通道会改变权重。增加通道不是免费提升。

打开 `reciprocal_rank_fusion`：每路单独用 seen 防止同证据重复贡献；scores 按 ID 累加；documents 保存真正候选对象；最后构造 Hit 并排序。没有出现过的 ID 无法进入结果。融合代码只看候选，不看评估集的答案或 gold ID。

## 权限过滤在候选之前

`Retriever.search` 先根据 audience 选 allowed，再每路检索取前 8，最后融合。若先取全库 top8 再删除隐藏项，可能既泄露候选又挤掉本来可见的相关段。生产服务应由可信身份推导权限，查询改写和缓存键也不能跨权限复用。

本工程的共享词表和 SVD 仍在全语料拟合，仅结果范围过滤；这是教学索引，不等同于租户完全隔离。日志、计时、统计和训练语料也可能有隔离要求，部署前需另外设计。

## 重排比融合多看了什么

工程的规则重排对前 8 个融合候选计算：服务匹配得 1，字段匹配得 1，再加较小的 RRF 分数。同服务同字段会靠前。它是透明元数据基线，不能理解复杂上下文，不是神经 Reranker。

真正的 **CrossEncoder** 将 query 和文档一起输入模型，输出配对分数；它通常比预计算单独文档向量更耗算力，因此只用于召回后的小候选集。可参考 [Sentence Transformers 召回与重排说明](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。分数也需要校准，不能直接叫正确概率。

```text
原 query + 改写 query
    → 各自 BM25 top8、LSA top8
    → RRF 合并
    → 规则重排融合前8
    → 返回 top_k
```

当 top_k 大于 8 时，rerank 最多返回 8，这是候选预算限制。增大最终 K 不能弥补前级候选数太小。真实系统应分别配置 recall_k、rerank_k、context_k，并测延迟/成本。

## 动手对照

在示例工程新建 `inspect_hybrid.py`：

```python
from pathlib import Path
from data import load_dataset
from retrieval import Retriever

documents, _ = load_dataset(Path(__file__).parent / "fixtures")
retriever = Retriever(documents)
query = "How early must I cancel storage?"
for strategy in ["bm25", "dense", "hybrid", "rerank"]:
    hits = retriever.search(query, strategy, top_k=3)
    print(strategy, [hit.document.document_id for hit in hits])
```

运行后检查 `storage-cancellation` 在不在前三、位置是否改变。列表推导式这里只做一件事：从每个 hit 取 ID。你也可以先用普通 for 循环逐个 print。

不要直接对四种方案说“重排提高了召回”。当前 hybrid 同时包含改写、多查询、两路融合；rerank 又增加元数据排序。要定位贡献，迁移实验应逐步关闭其中一个功能，其他配置固定。这个叫**消融实验**：移除一个组件，观察差别。

## 常见错误与练习

融合后重复结果：检查各路 ID 是否稳定、融合是否按 ID 去重。权限题有引用：先追 allowed，再看缓存/后处理是否跨身份。重排不改善：看 gold 是否进入候选；没进入先修召回，已进入才调排序。

**跟做：** 手算 A 两路排名 1/3、B 两路 2/2 的 RRF。完成标准：没有使用 BM25 原分数。

**独立：** 写出“query 有 gold、候选没有 gold、重排后仍没有 gold”的失败流程，指出应修改的阶段。

**迁移：** 用 10 条同义题做四步消融：BM25；BM25+改写；BM25+LSA 融合；融合+重排。完成标准：同一数据和权限、相同 K、记录延迟、逐题结果和改变的组件。

> [!example]- 参考答案与解析
> A=`1/61+1/63≈0.03227`，B=`2/62≈0.03226`，A 略高，不能只看四舍五入后的 0.032。gold 不在候选应检查解析/切块、词表或 Embedding、改写和过滤；重排只能调整已有候选。若使用多个几乎相同 query，RRF 会让对应信号重复加权，需明确通道配置。
