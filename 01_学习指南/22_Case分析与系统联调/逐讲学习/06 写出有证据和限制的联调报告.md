## 本讲任务与前置

修复后需要一份别人看得懂、能复查的报告。不能只说“全部通过”。本讲把五Case、单变量、组合和未测范围写成结论，复习单元19评估报告与单元20观测证据。

## 报告先回答什么

目的：让限定的合成账户退款任务符合契约。范围：八条、五故障、三正常，mock模型与本机工具。基线：3/8。主要发现：同义检索、参数命名、围栏解析、owner授权、暂时上游重试；严重度最高为跨用户读取。

结论要连接证据，不用“明显有效”。每项单变量4/8且改善对应一ID，无退步；合用8/8，工具尝试6→8；权限读取前拒，持续故障最多2次。代价和限制与收益同时报告。

## 最小示例：从报告取关键结果

新建`lesson_report_summary.py`：

```python
from experiments import run_experiments

report = run_experiments()
for name in ["baseline", "combined"]:
    data = report["reports"][name]
    print(name, data["successes"], data["n"], data["attempts"])
print("数据摘要", report["case_sha256"])
print("限制", report["limitations"])
```

预期baseline3 8 6、combined8 8 8，完整数据摘要与四限制。摘要不需要背；放在报告用于确认数据没换。实际duration_ms_measured是本机函数耗时，每次略变，不作为真实模型延迟证据。

## 动手：按模板写一页

在Obsidian自己的学习笔记写以下顺序：

1. 任务目标、适用用户/权限、数据来源与版本。
2. 五失败表：Case/症状/根因证据/严重度/责任组件。
3. 实验：唯一变量、固定输入、前后ID、正常回归、反证/失败路径。
4. 组合：成功分母、调用变化、权限实际读取、持续故障上限。
5. 实际命令/环境/报告文件、未运行项目。
6. 结论、残余风险、按优先级下一步。

你的报告使用亲自运行输出，不复制作者验证为已完成。若只阅读尚未操作，标“阅读记录/待运行”。

## 根因证据怎样足够

根因不是因为annotation写了retrieval就成立：要有检索missing、同题单开aliases改善、其他Case不变的链。工具参数要有planning参数key、tool拒、改名后恢复。解析要有格式条件、严格解析失败、仅约定包装适配后恢复。权限要有跨owner读取和读取前拒。上游要有暂时失败、有限重试与持续失败耗尽。

真实事故通常不能构造完全可控上游，证据可分确认/较强推断/待证，写置信程度。不要为了漂亮报告把所有推断写成事实；下一步实验应补最关键的不确定项。

## 后续行动按风险排序

先阻止跨用户/无批准副作用，再修高影响可用性；检索/解析质量同时入回归集。真实业务加入脱敏的多样问法、模型版本、真实上游超时/限流、并发/取消/缓存与持久化测试。样本不够时报告实际n而非补复制题。

根因类别里模型/上下文/基础设施广泛，这八条只展示五机制；下一轮应从真实或压力证据补缺口，不凭课程列表声称已经全类别实测。50Case深化目标要来源与审查，不能为了数量稀释质量。

## 联调与需求的连接

修复优先级来自业务目标：例如退款期限查询错误影响客服答复，跨用户泄漏影响数据边界，重试提升可用性但增加调用。如果需求没有明确用户、允许动作和成功标准，联调分数再高也可能验错任务。下一单元从需求开始定义技术方案。

## 常见错误

- 只报8/8，不说八条合成：结论超范围。
- 只报工具次数减少/增加：需结合失败被修与权限，不单一追省调用。
- 每个问题都建议换更强模型：先按已定位组件最小改动。
- 没有后续行动：报告还要让协作者知道接着验证什么、为什么。

## 单元验收练习与答案

跟做：一页报告列3/8→8/8、5单变量、6→8尝试、安全边界及限制。完成判断：读者可复查命令与数据身份。

独立：写一句不会夸大当前结果的结论。

迁移：整理自己的五条失败台账，至少标来源、根因假设、严重度、复现、唯一变量实验计划；尚无五条时写实际数量，不虚构真实事故。

> [!example]- 参考答案与解析
> “在固定八条作者合成退款任务上，五项机制修复单独改善对应ID，组合8/8且三正常回归未退步；真实模型、网络并发和生产数据尚未验证。”
>
> 真实Case不确定时保留假设和证据缺口，行动优先补高风险边界；作者夹具可练写法，但来源必须注明模拟。
