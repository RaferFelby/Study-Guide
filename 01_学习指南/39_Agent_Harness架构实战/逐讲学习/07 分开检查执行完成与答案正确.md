## 今天先完成什么

先预测：“查询成功、笔记已保存，但回答写成 300 天”，算不算成功？随后在 VS Code 打开本单元 `示例工程`，运行 `quality_examples.py`，核对执行、答案、笔记三列。能分别解释三列，再检查自己的数据库，才完成本讲。

## 旧规则为什么会误判

早期检查包含这样的条件：

```python
"30" in text and "policy-v1" in text
```

`in` 检查一个字符串是否出现在另一个字符串里。数字字符 `30` 出现在 `300` 里；“不是 30 天”也包含它。因此它可以检查关键词，却无法判断期限是否正确、句子有没有否定。

本任务的政策是“教学商店允许购买后 30 天内申请退款”。成功还要求保存带来源的笔记。于是有三个分别需要回答的问题：

| 问题 | 证据 | 不能替代它的东西 |
| --- | --- | --- |
| 工具执行完成了吗 | 实际查询观察、保存回执、SQLite 笔记行 | 模型说“我已经保存” |
| 答案符合任务约定吗 | 期限和来源与可信政策一致 | 出现两个关键词 |
| 保存的笔记也正确吗 | 从数据库读出的实际正文 | 最终答案正确 |

例如笔记写成 300 天，最终答案写对了 30 天，第三项仍不通过。最终评估不会撤销已经批准并提交的笔记，也不会悄悄修改它；失败轨迹需要保留供排查。

## 先限定可判断的表达，再提取字段

这个教学任务采用固定句式：

```text
30 天内申请退款 [policy-v1]
```

`30` 是天数，`policy-v1` 是来源标识。申请的起点“购买后”由当前固定任务与可信政策给出；本格式不能描述其他业务条件。方括号不是引用真实性的证明，程序还要核对实际查询结果。

程序将这句话拆成结构化数据，即每个值都有明确名称的字典：

```python
{"days": 30, "source": "policy-v1"}
```

这里 `days` 是整数，不能与字符串 `"30"` 混用；`source` 是字符串。两个字典相等要求键和值对应相等，天数 300 不会等于 30，`policy-v2` 不会等于 `policy-v1`。

打开 [contracts.py](../示例工程/contracts.py) 的 `parse_refund_claim`，按顺序读：

1. `partition(" 天内申请退款 [")` 用固定分隔文字切成三段：前半段、分隔文字、后半段。没有找到时，中间一段为空，返回 `None`。
2. `endswith("]")` 要求最后一个字符为右方括号；`source_text[:-1]` 取掉它。切片 `[:-1]` 表示取末尾字符以前的内容。
3. `isascii()` 与 `isdecimal()` 要求天数由 ASCII 数字组成；长度限制为 1～3 位。`int` 再把数字字符转为整数。
4. 用拆出的字段重新拼出句子，要求与原文完全相同，避免把 `030` 等未约定格式悄悄接受。
5. 成功返回字典，无法按此格式解析则返回 `None`。这表示“不能按本契约提取事实”。

> [!important] 固定句式的限制
> “购买后30天内可申请退款，来源policy-v1”可以是正确的同义表达，但不符合本课格式，因此不能自动通过。`answer_correct=False` 在本工程表示“未通过当前任务契约的核验”，不证明所有被拒绝的自然语言都事实错误。不要用增加关键词的方式伪装成通用语义理解。

若以后接自由文本，应保留原文、建立独立评估题集，并设计人工复核或有证据约束的评估流程。模型评委同样会出错，不能靠换一个模型就省掉验证。

## 检查保存事实，需要读实际数据库

`evaluate_final(state, text, notes)` 的三个输入分别是可信的本地会话状态、最终回答、数据库中的笔记。`notes` 的结构为“动作摘要 → 保存正文”，由程序查询 SQLite 得到，不能让模型填写。

按 [runtime.py](../示例工程/runtime.py) 的最终回答分支顺序阅读：

1. 获取 `SELECT action_key, body FROM notes` 的记录，用 `dict(...)` 将每行两个值转换为键值对。
2. 核对查询结果与当前固定政策一致。仅存在名为 `lookup_policy` 的记录不够。
3. 核对恰好有一条成功保存回执，以及与摘要对应的一条实际笔记。这个任务只要求一条；多条记录不会挑一条好的充数。
4. 根据数据库正文重新构造 `save_note` 动作，计算摘要，与回执中的摘要对照。正文变化后就不能继续称它是原批准内容。这里检查的是内容一致性，不是用户身份认证。
5. 分别解析答案和笔记，与可信的 `days/source` 比较。
6. 记录各项结果，并且只有全部通过才写入 `status=completed`。

`checks` 保存五项检查结果；`failed_checks` 保存未通过项的名字，方便定位。`all(checks.values())` 在五个布尔值都为真时才返回 `True`。

| 输出字段 | 本例中的含义 |
| --- | --- |
| `execution_completed` | 查询证据有效，笔记落库且正文与动作摘要一致 |
| `answer_correct` | 回答按固定格式核验通过 |
| `note_correct` | 实际笔记按固定格式核验通过 |
| `accepted` | 所有要求都通过 |

本地数据库必须可信，一个数据库仍只允许一个操作者。这些检查不提供防篡改签名、身份认证或通用数据库损坏修复。

## 动手一：预测七个案例

在 VS Code 的 PowerShell 终端确认当前目录是 `01_学习指南/39_Agent_Harness架构实战/示例工程`，运行：

```powershell
..\..\..\.venv\Scripts\python.exe quality_examples.py
```

路径中的三个 `..` 逐层回到工作区根目录，然后使用共享环境的 Python。脚本只创建内存中的教学数据，不写数据库，也不连接模型。

“夹具”是为了隔离某个机制而准备的固定输入。脚本的 `make_fixture` 模拟已经完成查询和保存的会话，不能把它当作真实执行证据。真正落库链仍需下面的动手二。

先遮住结果列预测，再对照输出：

| 案例 | 执行 | 答案 | 笔记 | 接受 |
| --- | --- | --- | --- | --- |
| 正确 | True | True | True | True |
| 天数 300 | True | False | True | False |
| 否定回答 | True | False | True | False |
| 来源 policy-v2 | True | False | True | False |
| 笔记 300、回答 30 | True | True | False | False |
| 同义改写待人工复核 | True | False | True | False |

最后一行“只有回执没有笔记”应为 `False`，失败项包含 `note_committed`、`note_matches_approval`、`note_supported`。这是向评估函数传空字典模拟缺少数据库行，没有删除任何真实笔记。

## 动手二：复核自己的会话

先按第 1～3 讲完成 `results/first.db` 的正常查询、确认、保存与回答。仍在示例工程目录运行：

```powershell
..\..\..\.venv\Scripts\python.exe evaluate.py --db results/first.db
```

`--db` 指定要读取的数据库，相对路径以当前终端目录为准。正常新会话应显示四个汇总值均为 `true`，`failed_checks` 为 `[]`。JSON 中的 `true` 与 Python 打印的 `True` 表示同一个布尔含义。

`evaluate.py` 只读取、打印，不重新调用模型、不重新执行保存、不改写历史终态。提前复核时若还没有最终回答，答案检查不通过是预期结果，先看自己停在哪一步。

新会话最终回答后，`demo.py show` 的 `state.evaluation` 与 `final_checked` 事件会保存当时报告。旧数据库没有这个新增字段仍可读取；原来已经结束的会话不会自动重跑。旧报告只反映旧规则，使用 `evaluate.py` 得到当前复核结果。若旧答案是自由表达，可能被当前格式拒绝，需人工复核；不要覆盖旧数据库来改写历史。

## 常见错误与定位

| 现象 | 先检查 | 处理方式 |
| --- | --- | --- |
| `session does not exist` | 终端目录、`--db` 路径 | 回到工程目录，确认已创建会话 |
| `evidence_valid` 失败 | 查询结果是否来自本任务政策 | 查看观察，不把来源标签本身当证据 |
| `note_committed` 失败 | 是否仍在等待确认、实际行是否存在 | 用 `show` 查状态；不要仅凭模型自报 |
| `note_matches_approval` 失败 | 实际正文与批准动作是否一致 | 保留记录排查，不用新摘要掩盖修改 |
| `answer_supported` 失败 | 句式、数字、来源 | 格式外同义句人工复核，错误事实保留为失败 |
| 答案对、`note_supported` 失败 | 数据库内正文 | 区分已写入和写对了，不能只改最终回答 |

评估是最后一道质量检查，不会替代保存前的人类确认。发现坏笔记时，不要以为 `failed` 已自动回滚之前提交的事务。

## 跟做、独立与迁移练习

### 跟做：拆出字段

在 VS Code 新建 `lesson_quality.py`，保存下面完整脚本，运行 `..\..\..\.venv\Scripts\python.exe lesson_quality.py`。

```python
from contracts import parse_refund_claim


def main():
    answer = "300 天内申请退款 [policy-v1]"
    claim = parse_refund_claim(answer)
    print(claim)
    print(claim == {"days": 30, "source": "policy-v1"})


if __name__ == "__main__":
    main()
```

> [!example]- 参考答案
> 第一行是 `{'days': 300, 'source': 'policy-v1'}`，第二行是 `False`。句式解析成功不代表事实正确。将 300 改为 30，第二行才变为 `True`。完成标准：能解释为什么“可以解析”和“通过事实检查”是两个步骤。

### 独立：补一个错误来源案例

在自己的练习脚本中，使用 `quality_examples.make_fixture` 创建正确笔记，然后将回答设为 `30 天内申请退款 [policy-v2]`。调用 `evaluate_final`，打印 `failed_checks`。提示：夹具函数返回两个值，用 `state, notes = ...` 分别接收。

> [!example]- 参考答案与过程
> ```python
> from contracts import evaluate_final
> from quality_examples import make_fixture
>
>
> def main():
>     state, notes = make_fixture("30 天内申请退款 [policy-v1]")
>     report = evaluate_final(state, "30 天内申请退款 [policy-v2]", notes)
>     print(report["failed_checks"])
>
>
> if __name__ == "__main__":
>     main()
> ```
> 输出 `['answer_supported']`。查询和保存都正确，只有回答来源不一致；不能把它记录为工具执行失败。完成标准：不改检查器就能构造此反例，并说明哪一项失败。

### 迁移：政策换成 14 天以后怎么办

假设业务确实推出 `policy-v2`，期限改为 14 天，旧会话仍有 v1。应直接修改一个常量，然后把所有旧会话重新标成失败吗？先写出你需要保存的版本信息，再看答案。

> [!example]- 参考答案与过程
> 不应改写旧执行历史。应明确任务按哪个时间点、哪一版政策判断，保存对应来源版本和可信内容；评估器据该版本核验。新任务可用 v2，旧任务可按当时 v1 复核。仅把字符串 v1 换成 v2 不能建立政策可信性。本课固定政策不实现多版本业务，这是迁移设计练习。完成标准：能区分“当时任务是否正确”和“按今天政策是否仍适用”。
