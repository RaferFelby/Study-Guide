## 先明确本篇要完成什么

给定一次失败轨迹，你要能写出“改哪里、预期哪个行为改变、怎样对照、何时保留旧配置”。本篇逐步讲解 Harness² 的 Propose–Probe–Compose：**提出修改 → 对照试跑 → 组合配置**。使用 v1，出处与授权说明见上一篇；主要定位为 [§2.2～2.3](https://arxiv.org/html/2610.14224v1#S2.SS2) 与 [附录 H](https://arxiv.org/html/2610.14224v1#A8)。

前置是两层改进、工具轨迹和产物核验。trajectory（轨迹）记录调用、观察等执行过程；deliverable（产物）是任务要求交出的文件或答案。只看到最终答案，通常无法判断失败发生在哪一步。

## 第一步：取得基准执行

先让当前配置运行当前任务，得到参考轨迹和产物。reference 是供比较的参考，不是正确答案。这里的“基准执行”也不同于第三篇用于研究评分的 benchmark 数据集。

**教学情景：** 任务要求从三份虚构活动资料整理预算说明。参考轨迹只读取了两份文件，写出说明后没有重开；产物看起来完整，但某个费用口径没有核对。此例借鉴论文讨论的问题类型，下面的记录都是为讲机制构造的，不是论文测量数据。

先写“未读取第三份文件”和“没有重开产物”这两条可观察事实。不要直接写“模型知识不足”或“答案一定错了”，因为轨迹目前还不足以支持这些判断。

## 第二步：Propose，提出两种范围的候选

论文从当前配置产生两类可执行候选：

| 候选范围 | 关注的问题 | 对教学情景的修改假设 |
| --- | --- | --- |
| invariant，跨领域过程问题 | 计划、工具使用、上下文、委派与完成过程 | 先列输入清单，交付前重开文件检查 |
| domain-specific，领域特定问题 | 当前业务的知识、操作步骤、约束 | 加入活动预算跨文件核对技能 |

这里的 invariant 表示关注常见过程问题，不是已经数学证明跨领域都有效。两类候选都可以读取已有经验库，但旧任务事实要在当前资料中重新核实。

候选是实际配置文件的修改，不只是“建议更认真一点”。diff 表示修改前后具体哪些行或组件改变了；后续组合器需要把行为变化与这些修改对应起来。

论文附录 D.2 还说明了执行前的结构检查：例如技能缺少触发说明、脚本不能编译、技能依赖的辅助文件未携带。失败时按验证信息重试一次，再失败则回退到该阶段起始配置，并记录回退。[定位：D.2](https://arxiv.org/html/2610.14224v1#A4.SS2)

这是结构验证，不是任务质量验证：脚本能够编译仍可能计算错，技能能被发现也不证明步骤适用。

## 第三步：Probe，在匹配条件下试跑

让两个候选分别执行**同一个任务**，保持模型和环境配置匹配，并把轨迹、产物与参考比较。可检查：以前漏读的资料现在是否读取；错误是否仍然出现；是否增加了无关调用；产物是否可打开。

| 教学记录 | 观察到的变化 | 目前可以说什么 |
| --- | --- | --- |
| 过程候选 | 三份文件均被列出，产物被重新打开 | 目标检查行为出现 |
| 领域候选 | 核对了费用口径，但新增一项无来源假设 | 有局部改善，也有新问题 |
| 基准 | 只读取两份资料，没有产物回读 | 用作对照，不视为正确标准 |

这些差异是行为证据。随机性、模型共同偏见和一次修改多个组件都会影响解释。一次试跑更好，不足以证明“就是某一行提示导致改善”。

在本地设计对照时，还应记录输入快照、配置版本、预算、运行目录与日志。对会写入的任务，每个候选用独立临时副本；避免前一个候选的输出污染后一个。这里是本指南的实验设计建议，不是宣布已有本地工程实现了论文的隔离运行器。

## 第四步：Compose，按证据形成后继配置

组合器读取基准、候选配置、diff 和可用执行记录，决定：保留某项、修改某项、舍弃某项、采用一个候选，或保持当前配置。**合并并不是把所有修改连接起来。**

对上例可以保留输入盘点和产物回读；修订领域核对步骤；去掉无来源假设。但这是一次待验证的组合决策，组合后的配置还要执行一次，获得新的轨迹与产物。两个候选分别有效，也不能保证合并后没有冲突。

用下面的格式记录理由，中文字段是本指南的阅读练习格式：

```text
决定：保留／修订／舍弃／保持当前配置
涉及组件：具体文件与修改内容
证据：哪次执行、哪一步观察到了什么
不确定性：是否多项同时变化，是否只有一次试跑
后续检查：组合后的哪种行为应发生
```

论文把一步操作记为 `Φ(q,H,E;R) → (H′,e′,ξ)`：q 是任务，H 是当前配置，E 是已有执行历史，R 是本任务固定的改进配置；输出 H′ 是后继配置，e′ 是它的执行记录，ξ 保存候选、试跑和决策过程。分号只是帮助区分这里保持固定的 R，不是要写成某种 Python 语法。

## 加大预算：并行探索与顺序改进

`k` 是正整数探索预算。两种方式使用相同的“提出—试跑—组合”思想，但信息如何流动不同。

| 方式 | k 控制什么 | 后续修改可以看到什么 |
| --- | --- | --- |
| 并行 | 每个范围的候选数及独立组合次数 | 各组合器看到完整参考与候选池 |
| 顺序 | 连续改进轮数 | 当前配置、当前候选以及之前的执行与修改历史 |

并行方式收集 k 次参考执行、k 个过程候选和 k 个领域候选的试跑，再由 k 个独立组合器形成并执行各自的后继配置。论文这一实现做一次候选群体更新，k 增大的是探索宽度，不能描述成 k 层串行优化。

顺序方式初始化 k 次基准执行作为共享历史，然后连续进行 k 步改进；前一个配置和其执行结果进入后一轮。可以保留、修订乃至恢复更早的配置，不必相信最后一轮总是最好。

当 `k>1` 时，选择器根据任务与来源材料比较匿名产物，选一个现有输出交付；它看不到产物来自哪套配置，也不会把几个产物再生成一个新答案。`k=1` 跳过此选择。记号 H★ 中的星号只代表采用，不代表已经验证为最优。[定位：§2.2.2](https://arxiv.org/html/2610.14224v1#S2.SS2.SSS2)

## 动手：先数清执行次数

按上面的并行流程推导，正常路径的执行器运行次数为 `k + 2k + k = 4k`。这是**本指南对论文流程的计数推导**，不包含提出修改、组合推理、最终选择、任务后反思或重试所消耗的模型调用。

在 VS Code 打开本单元 `示例工程`，与 `demo.py` 平级新建 `lesson_harness2_budget.py`：

```python
def parallel_execution_counts(k: int) -> dict[str, int]:
    if type(k) is not int or k < 1:
        raise ValueError("k must be a positive integer")
    reference_runs = k
    candidate_runs = 2 * k
    composed_runs = k
    return {
        "reference": reference_runs,
        "candidate": candidate_runs,
        "composed": composed_runs,
        "total": reference_runs + candidate_runs + composed_runs,
    }


def main():
    for k in [1, 2, 5]:
        counts = parallel_execution_counts(k)
        print(k, counts)


if __name__ == "__main__":
    main()
```

按执行顺序读代码：`k: int` 标注预算应为整数，`-> dict[str, int]` 标注返回字典的键为文字、值为整数；标注本身不会拒绝非法输入，因此第一条判断主动检查。`type(k) is not int` 连布尔值也拒绝，避免 Python 中 `True` 可作为整数 1 参与计算的行为混淆预算。`or` 表示任一条件成立就抛出 `ValueError`。

接着分别计算参考、两类候选、组合后执行次数，再放进字典返回。`main()` 依次用 1、2、5 调用函数并打印；入口判断让导入这个文件时只定义函数，不自动开始打印。不熟悉函数、类型标注或字典时，先回看 [[01_学习指南/01_Python工程化/逐讲学习/01 运行Python并统计工单|Python 第 1 讲]]与该单元后续基础讲解。

在该目录 PowerShell 运行：

```powershell
..\..\..\.venv\Scripts\python.exe lesson_harness2_budget.py
```

共享解释器运行标准库脚本，不调用真实 Agent。预期 total 依次为 **4、8、20**；k=5 时 reference=5、candidate=10、composed=5。返回的字典把不同阶段分开，避免把“20 次完整执行”误说成“20 个 token”或“20 次模型请求”。一次执行本身可包含许多模型回合和工具调用。

命令中的三个 `..` 返回工作区根目录。若提示找不到解释器或脚本，先检查终端位置和文件扩展名；若输入 0 出现 `ValueError`，这是主动拒绝非法预算，不需要安装依赖。不要为了让非法输入继续运行而删掉检查。

## 任务后反思：只积累有条件的经验

完成当前交付后，反思器查看整个改进记录，保存采用的可执行配置，以及说明适用条件、经验和证据的 `EXPERIENCE.md`。附录 H 将修改效果分成有帮助、有害、没有观察到影响和因素混杂；多项一起修改或证据不足时，不能编造精确归因。

论文允许证据不足时不新增可迁移经验；不是每次都必须写一条“成功经验”。附录 D.2 按 benchmark domain 隔离经验库，域内任务按顺序读取先前条目。后续任务应从共同 H₀ 开始，经提出修改阶段选择复用内容。[定位：§2.3、D.2 与 H](https://arxiv.org/html/2610.14224v1#S2.SS3)

## 分层练习

### 跟做：写一次组合理由

用上面的活动资料教学记录，为“保留文件回读、舍弃无来源假设”各写一条决定，包含组件、证据与限制。

> [!example]- 参考答案
> 保留回读步骤：过程候选轨迹显示写入后重新打开了产物，基准没有这一步；这支持行为已改变，仍需检查回读是否覆盖所需内容。舍弃无来源假设：领域候选新增的判断没有资料支持；删去该假设后重新试跑，不能直接宣称组合后的总质量一定提高。

### 独立：把 k 改为 3

先手算并行流程各类执行次数，再修改脚本。补上非法输入 0 的处理，解释为何不能把总数当完整推理成本。

> [!example]- 参考答案
> 参考 3、候选 6、组合后执行 3，共 12。调用 `parallel_execution_counts(0)` 会抛出 ValueError；用第 2 讲讲过的 `try/except ValueError` 展示预期拒绝即可。12 只统计执行器完整运行，编辑器与其他阶段也耗费计算，每次执行长度也不相同。

### 迁移：两个候选都相信错误前提

两个候选都认为一份缓存是最新的，并据此产生一致答案。能否把一致性当正确证据？如何改下一次试跑？

> [!example]- 参考答案
> 不能，共同前提会产生相关错误。应核查缓存来源和版本，设计直接读取当前资料的对照，把“是否使用旧缓存”与其他改动分开。把共享前提写进不确定性记录；没有足够支持时保留未决状态，不把一致答案写成已证实的经验。

## 常见误读与完成标准

没有标准答案反馈不等于没有输入校验、任务要求和来源材料；更大 k 不保证每个任务都更好；选择输出不同于再次编辑配置；反思不是把最终答案复制进长期库。能走完四阶段并数清预算后，再看 [[01_学习指南/39_Agent_Harness架构实战/选修专题/03 核对Harness平方的实验与应用边界|实验与应用边界]]。
