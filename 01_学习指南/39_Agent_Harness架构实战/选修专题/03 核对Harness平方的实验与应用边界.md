## 本篇先做什么

先手算 `75.7 - 64.2`，再回答：“这个差值描述哪种模型、哪个环境、什么任务和什么指标？”如果只有一个提高了的数字，却说不出条件，就还不能据此选型。

本篇沿用前两篇的 Harness² v1，读论文报告的结果，再用本地算术核对读表方法。**所有任务分数来自论文，教材没有独立复现其模型实验。** 前置是上一讲的 k、参考执行和选择器；不熟悉对照与消融时先看 [[01_学习指南/37_论文精读与技术趋势判断/逐讲学习/03 检查实验对照消融与复现条件|论文实验阅读]]。阅读顺序：实验条件 → 分数 → 成本与失败 → 动手核算 → 迁移判断。

本篇是对 Ruiyao Xu 等作者 [Harness² 原文 v1](https://arxiv.org/html/2610.14224v1) 的中文教学整理与改编，新增解释、练习和计算代码；原文标注 CC BY 4.0。它是预印本，版本提交日期为 2026-10-09，不把发布等同于同行评议完成。

## 实验究竟在比较什么

benchmark（基准任务集）是一组用于比较方法的任务和评分规则；baseline（基线方法）是作为参照的系统。前者提供测量场景，后者提供比较对象。

论文固定执行模型权重，在 Gemini 3.5 Flash／GLM-5 与 OpenCode／Codex 组成的四种配置上比较。默认编辑器、选择器使用 Claude Opus 4.8。这些名称是在转述论文的实验配置，不表示本机已安装，也不保证换成自己的小模型仍得到同样收益。[来源：§3.1、附录 D.1](https://arxiv.org/html/2610.14224v1#S3.SS1)

| 基准 | 本文实际评估范围 | 主要指标怎样理解 |
| --- | --- | --- |
| WorkBuddy-Bench | 测试划分：Code 40、Web 35、Office 25 个任务 | 综合检查得分；Avg 对三个领域等权平均，不按各领域任务数加权 |
| JobBench | 固定 31 个训练任务／34 个测试任务，报告测试结果 | 按任务评分细则加权的产物分数，裁判为 Claude Opus 4.8 |
| LAB，Legal Agent Benchmark | 从原基准中使用 100 个留出任务 | Partial 是细则层面的通过比例，不是整道法律任务全部正确的比例；裁判为 Claude Sonnet 4.6 |

“留出”指不拿这些任务作为对应的开发训练集。论文另为 Meta-Harness 提供开发任务：WorkBuddy 的训练划分、JobBench 的 31 个训练任务、LAB 的 24 个开发任务。不能误读为 LAB 的全部 1251 个原始任务都在本研究中跑过。[来源：附录 B、C](https://arxiv.org/html/2610.14224v1#A2)

论文比较的参照包括：保持配置不变、ReasoningBank 的经验检索、Meta-Harness 的离线配置搜索、Harness Scaling 的任务内适配。它们积累状态和使用开发数据的方式不同，读“超过某方法”时要连这些条件一起读。

### 没有标准答案反馈，为什么还能报告分数

需要分开两个阶段：

1. **运行中修改配置：** 编辑器依据任务、来源材料、执行轨迹与产物对照工作，不接收基准的隐藏答案、评分细则和评委分数。
2. **研究中评价结果：** 研究者用独立的基准检查和评委打分，比较最终产物。

因此，“不依赖标准答案指导修改”不等于“实验没有评价”，也不等于“用模型判断就能证明真实正确”。论文实现还检查改进工作区是否混入评分反馈；这说明评分泄漏是需要控制的实验问题。[来源：§3.1、附录 D.2](https://arxiv.org/html/2610.14224v1#A4.SS2)

## 读主表：先看条件，再计算差值

下面选择三行说明摘要中的最大单步增益，**每行的配置不同**。分数按论文表 1／表 2 的 0～100 尺度抄录；括号内是三个独立任务流的标准差，即重复运行结果的波动大小。

| 基准与执行配置 | 原始配置 | Harness²，k=1 | 平均分之差 |
| --- | --- | --- | --- |
| WorkBuddy，GLM-5／OpenCode | 64.2（1.4） | 75.7（2.2） | +11.5 分 |
| JobBench，Gemini 3.5 Flash／OpenCode | 31.5（1.1） | 36.0（2.3） | +4.5 分 |
| LAB Partial，GLM-5／OpenCode | 59.6（2.7） | 71.4（2.9） | +11.8 个百分点 |

三个任务流会改变任务顺序，并各自积累经验库。标准差不是每个任务的误差，也不是置信区间；只有三次重复，不宜把几分的差异直接叫作经过显著性检验证实。以上是论文报告的均值差，不是每个任务都提高同样多。[来源：§3.2 表 1、表 2](https://arxiv.org/html/2610.14224v1#S3.SS2)

百分比与百分点要分清：通过比例从 59.6% 到 71.4%，相减是 **11.8 个百分点**；相对于原值的增幅则约为 `11.8 / 59.6 × 100% = 19.8%`。如果不说明算法，把两者混写成“提高 11.8%”会误导读者。

表中 `+ Recursion` 是从 k=1 到并行 k=5 的**增量**。例如 Gemini／OpenCode 的 WorkBuddy Avg 为 77.5，后面的 +3.3 表示 k=5 为 80.8；原始配置为 72.4，所以从原始配置到 k=5 的总差是 8.4 分，不能把 +3.3 当最终得分。

还要寻找不支持过强结论的行：LAB 的 Gemini／Codex 配置下，Meta-Harness 的 Partial 为 76.5，Harness² k=1 为 75.6。因此“比原始配置有提升”不能改写成“每个设置都打败所有基线”。这两个均值本身也不足以断言差异显著。

## 消融：去掉一个环节以后发生什么

ablation（消融实验）是在其他设置尽量可比的条件下，去掉或替换一个组成部分，看结果如何变化。直觉是拆掉某个部件观察影响；局限是部件之间有相互作用，不能把每个差值当独立贡献再相加。

论文表 3 使用 Gemini／OpenCode、k=1：

| 方法 | WorkBuddy Avg | JobBench |
| --- | --- | --- |
| 完整方法 | 77.5 | 36.0 |
| 不用经验库 | 74.4 | 34.2 |
| 不区分两类修改范围 | 74.6 | 32.3 |
| 不做组合阶段 | 75.9 | 34.1 |

第二个删减实验仍有两个编辑器，只是都做通用修改，保持候选数量可比。第三个用选择候选替代组合，不能理解为“删掉所有后续决策”。结果支持这些部件在所测条件下有价值；不证明经验库对所有业务都有效，也不证明三个差值可以相加预测一个新系统。[来源：§4 表 3](https://arxiv.org/html/2610.14224v1#S4)

## 成本与经验复用：两个容易读错的地方

### 任务内的计算成本

主表中的 `#Steps` 是每任务的执行器模型回合数，不是编辑、试跑、组合、选择等整个流程的总调用成本。上一讲推导的 4k 也只是正常路径中的执行器运行次数。

论文图 6 比较交付前所有阶段的 token 使用，包含执行与改进。并行可能缩短等待时间，却仍会消耗更多总计算。部署时还应另记任务交付后的反思、经验存储和维护成本；这是本指南的成本核算建议，不能说论文图 6 已包含所有长期维护费用。实验只支持其所测预算范围，不能据此宣布 k 越大越好或 k=5 全局最优。[来源：§4、附录 F](https://arxiv.org/html/2610.14224v1#S4)

### 任务之间的经验复用

在线任务流中，当前任务只能读取此前积累的库。附录 E.2 另做了一项**回顾性复用分析**：任务流结束后，用完整经验库重跑任务，排除当前任务自己的条目。WorkBuddy 为 77.5→79.4，JobBench 为 36.0→37.7。

虽然排除了自己的条目，但库仍可能包含时间顺序上更晚任务的经验；这是离线复用证据，不是原在线流程立刻能取得的额外收益。重复运行本身也可能带来变化。读这种实验时，要画出“建库时间”和“使用时间”，不能只看排除了自身条目就认定等价在线评测。[来源：附录 E.2](https://arxiv.org/html/2610.14224v1#A5.SS2)

## 失败案例告诉我们哪些边界

论文附录 E.6 回顾了选择错误、覆盖范围收窄、共享错误前提等失败。例如，选择器可能偏爱看起来整齐却缺内容的产物；多个候选也可能都相信同一条错误缓存。对照能增加证据，但共同偏见仍可能让编辑器和选择器一起出错。附录中的失败分数是研究后的诊断，不是算法当时可用的评分反馈。[来源：附录 E.6](https://arxiv.org/html/2610.14224v1#A5.SS6)

经验库还会遇到过时、重复、互相冲突和检索不相关的问题。库治理、自适应预算和停止规则在论文未来方向中讨论；不能写成本地教材已经实现的能力，或把它们当成经过主表验证的完整产品功能。[来源：附录 F、G](https://arxiv.org/html/2610.14224v1#A6)

## 动手：用 Python 核对读表算术

在 VS Code 打开本单元 `示例工程`，与 `demo.py` 平级新建 `lesson_harness2_scores.py`，输入完整代码：

```python
def main():
    results = [
        ("WorkBuddy", 64.2, 75.7),
        ("JobBench", 31.5, 36.0),
        ("LAB Partial", 59.6, 71.4),
    ]
    for name, base_score, improved_score in results:
        gain = improved_score - base_score
        print(f"{name}: {gain:.1f}")

    one_step_score = 77.5
    recursion_gain = 3.3
    parallel_score = one_step_score + recursion_gain
    print(f"WorkBuddy k=5: {parallel_score:.1f}")


if __name__ == "__main__":
    main()
```

`results` 是列表，每项是依次存放名称、原始分数、改进后分数的元组。`for` 每次取出一项，并把三个值分配给三个名字；`gain` 保存相减结果。格式中的 `.1f` 表示显示一位小数，避免把浮点表示误差误读成论文数字不一致。最后一个加法把“单步分数”和“额外增量”组合起来，没有调用模型。

在该目录的 PowerShell 终端执行：

```powershell
..\..\..\.venv\Scripts\python.exe lesson_harness2_scores.py
```

三个 `..` 从示例工程返回工作区根目录，命令使用共享 Python 运行刚创建的文件。预期输出：

```text
WorkBuddy: 11.5
JobBench: 4.5
LAB Partial: 11.8
WorkBuddy k=5: 80.8
```

成功标准是输出一致，并能口头解释前三行各自的配置和指标；这只核对算术，不能验证论文原始分数。若提示找不到文件，确认终端停在 `01_学习指南/39_Agent_Harness架构实战/示例工程`，文件不是 `.py.txt`；若出现解包错误，检查每个元组是否恰好三个元素。不要把复制时漏项的错误当作环境缺包。

## 怎样接回现有工程

当前教学工程用固定政策和机械规则检查笔记；这与论文没有隐藏答案反馈的开放任务不同。可先保留 [[01_学习指南/39_Agent_Harness架构实战/逐讲学习/07 分开检查执行完成与答案正确|分项质量检查]]，再练习记录失败、提出一个配置假设、比较轨迹。任何外部写入权限、动作批准和预算约束仍由运行系统控制，候选文本不能自行获得修改这些规则的权限。

真正扩展成递归改进工程，还需候选工作区隔离、配置版本、重复试跑、独立评价、失败回退、经验检索与污染控制。本文三篇没有把这些能力加入 `runtime.py`；接下来的 [[01_学习指南/39_Agent_Harness架构实战/选修专题/04 用本地对照实验检查配置修改|本地实验]]只增加手工候选、确定性轨迹和已知答案检查，用来练习证据记录。

如果以后复现官方实现，先读 [官方仓库 README](https://github.com/google-research/harness2)：本次阅读时其安装路径面向 Linux、Python 3.12 与 uv；真实基准还涉及模型服务和相应外部工具，WorkBuddy 需要 Docker。官方确定性演示与完整模型基准是不同运行范围。当前本机教程使用 Windows 共享 Python 3.13 环境，不能把 Linux 命令直接当成本机已验证步骤。本轮没有安装官方工程或运行其演示；后续应先选定目标环境、预算及依赖方案，再按工作区审批规则安装。

## 分层练习与参考答案

### 跟做：解释一条增量

先合上上方解释，写出 WorkBuddy 77.5 后面的 +3.3 代表什么，再运行脚本检查。

> [!example]- 参考答案
> 它表示从单步 k=1 到并行 k=5 的平均分增量；k=5 为 80.8。不是 3.3 的最终分数，也不是三次递归。原始配置 72.4 到 80.8 的差为 8.4 分。

### 独立：给三个结论纠错

“LAB 71.4 说明 71.4% 的完整法律任务全部正确”；“去掉经验库降 3.1 分，所以任何业务加库都升 3.1 分”；“去掉自身条目的完整库等价于在线历史库”。分别写一条修正，提示：查指标定义、实验条件与时间顺序。

> [!example]- 参考答案
> LAB Partial 统计细则通过比例，不能换成整任务成功率。3.1 是该配置下的 WorkBuddy 均值差，可能依赖其他部件、任务和预算。完整库即使去掉自身，仍可能含更晚任务经验，不能等价原在线历史库。

### 迁移：怎样验证自己的配置修改

自己的候选恰好比原配置好一次，能否宣布新方法成功？写出一个更有说服力的小实验方案，暂不调用真实模型。

> [!example]- 参考答案
> 固定任务资料、模型、权限和总预算，记录原配置、仅重复执行后选择、修改后执行三组，避免把更多采样的收益全部归因于修改。用独立任务检验迁移，预先写清质量标准，做多次重复并保留失败；分别报告任务质量、总成本与不确定性。编辑器不读取留作评价的答案或隐藏分数。样本很少时只能写初步观察，不能保证真实业务收益。
