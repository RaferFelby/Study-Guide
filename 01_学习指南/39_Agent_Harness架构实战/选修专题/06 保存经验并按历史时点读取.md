## 今天的第一步

画四个时间点：任务 1 结束写入经验，任务 2 开始读取，任务 3 结束撤回，任务 4 开始再次读取。先预测：撤回以后再查“任务 2 开始时的记录”，应该看到 active 还是 revoked？

答案应是 active。撤回会影响后续使用，但不能把过去的状态抹掉。今天会亲自创建 SQLite 文件，在多个独立 Python 进程之间读取同一条经验，并验证这个判断。

> [!info] 本节实际增加什么
> 增加本地持久记录、带任务时点的撤回和历史读取。经验仍由人准备，只支持上一节的单位处理卡；不运行模型、不自动提取经验、不做语义搜索。历史时点是程序内部的任务序号，不是可信外部时间证明。

## 一、内存变量与持久文件有什么区别

上一节的卡片写在 Python 程序里。程序退出后，内存中的对象消失；再次启动会重新创建作者指定的卡片，不能称为“系统记住了上次学到的经验”。

持久化是把必要状态保存到进程退出后仍存在的介质。本节用一个单独的 SQLite 文件：程序关闭后，另一个进程从文件读取原记录。它与退款会话 `first.db` 是不同数据库，不能混用。

保存状态还要保留变化发生的时点。如果直接把 status 从 active 改为 revoked，只能知道现在的状态，不能回答“第 2 个任务开始时它是否已经被撤回”。因此本课追加一条撤回记录，读取时结合时间重建状态。

## 二、三张小表各自负责什么

打开 [experience_store.py](../示例工程/experience_store.py)，先找到 `create_store()`。

| 表 | 保存什么 | 为什么需要 |
| --- | --- | --- |
| store_meta | 本教学格式的版本 1 | 防止把不兼容的记录当成当前格式 |
| entries | 经验编号、来源任务、可用时点、规则版本、证据说明 | 保存创建时的信息；本课不原地改写 |
| revocations | 经验编号、撤回时点、撤回原因 | 追加历史变化，不删除原始经验 |

`entry_id` 是经验编号，`source_task_id` 是产生经验的任务编号，两者不是一个字段。一个任务可以产生多个不同编号的记录。经验表的主键阻止覆盖同号经验；撤回表的主键让本课每条经验最多撤回一次。它没有重新激活功能；修订后应使用新编号和新的依据。

外键要求撤回记录指向已存在的经验。应用层也先检查编号，为学习者提供明确错误。`evidence_note` 只是你填写的说明，不会自动验证其真实性；它不等于原始轨迹、签名或文件摘要。保留来源报告并人工核对仍然必要。

## 三、在 VS Code 跨进程操作

在本单元 `示例工程` 打开 PowerShell。用 `Get-Location` 确认目录为 `01_学习指南/39_Agent_Harness架构实战/示例工程`。从 [[01_学习指南/39_Agent_Harness架构实战/示例工程/README|代码导航]]打开源码；不需要安装新依赖。

### 第一步：创建新的经验库

```powershell
..\..\..\.venv\Scripts\python.exe experience_store.py --db results/experience-first.db init
```

`--db` 指定文件；`init` 创建表。路径相对终端当前目录，预期输出“经验库已创建”。已有同名文件会抛出 `FileExistsError`，不会覆盖；重复跟做时换新文件名并在后续命令中保持一致。

### 第二步：在任务 1 结束后记录一条经验

```powershell
..\..\..\.venv\Scripts\python.exe experience_store.py --db results/experience-first.db add --id unit-check-v1 --source-task task-a --after-task 1 --rule cny-fen-v1 --evidence "人工核对：先按来源单位换算，再检查费用覆盖"
```

`add` 新增，`--id` 指定经验编号，`--source-task` 标注来源，`--after-task 1` 表示任务 1 结束后才可用，`--rule` 标注规则版本；`--evidence` 是说明文字，带空格时用引号括起来。预期“经验已记录”。本节练习的来源与说明是人工教学记录，不是系统刚运行完真实任务的证明。

### 第三步：读取任务开始前的快照

snapshot（快照）是指定时点可见的一组记录，本节每次查询临时重建，不是复制一整个数据库文件。

```powershell
..\..\..\.venv\Scripts\python.exe experience_store.py --db results/experience-first.db snapshot --before-task 1
..\..\..\.venv\Scripts\python.exe experience_store.py --db results/experience-first.db snapshot --before-task 2
```

第一条打印空列表 `[]`，因为任务 1 开始时经验还未产生。第二条打印一条 JSON 记录：`entry_id` 为 unit-check-v1，`experience.status` 为 active，`available_after` 为 1，`revocation_reason` 为 null。null 表示这个时点没有可见的撤回原因。

每条命令都启动并结束一个新的 Python 进程。第二次仍读到记录，才说明这次练习使用了磁盘中的持久数据，而不是沿用了同一个内存变量。

### 第四步：任务 3 结束后撤回

```powershell
..\..\..\.venv\Scripts\python.exe experience_store.py --db results/experience-first.db revoke --id unit-check-v1 --after-task 3 --reason "来源证据需要重新核对，暂停用于新任务"
..\..\..\.venv\Scripts\python.exe experience_store.py --db results/experience-first.db snapshot --before-task 4
```

`revoke` 追加撤回事件，预期“撤回事件已记录”；任务 4 开始时的快照中 status 为 revoked，并保留填写的原因。没有删除旧经验，也没有宣布以前算出的每个答案都错了。

### 第五步：撤回后重新查过去

```powershell
..\..\..\.venv\Scripts\python.exe experience_store.py --db results/experience-first.db snapshot --before-task 2
..\..\..\.venv\Scripts\python.exe experience_store.py --db results/experience-first.db snapshot --before-task 3
```

两次都仍是 active。撤回发生在任务 3 **结束后**，所以任务 3 开始时也还没看到撤回。严格的小于边界与上一节一致。

完成判断：不删库、不改数据，仅改变 `--before-task` 就能解释 1、2、3、4 四个时点。不要看到旧快照 active 就把它用于当前任务；查询过去的目的应是复核过去。

## 四、按代码顺序理解保存与读取

### 创建和连接为什么分成两个入口

`create_store()` 用文件独占创建模式先占用新文件名，再建立三张表。普通连接使用 SQLite URI 的 `mode=rw` 或 `mode=ro`：rw 连接已有库用于写入，ro 只读；都不会因为路径写错而静默新建数据库。连接前还检查文件存在。

`path.resolve().as_uri()` 把路径转换成 SQLite 可用的文件 URI，避免手工拼接空格或中文路径。这里 URI 只是程序内部连接格式，教材代码导航仍用普通相对链接。

连接使用 `closing()` 负责关闭资源，连接对象自身的上下文负责提交或回滚事务；两者职责不同。Python 的 SQLite 连接上下文不会自动关闭连接。[依据：Python 3.13 sqlite3 文档](https://docs.python.org/3.13/library/sqlite3.html#how-to-use-the-connection-context-manager)

### 为什么追加前检查顺序

`check_append_order()` 查询 entries 与 revocations 中已经记录的最大任务序号，拒绝比它更早的追加。`UNION ALL` 把两类序号放进一张临时结果表，`MAX` 取最大值；空库的结果是 None。同一任务结束后可以写入多条经验，因此相等允许。

例如已经记录任务 3 结束后的撤回，再试图把另一条经验写成任务 2 之后才可用，程序会拒绝。若实际到任务 5 才发现旧任务的经验，应保留旧来源任务编号，但把可用时点写为 5。**来源产生时间与进入经验库的时间可以不同。**

这只能约束通过当前接口提交的顺序，不能阻止有人直接改数据库或在空库里谎报时间。它是教学数据约束，不是防篡改审计。

### 一个事务内完成检查与追加

写连接显式开启 `BEGIN IMMEDIATE`，然后检查顺序、检查编号、插入记录；成功时一起提交，异常时回滚。它先申请写事务，避免把检查与插入拆成不相关操作；另一写事务占用时仍可能报忙，不保证无限并发或自动重试。[依据：SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)

本课约定一个库同一时刻由一个操作者使用，不将数据库锁等同于生产权限系统。初始化失败可能留下未完成的文件；保留它用于排错，使用新文件名重试，不把初始化失败当成功。

### 两次查询如何组成同一个历史快照

读连接先开启只读事务，再查询 `available_after < before_task` 的创建记录，以及 `after_task < before_task` 的撤回记录。两次查询在同一读事务内完成。程序遍历创建记录：若编号存在于当时可见的撤回表，标为 revoked，否则 active。

`ORDER BY available_after, entry_id` 给出稳定显示顺序，但不是经验价值排名。读取结果保留 revoked 项，便于解释历史；真正试跑时仍交给上一节的范围检查器过滤。当前格式检查只核对版本，不是针对恶意数据库的完整校验；只打开自己创建、可信的教学库。

## 五、把读取结果接回上一节试跑

完成上述命令后，新建 `lesson_stored_trial.py`：

```python
from pathlib import Path

from contrast_lab import BudgetConfig, Expense
from experience_store import load_snapshot
from experience_transfer import TaskContext, UnitExperience, run_transfer


def main():
    database = Path("results/experience-first.db")
    expenses = [Expense("room", 600, "yuan"), Expense("meal", 25000, "fen")]
    for task_order in (2, 4):
        records = load_snapshot(database, task_order)
        record = records[0]
        entry = UnitExperience(**record["experience"])
        context = TaskContext(f"task-{task_order}", task_order, "cny-fen-v1")
        report = run_transfer(entry, context, expenses, BudgetConfig(2, False), 85000)
        if report["skip_reasons"]:
            print(task_order, "跳过", report["skip_reasons"])
        else:
            print(
                task_order,
                "通过",
                report["runs"]["candidate"]["evaluation"]["accepted"],
            )


if __name__ == "__main__":
    main()
```

在同一工程目录运行：

```powershell
..\..\..\.venv\Scripts\python.exe lesson_stored_trial.py
```

预期为：

```text
2 通过 True
4 跳过 ['inactive']
```

`records[0]` 取本练习唯一的经验；这不是通用多条经验选择策略。若列表为空，说明你还没按顺序写入，不能随便编造一条填补。`**record["experience"]` 把字典键值作为同名参数传给数据类，等价于逐个填写 source_task_id、available_after、rule_version、status。这里的字典来自本程序固定格式。

本次实际在今天重跑任务 2 的历史快照，是历史情景演练，不是声称程序当时真的执行过任务 2。也没有将旧快照重新设为当前有效状态。

## 六、练习与参考答案

### 跟做：把四个时点写成表

先不看输出预测，再运行四个 snapshot。记录“是否存在”“状态”“可见撤回原因”。

> [!example]- 参考答案
> 任务 1 前不存在；任务 2 和 3 前存在且 active，撤回原因为 null；任务 4 前存在且 revoked，原因是任务 3 后填写的文字。完成标准是能用严格小于条件逐项解释，不只是截图。

### 独立：旧来源、晚写入

创建一份新的练习库。来源仍是 task-a，但直到任务 5 结束后才完成核查并写入。应填哪个 source_task 和 after_task？任务 5 与 6 开始时分别能看到什么？

> [!example]- 参考答案与操作
> 使用新路径如 results/experience-late.db 执行 init，再 add，保留 `--source-task task-a`，使用 `--after-task 5`，证据说明中记录晚核查的原因。snapshot 的 `--before-task 5` 返回空列表，6 返回 active。不能为了让过去结果更好看而把 after_task 改成 1；完成标准是在新库复现两个结果。

### 迁移：新证据推翻旧经验

任务 7 结束后发现旧经验只适合某类数据，还能用原编号覆盖说明、再把撤回记录删除吗？如何保留复核依据？

> [!example]- 参考答案
> 不覆盖。为旧条目记录撤回原因，再用新编号写入经过核查的经验和新的可用时点。本课格式只支持固定单位规则，不能表达任意业务范围；复杂新条件需要明确扩展格式与验证，不能把长说明当成程序已经理解的条件。过去快照仍按原记录解释，当前任务应用新的选择与复核规则。

## 常见错误与完成判断

| 报错或现象 | 检查与修复 |
| --- | --- |
| 经验库不存在 | 先 init，确认 --db 路径和终端目录，不用退款 first.db 代替 |
| 编号已存在／已有撤回 | 先查自己的历史；新经验用新编号，重复操作不覆盖 |
| 不能补写到旧时点 | 写真实进入库的时点，保留来源任务编号 |
| 不支持的版本或 no such table | 是否打开了别的单元数据库；不要随便改版本或建同名表 |
| database is locked | 关闭其他写入程序，确认单操作者；不删除正在使用的库 |
| 新任务仍读取 active | 是否误用了过去的 before-task；查看当前实际任务序号 |

完成标准：跨独立命令保存并读取；撤回后能重建过去；当前读取会阻止已撤回经验试跑；能说明时点是人工记录、证据说明尚需核验，持久化本身也不代表模型学会了新知识。
