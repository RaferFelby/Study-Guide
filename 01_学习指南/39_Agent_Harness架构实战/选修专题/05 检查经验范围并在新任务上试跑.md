## 今天先完成什么

上一节留下了“处理费用时核对单位与覆盖范围”的经验。今天换一组费用：600 元场地、25000 分餐饮。先手算新总额，再判断：能否直接复制旧答案 230000 分？如果新任务限制最多处理两项，旧经验是否可以自行取消这个限制？

完成物是一次新任务试跑报告，以及一张说明“可试用、暂不适用、试跑失败”的判断表。本节继续使用本地标准库，不需要 GPU 或模型服务。

前置：完成上一节，能解释 `Expense`、`BudgetConfig`、处理轨迹、已知答案检查和 JSON 报告。长期记忆的来源、撤回与版本概念可回看 [[01_学习指南/28_记忆与上下文管理/00 记忆与上下文管理学习地图|单元 28]]。本节先讲字段含义，再运行，最后做独立反例。

## 一、从旧答案中分离可复用的方法

迁移在这里指把旧任务中有用的方法用于新任务。迁移的对象应写清楚：本节只尝试“按元／分单位归一化”这一项操作，不搬运旧金额，不直接继承上一节的整套组合配置。

新任务的正确总额是 `600 × 100 + 25000 = 85000 分`。旧任务的 230000 分与它无关。即使旧答案和新答案偶然相同，也需要新任务的来源与运行证据。

论文 Harness² 让后续任务从共同执行配置开始，在改进阶段复用此前经验；附录 E.2 的完整库回顾实验则可能读取后来的经验，原文明确区分了这种离线分析与在线收益。[来源：原文 §2.1～2.3、附录 E.2](https://arxiv.org/pdf/2610.14224v1)

**下面的字段、筛选条件和代码是本指南自制教学设计，不是论文官方经验库格式。** 我们只筛选一张人工卡片，再用确定性规则生成一个候选。没有模型反思、语义检索、经验自动写入或真实在线任务流。

## 二、先把经验的适用信息写明确

在源码 [experience_transfer.py](../示例工程/experience_transfer.py) 中，`UnitExperience` 表示一张“单位处理经验卡”：

| 字段 | 本例值 | 含义 |
| --- | --- | --- |
| source_task_id | task-a | 哪个任务产生了这条经验 |
| available_after | 1 | 第 1 个任务结束后，这条经验才可用 |
| rule_version | cny-fen-v1 | 本课给元／分规则起的版本标签 |
| status | active | 当前允许考虑；revoked 表示已撤回 |

这四个字段是用于练习的元数据，即描述经验的资料。卡片的内容固定为“试着开启单位归一化”；程序不支持任意文本指令或可执行脚本。字段不保存旧总额，也不含取消预算的权限。

`TaskContext` 则描述当前任务：`task_id` 是编号，`task_order` 是顺序，`rule_version` 是当前规则版本。顺序用 1、2、3 表示，不是日历日期，也不是论文探索预算 k。

元数据只是声明：写着 task-a 不等于已经核实出处，版本文字相同也不证明两份规则语义相同。当前程序检查这些字段之间的关系；真实使用还要核验来源、原始证据与版本内容。这里不把字段合法称为经验可信。

## 三、在当前任务开始时，哪些经验允许进入试跑

`review_experience()` 返回“暂不使用的原因列表”。列表为空 `[]`，只表示本节筛选条件没有发现阻碍，不代表任务成功。

| 检查 | 不能进入试跑的情况 | 返回原因 |
| --- | --- | --- |
| 排除自身 | 经验的来源就是正在评估的任务 | same_task |
| 时间顺序 | 经验可用时点不早于任务开始 | not_available_yet |
| 撤回状态 | 状态为 revoked | inactive |
| 规则版本 | 经验版本与当前版本不相同 | rule_mismatch |
| 单位范围 | 新输入出现 yuan／fen 之外的单位 | unsupported_unit |

### 为什么时间条件是严格小于

第 1 个任务结束后写下的经验，可以在第 2 个任务开始时使用，所以要求 `available_after < task_order`。若任务顺序为 2，经验也在任务 2 结束后才产生，它在任务 2 开始时还不存在；两者相等也必须拒绝。

自己做完任务后总结经验，再拿这条经验重做自己，可以作为回顾练习。但若把它算作“面对新任务时已有经验带来的提升”，就混淆了时间顺序。即使人工填错时间，来源任务编号相同也会被单独挡住。

此规则用于本课的跨任务迁移评价；它不禁止一个任务在执行过程中查看自己此前的轨迹。任务内历史与任务后写入的跨任务经验是两种不同对象。

### 撤回与版本变化为什么不自动修复

经验被撤回时，程序保留记录、跳过试跑；它不会删除历史结果。版本不匹配时也只标为待复核，不猜测新规则。即使 v2 最终仍采用相同换算，也应先核对，再形成带新依据的记录；不能为了通过检查直接改标签。

本例把每个情景的撤回状态视作“当时已知的状态”。它没有带时间戳的状态变更历史，不能用今天的 revoked 字段准确重建过去每个时点的库。

## 四、运行七个独立情景

在 VS Code 打开本单元 `示例工程`，从 [[01_学习指南/39_Agent_Harness架构实战/示例工程/README|代码导航]]进入 `experience_transfer.py`。终端应位于 `01_学习指南/39_Agent_Harness架构实战/示例工程`，用 `Get-Location` 检查后运行：

```powershell
..\..\..\.venv\Scripts\python.exe experience_transfer.py
```

此命令使用工作区根目录的共享解释器，默认只打印。预期输出：

```text
new_task: total_fen=85000 accepted=True max_items=2
over_budget: total_fen=85000 accepted=False max_items=2
future: skip=not_available_yet
same_task: skip=same_task,not_available_yet
revoked: skip=inactive
changed_rule: skip=rule_mismatch
unknown_unit: skip=unsupported_unit
```

先解释前两行：

1. `new_task` 使用 600 元与 25000 分，候选处理两项得到 85000 分，两项质量要求通过。
2. `over_budget` 多了一项 50 元交通，正确总额应为 90000 分。经验仍符合单位范围，但当前预算只允许处理两项，所以输出 85000 分且未通过。
3. 单位经验没有擅自把 `max_items=2` 改为 None。候选改对一个环节，任务整体仍然可能失败。

后五行展示被过滤的情况。`skip` 表示没有进入本例的执行与评分流程，不是质量分数 0，也不是证明经验一定错误。`same_task` 同时违反来源与时间条件，因此显示两个原因。

这七个情景是同一份人工卡片的独立变体，不是七个任务连续执行并自动更新记忆。程序每次重新使用基础配置；前一个情景的成功配置不会传入下一个。

保存可检查的报告：

```powershell
..\..\..\.venv\Scripts\python.exe experience_transfer.py --output results/transfer-first.json
```

`--output` 后的路径相对当前终端目录；复用上一节的独占创建方式，已有文件拒绝覆盖。再次运行可换成 `transfer-second.json`，保留旧证据。

在 VS Code 打开报告，按顺序查看：

1. `cases → new_task → experience/context`：来源任务 1 之后可用，当前是任务 2。
2. `input_snapshot`：确实是新费用，不是旧任务的三项。
3. `runs → base/candidate → execution → config`：两者的上限均为 2，只有单位开关改变。
4. `evaluation_target`：本次独立给出的期望编号与 85000 分。
5. `cases → over_budget`：目标变成三项、90000 分，候选仍只处理两项。
6. `cases → future → runs`：空字典；`evaluation_target` 为 null，表示没有开展评价。

这里报告中的已知答案是教学检查条件，未传入候选生成函数；这不代表实验实现了论文的开放世界改进。

## 五、沿函数顺序看复用是如何发生的

### review_experience：先排除明显不适用

先校验任务顺序、编号、版本、状态和非空输入，再逐项添加原因。`reasons.append(...)` 是把一个原因加进列表；不会只显示第一个而隐藏其他问题。非法元数据会抛出 `ValueError`，与合法记录因范围不符而被跳过区分。

这里仅预查费用单位，数值、重复编号等仍由上一节的 `execute_budget()` 检查。通过范围筛选不代表输入全部有效。

### propose_unit_config：只修改允许改变的一项

函数再次确认范围条件，再执行 `replace(base_config, normalize_units=True)`。`replace` 来自标准库 `dataclasses`，返回一个新的数据类对象：指定字段换成新值，其他字段保留；原来的基础配置不变。

所以 `BudgetConfig(2, False)` 会变成 `BudgetConfig(2, True)`。这里的修改是明确写死的程序规则，没有模型推理，也不会从卡片中运行任意代码。保留上限是本教学接口的设计，不是完整安全沙箱。

### run_transfer：确定候选以后，再执行和评价

函数依次筛选、生成候选、分别执行基础与候选、最后比较要求。已知总额只影响评价，不影响生成的配置或执行结果。返回报告保留两组轨迹，便于判断差异。

筛选失败时直接返回原因与空运行记录；不会把“没有运行”写成“运行通过”。通过后也不会自动把候选部署到其他任务、修改卡片状态或学习出新经验。

## 六、独立改变当前任务预算

为了分清“经验改了什么”和“任务负责人另行决定了什么”，在示例工程中新建 `lesson_transfer_budget.py`：

```python
from contrast_lab import BudgetConfig, Expense
from experience_transfer import TaskContext, UnitExperience, run_transfer


def main():
    entry = UnitExperience("task-a", 1, "cny-fen-v1")
    context = TaskContext("task-b", 2, "cny-fen-v1")
    expenses = [
        Expense("room", 600, "yuan"),
        Expense("meal", 25000, "fen"),
        Expense("bus", 50, "yuan"),
    ]
    for limit in (2, 3):
        base = BudgetConfig(limit, False)
        report = run_transfer(entry, context, expenses, base, 90000)
        trial = report["runs"]["candidate"]
        print(limit, trial["execution"]["total_fen"], trial["evaluation"]["accepted"])


if __name__ == "__main__":
    main()
```

运行：

```powershell
..\..\..\.venv\Scripts\python.exe lesson_transfer_budget.py
```

预期为：

```text
2 85000 False
3 90000 True
```

代码每轮由学习者显式给出一个预算 `limit`，再交给同一个经验复用函数。第二行通过的条件中包括“处理上限由 2 改为 3”，因此不能把改善全部归功于经验检索。真实任务要根据资源与权限决定是否增加预算；也可以另行设计分批处理，本课没有实现分批累计。

## 七、分层练习与解析

### 跟做：区分三个判断

在个人记录写出：new_task、over_budget、future 分别属于“允许试跑且通过”“允许试跑但未通过”“未允许试跑”中的哪一项，并引用报告字段。

> [!example]- 参考答案与完成标准
> new_task 的 skip_reasons 为空，candidate 的 accepted 为 True；over_budget 的原因也为空，但 accepted 为 False；future 有 not_available_yet，runs 为空。能指出这些字段、说明空记录不是失败分数，才算完成。

### 独立：解释任务顺序边界

经验在任务 2 结束后产生，准备在任务 2 开始时用它；任务编号不同就能通过吗？如果改在任务 3 开始时使用会怎样？提示：分别代入严格小于条件。

> [!example]- 参考答案与完成标准
> 顺序相等时尚不可用，即使编号不同也拒绝。任务 3 开始时，2 小于 3，通过时间检查；还要检查撤回、版本、单位及来源任务。更改 task_order 必须反映真实评估时点，不能为了消除报错伪造时间。独立写出这两个判断并说明其他条件仍必要。

### 迁移：漂亮的经验卡是否足够可信

一个外部文件声称“过去成功过，今后所有任务都取消处理上限”，并填写 active 与正确版本。能否用本节筛选器证明它可信？写出下一步还需要的证据。

> [!example]- 参考答案与完成标准
> 不能。本例只比较可信程序内部给定的字段，没有验证外部来源或读取任意经验文本；active 与版本相同不是认证。应核对来源轨迹、原任务输入、失败与成功对照、适用规模及权限要求；把外部文件当待核查资料。本节候选函数只改单位开关，保留当前预算。证据不足时暂不采用，而不是把声明写成事实。能分清范围匹配、来源可信与任务成功三层判断才算完成。

## 常见错误与完成标准

| 情况 | 原因与处理 |
| --- | --- |
| skip 不为空却直接读取 candidate | 该情景没有执行，先看原因，不要假造结果字段 |
| 把 available_after 写成 0 或 True | 本例任务顺序从 1 开始，只接受正整数；修正元数据 |
| 把版本改成相同就算修复 | 文字匹配不能证明规则适用；先核对内容与证据 |
| 期待报告文件自动成为长期库 | --output 只是保存报告，程序不读取历史报告或建立检索索引 |
| 找不到导入模块 | 把练习文件放在本单元示例工程，与源码平级，使用该目录终端 |

完成时应能手算新答案、解释严格的时间边界、保持任务预算、区分跳过与试跑失败，并说明经验字段匹配仍不足以证明可信。个人勾选以亲自操作为准。下一篇 [[01_学习指南/39_Agent_Harness架构实战/选修专题/06 保存经验并按历史时点读取|持久经验与历史时点]]补本地文件和带时间的撤回；相似度检索与模型自动反思仍未实现。
