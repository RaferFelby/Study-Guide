## 要解决的问题与前置

用户批准“创建退款工单”，执行前subject被模型改成另一事项，原批准是否仍有效？复习单元14待确认状态、单元15幂等。本讲用动作指纹绑定owner/tool/完整参数，写操作只在内存模拟。

## 批准与权限各管什么

role=operator说明当前用户有这类能力；approved_actions说明他通过可信渠道确认了某个具体动作。两者同时满足才执行。读者角色即使持有批准指纹也不获得operator能力；operator未批准也不能写。

动作指纹是owner、工具名和规范化JSON参数的SHA256摘要。摘要也叫哈希：把输入内容按确定算法计算成固定长度的值，本例用64个十六进制字符展示。相同输入得到相同结果，改内容通常会改变结果；它不隐藏输入本身，也不授予权限。这里用于比较动作内容，不能把它当加密后的批准凭据。它便于比较内容是否一致，不是用户签名，也不证明谁批准。可信来源仍是应用界面/会话；文档打印同一哈希不能自行成为批准记录。

规范化JSON按键排序和固定分隔符，所以字典插入顺序不影响摘要。字符串内容/空格本身仍影响动作：展示、确认、执行必须用同一验证后的参数，不能批准后再悄悄规范化成另一份。

## 最小示例：字典顺序与内容变化

新建`lesson_fingerprint.py`：

```python
from audit import fingerprint

first = {"subject": "退款", "request_key": "key-1"}
same = {"request_key": "key-1", "subject": "退款"}
changed = {"subject": "别的工单", "request_key": "key-1"}
print(fingerprint("alice", "create_ticket", first) == fingerprint("alice", "create_ticket", same))
print(fingerprint("alice", "create_ticket", first) == fingerprint("alice", "create_ticket", changed))
print(fingerprint("alice", "create_ticket", first) == fingerprint("bob", "create_ticket", first))
```

预期True、False、False。owner也参与，所以不能把Alice批准拿给Bob；工具名参与，所以读的批准不能用于写。摘要字符看起来杂乱，但计算是确定性的，不是每次生成随机数；不用背字符，重点是相同完整动作匹配、变化后不匹配。

## 动手：批准、重试、改参数

新建`lesson_approval.py`：

```python
from pathlib import Path
from audit import fingerprint
from runtime import ToolRuntime, TrustedContext

arguments = {"subject": "退款", "request_key": "lesson-1"}
action = fingerprint("alice", "create_ticket", arguments)
context = TrustedContext("alice", role="operator", approved_actions=frozenset({action}))
runtime = ToolRuntime(Path(__file__).parent / "fixtures")
first = runtime.execute("create_ticket", arguments, context)
again = runtime.execute("create_ticket", arguments, context)
changed = runtime.execute("create_ticket", {**arguments, "subject": "另一个事项"}, context)
print(first["data"]["ticket_id"], again["data"]["replayed"])
print(changed["error"]["code"], len(runtime.tickets))
```

这段先准备完整参数，再算Alice/create_ticket的指纹，将它装入可信上下文。创建runtime只是准备合成资料注册表，不读取Bob文件。前三次execute使用同一上下文：第一次创建，第二次因相同幂等键回放，第三次因subject变化不再匹配原批准。最后分别检查返回的工单ID、回放标志和内存工单数量。

这里 `first["data"]` 只适用于前面确认应成功的固定演示；真实调用先判断 `result["ok"]`，再读取data或error，不能在失败时仍取data导致KeyError。失败不是一定没有结构化结果，本例返回明确错误字典。

预期ticket-1 True，needs_confirmation 1。frozenset是不支持普通增删的集合；`{**arguments, ...}`先复制已有字段再覆盖subject，原arguments不变。代码构造批准仅供演示，真实应用不能把这个脚本当用户已经确认的证据。

## 逐步解释重试路径

create_ticket先字段/值验证，再角色、动作批准，然后查(owner,request_key)幂等记录。相同动作回已有ID；不同已批准动作但同key报idempotency_conflict。批准不是幂等键，幂等键也不是权限凭据。

撤销角色后，即使已有成功记录也permission_denied，因为当前权限先检查。批准记录当前无过期/撤销/一次性消费；实际可加批准时间、有效期、审批人、目标摘要和撤销版本。它们需要可信存储，不能由模型自己填写。

真实写副作用需要持久幂等，上游稳定操作ID与结果核对。本例内存字典重启消失，不证明支付/发邮件/订票严格一次；只有本次进程重复创建一份内存工单的行为。

## 高风险动作的确认界面应显示什么

给用户显示资源目标、关键参数、影响范围、不可逆后果和实际工具，而非只问“是否允许继续”。确认后执行器重新校验同一参数及权限；参数变更就重新展示确认。不可信工具结果声称approved=true不能更新批准集合。

确认对话与用户指令授权要结合已有会话：用户明确要求的可逆动作可按规则自动执行，但涉及高风险工具的系统政策和可信批准链不能由检索资料覆盖。本教程工程所有create_ticket都要求演示批准，这是教学项目约定，不是所有应用的唯一标准。

## 常见错误

- approved=true一个布尔覆盖所有写：没绑定目标/参数，容易错批。
- 只有批准没有角色：需同时核用户能力范围。
- 哈希算对就认为身份真实：摘要不是认证签名。
- 重试直接回缓存跳授权：撤权后仍需拒绝。

## 练习与答案

跟做：三次调用只保留一份工单，改subject需确认。完成判断：能解释指纹和幂等键不同职责。

独立：工具名不参与摘要会有什么问题？owner不参与又怎样？

迁移：为“删除指定目录生成结果”设计具体确认信息和执行前路径复核，不编写或运行删除代码。

> [!example]- 参考答案与解析
> 缺工具名可能跨动作复用；缺owner可能跨用户复用。真实还需租户/资源版本等与作用范围一致。
>
> 明确目标绝对路径、属于本次生成范围、列出将删除内容、不可恢复影响、确认身份和参数摘要；执行前解析路径留在允许根内，用户改动后重新核。此练习只设计，不能从教程文本推断用户授权实际删除。
