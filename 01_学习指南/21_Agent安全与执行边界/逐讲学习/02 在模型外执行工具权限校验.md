# 第 2 讲：在模型外执行工具权限校验

> [!nav] 页面导航

## 要解决的问题

即使模型提出错误工具调用，应用也应拒绝。本讲将允许工具、当前用户、角色与参数检查放在Python执行层，复习单元18认证/授权区别，单元15Schema校验。

## 最小权限与注册表

最小权限是只给完成当前任务需要的能力。退款资料查询需要read_document，不需要读环境变量或shell。当前注册表只有read_document和create_ticket，其他工具名统一unknown_tool。未暴露的能力比“暴露后希望模型不用”更易约束。

TrustedContext是应用构造的冻结数据类，owner/role/approved_actions不从arguments接收。frozen只防普通赋值，不是安全沙箱；真正可信来自它的创建通道和执行层使用方式。示例load_context_demo模拟该来源，没有真实登录。

## 最小示例：跨用户拒绝

新建`lesson_authorization.py`：

```python
from pathlib import Path
from runtime import ToolRuntime, TrustedContext

runtime = ToolRuntime(Path(__file__).parent / "fixtures")
context = TrustedContext(owner="alice")
own = runtime.execute("read_document", {"document_id": "alice-account"}, context)
other = runtime.execute("read_document", {"document_id": "bob-account"}, context)
print(own["ok"])
print(other["ok"], other["error"]["code"])
```

共享解释器运行，预期True和False not_found。私有文档元信息owner由受信注册表提供；比较context.owner，不看文件正文customer字段。Bob读Alice同理应拒，不因文件夹相同而允许。

## 逐步跟执行流程

execute先累计会话调用数，检查预算；要求arguments是对象；按工具名选择实现。read_document只接document_id文本，查注册表，核owner，再检查文件。create_ticket只接subject/request_key，核role=operator，再核批准与幂等。

失败抛SecurityError(code,message)，execute把它转换成结构化ok=false，并写deny审计；成功ok=true并写allow审计。意外程序错误不被SecurityError捕获静默吞掉，测试会发现。资源OSError在文件读取边界转换成resource_unavailable，避免把路径细节直接返给调用者。

同名工具的权限定义应由应用维护，不能让模型输出“requires_confirmation=false”来改注册表。对于读工具，仍可能有隐私风险，并非全部读都免费/安全。

## 动手：伪造权限参数

新建`lesson_fake_owner.py`：

```python
from pathlib import Path
from runtime import ToolRuntime, TrustedContext

runtime = ToolRuntime(Path(__file__).parent / "fixtures")
context = TrustedContext("alice", role="reader")
attempts = [
    ("read_document", {"document_id": "bob-account", "owner": "bob"}),
    ("create_ticket", {"subject": "退款", "request_key": "key"}),
    ("read_env", {}),
]
for tool, arguments in attempts:
    result = runtime.execute(tool, arguments, context)
    print(result["error"]["code"])
```

预期invalid_arguments、permission_denied、unknown_tool。多传owner被字段检查拒，合法写参数仍无角色，未知工具根本不执行。把context改operator后第二条变needs_confirmation，说明权限和批准是两层。

## 解析提议与授权不要混在一起

parse_proposal只接受tool文本与arguments对象，拒重复JSON键、NaN等非有限值、额外approved/role字段与超4096字节提议。它解决结构歧义，不能判断当前用户有权访问哪个文档；解析后仍必须execute。

反过来，只做授权而解析器允许同名键在不同层“取前/取后”，也可能造成批准显示与实际执行不一致。解析规则应在界面、批准、执行保持一致。入口解析失败当前函数直接报错，没有进入runtime审计；真实HTTP入口应单独记录解析拒绝事件。

## 常见错误

- 读private JSON后再查owner：越权数据已进入内存/日志，授权应在读取前。
- 用正文的customer来决定身份：该字段是业务数据，不是认证结果。
- 默认未知工具执行通用函数：注册表要默认拒绝，不自动尝试shell。
- 授权检查只在第一次，幂等回放直接返回：重试时仍核当前角色/批准，撤权后不能绕过。

## 练习与答案

跟做：三种伪造都拒，operator无批准也拒。完成判断：能指出每条在哪层失败。

独立：管理员角色是否应默认读所有租户数据？怎样定义显式范围？

迁移：为业务查询/写两个工具写字段白名单、可信身份来源、权限范围和默认拒绝错误码。

> [!example]- 参考答案与解析
> 角色只是能力类别，仍需租户/资源范围；operator能创建自己的工单，并不自动读Bob。真正管理员也应按产品明确授予范围和审计用途，不能凭名称推断全权限。
>
> 验证→授权→批准→执行→审计按实际职责安排，所有入口都走统一执行层，不能留下绕过的“方便调试”接口。
