## 1. 为什么需要配置

同一个程序可能在你的电脑、测试环境和服务器上使用不同的重试次数、日志位置或服务凭据。如果把这些值直接写在函数里，换环境就要改源码，也容易意外提交真实凭据。

配置就是程序运行时使用的一组可调整设置。常见来源包括命令行参数、环境变量、配置文件或密钥服务。本工程用环境变量演示最小做法。

## 2. 什么是环境变量

环境变量是操作系统在启动程序时附带的一组“名字—文字值”。例如 `TICKETKIT_ATTEMPTS=4` 表示名为 `TICKETKIT_ATTEMPTS` 的设置值是文字 `4`。因为环境变量读出来是文字，程序必须检查并转换。

示例工程用 `Config.from_env()` 读取设置：

```python
from ticketkit import Config

config = Config.from_env({"TICKETKIT_ATTEMPTS": "4"})
print(config.attempts)
```

这里传入字典是为了演示和测试；不传字典时，代码才读取当前进程的真实环境变量。函数把文字 `"4"` 转为整数 4，并拒绝小于 1 或不是整数的值。

你可以在 VS Code 打开 [config.py](../示例工程/src/ticketkit/config.py)，按顺序看：定义默认值、读取键、把次数转换成整数、检查次数范围、返回配置对象。

## 3. 配置对象和启动边界

示例用数据类保存经过检查的设置：

```python
from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)
class Config:
    attempts: int = 3
    api_token: str | None = field(default=None, repr=False)
```

`attempts` 默认是 3；`api_token` 可以是文字，也可以没有值（`None`）。`frozen=True` 避免程序开始运行后随意改配置。读取并检查配置属于程序启动边界：外部的文字值先在入口转换为可信的配置对象，再传给需要它的函数。

不要让每个函数自己到处读取环境变量。集中读取后，函数输入是什么更清楚，测试时也更容易传入固定设置。

## 4. 密钥与“隐藏”

API token、密码等密钥能让持有者访问服务。把它们写进 `.py` 文件有几个问题：文件容易被提交到代码仓库；复制代码时也会一起泄漏；截图和日志还可能再次传播。

本示例的 `repr=False` 只是不让普通对象显示文字时顺便打印 token。它不是加密，也不能阻止程序主动读取或打印它；`dataclasses.asdict()` 等操作仍可能取出字段。因此：

- 示例与文档只使用假值，例如 `demo-token`。
- 真实值通过受控的环境变量或密钥管理服务提供。
- 不把密钥打印到日志、报错、截图或聊天记录。
- 发现密钥泄漏时要及时撤销并重新生成，单纯删掉文件不足以撤销权限。

环境变量适合演示和简单部署；共享服务器上还要控制哪些用户和进程能读取它。不要把 `.env` 文件里的真实密钥提交到仓库。

## 5. 日志解决什么问题

`print` 适合简单的屏幕输出。程序长期运行时，我们通常希望记录时间、严重级别、请求编号和发生了什么，方便之后定位问题。这种带有字段的运行记录叫日志。

Python logging 有三个常见部分：

- **logger**：代码通过它发出记录，例如 `logger.info(...)`。
- **handler**：决定记录写到哪里，例如屏幕或文件。
- **formatter**：决定每条记录如何排版。

示例工程配置屏幕输出与轮转文件输出。轮转日志是指文件长到一定大小后换新文件，并保留有限数量的旧文件，避免一个日志无限增长。工程示例最多保留两个备份。

```python
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger("demo")

logger.info("processed rows=%d", 12)
logger.warning("tool timeout")
```

`info` 记录正常的重要进展；`warning` 记录需要注意但程序还能继续的情况。`"processed rows=%d"` 是格式模板，后面的 `12` 填入 `%d`。这种延迟格式化方式也避免日志级别关闭时提前拼接文字。

这是便于看懂的控制台最小例子。真实工程会在程序启动时调用 `setup_logging`，额外配置时间、请求编号和轮转文件；不要在每个业务函数里重复配置日志。

## 6. 让日志带请求编号

想象同时处理很多请求，只看到“工具失败”很难知道哪一条请求失败。请求编号可以把同一次任务相关的日志关联起来。示例工程用 `request_scope` 在一个代码范围内临时设置编号：

```python
from pathlib import Path
from ticketkit.observability import close_logging, request_scope, setup_logging

logger = setup_logging(Path("logs/tutorial.log"))
try:
    with request_scope("task-001"):
        logger.info("开始处理工单")
finally:
    close_logging()
```

`setup_logging` 创建控制台与文件处理器，并把请求编号加入日志格式；`finally` 确保程序结束时关闭文件处理器。运行后，控制台和 `logs/tutorial.log` 中都会出现大致类似的记录：

```text
2026-09-23 10:00:00,000 INFO request_id=task-001 开始处理工单
```

真实时间会不同。请求编号应是可用于关联的标识，不要把用户密码、完整请求正文或 token 充当编号。日志只记录解决问题所需的信息。

## 7. 记录异常和轮转文件

```python
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger("demo")

def parse_input():
    return int("不是数字")

try:
    try:
        parse_input()
    except ValueError:
        logger.exception("输入处理失败")
        raise
except ValueError:
    print("最外层收到错误，不能把这次输入当作成功")
```

这是一个完整的最小例子。运行时先看到带有错误堆栈的日志，再看到最外层的提示。`logger.exception` 应在异常处理块里调用，它会把当前异常堆栈写入日志；`raise` 把同一个错误继续交给上层决定。堆栈能指出错误经过哪些代码位置；原始输入可能包含隐私，因此通常不要顺手完整打印输入。

示例工程在启动时创建日志文件夹和 handler，运行结束时关闭它们。重复配置 logger 时，如果旧 handler 没清理，可能每条日志都出现多次。工程只管理自己的 `ticketkit` logger，不应该随意删掉整套应用的根 logger 配置。

多进程同时向同一个轮转文件写入需要额外设计；本例针对单进程。不要看到轮转文件可用就推断多进程写入也安全。

## 8. 运行与观察

在示例工程目录运行：

```powershell
..\..\..\.venv\Scripts\python.exe -m ticketkit
```

查看终端中的日志和统计结果，然后在 VS Code 左侧打开 `logs/demo.log`。终端日志通常写到 stderr，程序统计结果写到 stdout；PowerShell 默认会一起显示。日志里的时间、行顺序可能有环境差异。

如果没有生成日志文件，先检查终端当前位置，再检查你是否运行了示例入口。若日志重复，检查是否多次添加 handler。若 token 出现在输出中，停止复制日志，移除暴露内容并替换真实 token。

## 9. 练习与答案解析

**跟做：** 把尝试次数从默认 3 改成从传入映射读到 4；再传入 `"abc"` 和 `"0"`。

> [!example]- 跟做练习结果解析（先运行再展开）
> `"4"` 转成整数 4；`"abc"` 因不是整数产生配置错误；`"0"` 虽可转换成整数，但不符合“至少尝试一次”的规则，也产生配置错误。这展示了格式检查和业务范围检查是两件事。

**独立：** 增加一个 `LOG_LEVEL` 配置，至少接受 INFO 和 WARNING，其他值应报出清晰错误。完成标准是大小写策略明确，错误消息告诉使用者允许值。

> [!example]- 独立练习参考思路（先完成再展开）
> 先从传入映射读取 `LOG_LEVEL`，若没有则使用你选定的默认级别；把文字统一转成大写后，只接受 `INFO` 或 `WARNING`，其他值抛出带允许值的配置错误。把检查后的级别保存在配置对象中，启动日志时再应用它。验证 `"INFO"`、`"warning"` 和 `"DEBUG"` 三种输入，并解释第三种为什么被拒绝。

**迁移：** 为一条模拟任务增加 `request_id`，验证成功与失败日志都能关联到同一个编号，同时不记录 token 和完整用户输入。

## 10. 本讲小结

- 配置应在程序入口读取并验证，再传给需要它的功能。
- 环境变量是文字值，读取后仍要转换和检查。
- `repr=False` 只是减少无意显示，不是安全保护。
- logger 发出日志，handler 选择去处，formatter 选择格式。
- 请求编号帮助关联日志；日志不应该泄露密钥或不必要的个人数据。
