## 1. 先看一次性保存数据的做法

假设要处理 5 张工单。最直观的做法是先把 5 张工单全部放进列表，再逐张统计：

```python
tickets = ["T001", "T002", "T003", "T004", "T005"]
for ticket in tickets:
    print(ticket)
```

列表会把所有元素都保存在内存里。内存可以粗略理解为程序当前工作时使用的桌面：桌面有限，放的东西越多，空间占用通常越大。五条数据没有问题；如果有几千万条，全部先保存就可能耗费大量内存。

## 2. 可迭代对象和迭代器

“可迭代对象”就是能让 `for` 逐项取值的对象，列表、字符串和文件都可以迭代。“迭代器”是实际负责记住当前位置、每次交出下一个值的对象。你可以先想成一台逐张吐出工单的机器：机器记住已经发到哪一张，不需要把所有工单摊在桌面上。

调用 `next(iterator)` 会取出下一项。没有下一项时，Python 用 `StopIteration` 表示结束；通常 `for` 会自动处理这个结束信号：

```python
numbers = iter([10, 20])
print(next(numbers))
print(next(numbers))
print(list(numbers))
```

结果是 `10`、`20`、`[]`。前两次 `next` 各取走一个值，之后迭代器已经耗尽，所以转成列表时为空。迭代器通常只能从当前位置向前走，不能像列表那样回到开头；想重新遍历时，通常重新创建它。

## 3. 用 yield 创建生成器

生成器是一种编写迭代器的简单方式。普通函数遇到 `return` 就结束并交回结果；生成器函数遇到 `yield` 会交出一个值，然后暂停在当前位置，下一次取值时再继续。

```python
def count_to_three():
    print("开始准备数据")
    yield 1
    print("准备第二个数据")
    yield 2
    yield 3

items = count_to_three()
print("生成器已创建")
print(next(items))
print(next(items))
print(list(items))
```

按顺序运行会看到：

```text
生成器已创建
开始准备数据
1
准备第二个数据
2
[3]
```

调用 `count_to_three()` 时只创建了生成器，还没执行函数体，所以“开始准备数据”暂时没有打印。第一次 `next` 才开始运行，遇到 `yield 1` 后暂停。之后同理继续。这种“需要时才产生下一项”的特性叫惰性处理。

## 4. 为什么生成器能省内存

示例工程的 `generated_tickets(100_000)` 每次产生一张工单；`summarize` 一边接收工单，一边更新两个数字：已打开多少张、已关闭多少张。它不需要同时记住十万张工单。

在 VS Code 打开 [data.py](../示例工程/src/ticketkit/data.py)，先找到 `generated_tickets`，再找到 `summarize`。关键逻辑可以缩小成下面这个独立例子：

```python
def make_numbers(count):
    for number in range(count):
        yield number

def total_numbers(numbers):
    total = 0
    for number in numbers:
        total += number
    return total

print(total_numbers(make_numbers(5)))
```

`make_numbers(5)` 不会先生成 `[0, 1, 2, 3, 4]`，而是每次交出一个数字。`total_numbers` 每次只拿一个数字并加到 `total`。结果为 `10`。列表版本 `total_numbers(list(make_numbers(5)))` 会先把全部数字放进列表，再统计；数据越多，列表占用通常越大。

但是，写了生成器不代表整条程序一定省内存。如果后面写 `list(make_numbers(10_000_000))`，还是把所有值保存起来了。如果你把每条记录都放进 `totals[ticket_id]`，记录数越多，字典也会越大。要观察内存，必须看整个数据处理过程，而不只是输入是不是生成器。

## 5. 读取文件时一行一行处理

本节首次把 `with` 文件管理与 `try/except` 错误处理放进生成器。它们的详细执行过程在 [[01_学习指南/01_Python工程化/逐讲学习/06 看懂报错并安全管理资源|第 6 讲：看懂报错并安全管理资源]]；现在先按下面解释跟做文件读取。若尚不能辨认缩进块，先读下一讲的基础部分，再回来完成本节和第 6 节，最后做内存比较。

文本文件由许多行组成。`read_text()` 一次读完整个文件；`open()` 后逐行遍历则可以一行处理完再读下一行。适合一条记录占一行的数据格式是 JSONL，也就是每一行各自是一段 JSON 文本。

### 先创建一个 JSONL 文件

1. 在 VS Code 的示例工程文件区新建 `tickets.jsonl`。
2. 每行写一个 JSON 对象，不要在两条记录中间加逗号，也不要把整个文件包在方括号里。
3. 以 UTF-8 编码保存。文件内容如下：

```json
{"ticket_id":"T001","status":"open"}
{"ticket_id":"T002","status":"closed"}
```

### 写一个简化的逐行读取器

为了先看清每一步，下面写一个可独立运行的简化版本。把它放在刚才创建 `tickets.jsonl` 的同一目录，保存为 `read_jsonl_demo.py`：

```python
import json
from pathlib import Path

def read_jsonl(path):
    with path.open(encoding="utf-8") as stream:
        for line_number, line in enumerate(stream, start=1):
            try:
                value = json.loads(line)
            except json.JSONDecodeError as error:
                raise ValueError(f"第 {line_number} 行不是有效 JSON") from error
            yield value

for record in read_jsonl(Path("tickets.jsonl")):
    print(record["ticket_id"], record["status"])
```

这里的 `read_jsonl` 是一个生成器函数：每次读一行、解析一行，再用 `yield` 交出一条记录。`with` 在离开缩进块时关闭文件；`encoding="utf-8"` 指定文字编码；`enumerate(..., start=1)` 同时提供从 1 开始的行号。`json.loads` 把一行 JSON 文本变成 Python 字典。当前两条数据会分别打印工单编号和状态。若 JSON 格式有误，异常会指出出错行号，并保留解析器提供的原始原因。

这个教学版本把空白行也视为格式错误，因为空行不是一条 JSON 记录。配套的 `ticketkit` 生产式实现选择跳过空白行，避免文件末尾多余空行导致整批数据读取失败；打开 [data.py](../示例工程/src/ticketkit/data.py) 搜索 `if not line.strip()`，可以看到这个额外边界处理。两种行为是明确的设计选择，不要把它们误认为实现不一致。

在示例工程根目录的 VS Code 终端运行 `..\..\..\.venv\Scripts\python.exe read_jsonl_demo.py`。若运行时报告找不到 `tickets.jsonl`，先用 `Get-Location` 确认终端位置与文件位置一致。

运行后应看到 `T001 open` 和 `T002 closed` 两行。

### 再用工程读取器检查工单字段

上面的小程序只检查每一行是不是有效 JSON；格式正确的数据仍可能缺少工单编号或使用了未知状态。真实工程的 [read_tickets 函数](../示例工程/src/ticketkit/data.py) 还会把字典交给 `parse_ticket` 做字段和状态校验。另存下面的程序为 `check_tickets.py`：

```python
from pathlib import Path
from ticketkit import read_tickets

for ticket in read_tickets(Path("tickets.jsonl")):
    print(ticket.ticket_id, ticket.status)
```

运行命令是 `..\..\..\.venv\Scripts\python.exe check_tickets.py`。正常输出与前一个示例相同。如果删掉第二条工单的 `status` 字段，工程会停止并报告 `invalid ticket at line 2`；停止而不是悄悄跳过坏记录，可以避免错误数据混进统计。若业务确实选择跳过坏行，还必须统计跳过数量和原因。

常见错误：把 JSON 数组格式误当成 JSONL；少逗号或引号；当前工作目录不在示例工程里，导致提示找不到文件；文本编码不匹配。路径报错时先在终端运行 `Get-Location`。

## 6. 提前停止时关闭文件

如果完整读取文件，`for` 会走到末尾，离开 `with`，文件随之关闭。如果只取第一行就停止，生成器还暂停在 `yield` 上，里面的 `with` 也可能仍然打开着。程序不应该依赖“不知道什么时候发生”的垃圾回收来关闭文件。

工程用 `closing` 明确表示“离开代码块时请关闭这个生成器”：

```python
from contextlib import closing
from pathlib import Path
from ticketkit import read_tickets

with closing(read_tickets(Path("tickets.jsonl"))) as tickets:
    first_ticket = next(tickets, None)
    print(first_ticket)
```

`next(tickets, None)` 表示取下一条；如果文件没有工单，就给出 `None` 而不是抛出“没有下一项”的异常。离开 `with closing(...)` 时，生成器的 `close()` 会触发文件清理。

你可以把这个文件处理方式记成一个规则：进入资源使用范围时用 `with`，需要提前停掉生成器时也要明确关闭。资源包括文件、网络连接和锁等稍后需要释放的东西。

## 7. 运行内存对比实验

在 VS Code 终端确认位于示例工程目录，然后运行：

```powershell
..\..\..\.venv\Scripts\python.exe -m ticketkit.benchmark
```

程序分别对 1 万和 10 万条数据测量两种方式：直接流式处理、先转为列表再统计。输出包含 `peak_python_bytes` 和 `elapsed_seconds`。前者是 Python 跟踪到的内存峰值字节数；后者是耗时秒数。

你的数字可能与验证报告不同，因为电脑、系统和后台负载会影响测量。重点看趋势：流式版只保存少量计数时，数据条数增加后额外内存仍应较小；列表版需要保存全部工单，通常会明显增加。这里的 `tracemalloc` 不等于系统任务管理器看到的进程总内存，也不测 GPU 内存。

> [!warning] 做实验时不要背固定数字
> 性能结论要写明测量方式、输入规模和机器环境。一次运行只能说明这一次的结果，不能因此断言所有生成器都比列表快。

## 8. 练习与答案解析

**跟做练习：** 把 `make_numbers(5)` 改为产生 1 到 5，确认总和是 15。

> [!example]- 跟做练习参考答案（先尝试再展开）
> 可以写 `yield number + 1`，也可以让循环从 `range(1, count + 1)` 开始。原来的 `range(5)` 产生 0 到 4，因此总和是 10；边界从 1 开始后才得到 1 到 5，总和为 15。

**独立练习：** 逐个读取 100 张工单，统计 open 和 closed 两种状态，不要创建存放 100 张工单的列表。判断标准：结果正确，且代码没有把输入转换为 `list`。

> [!example]- 独立练习参考答案与解析（先完成再展开）
> ```python
> from ticketkit import generated_tickets
>
> counts = {"open": 0, "closed": 0}
> for ticket in generated_tickets(100):
>     counts[ticket.status] += 1
> print(counts)
> ```
> 输入逐张产生，没有先转成列表。100 是偶数，两种状态交替出现，预期为 `{'open': 50, 'closed': 50}`。对照示例工程的 `summarize`，看看它怎样接收同样的生成器。

**迁移练习：** 将输入换成商品记录，统计不同价格区间的商品数。解释如果保存每个商品的全部详情，内存是否仍固定。

使用价格为整数元且非负的五件商品：`0、99、100、199、200`。区间约定为低价 `[0,100)`、中价 `[100,200)`、高价 `[200,+∞)`；方括号表示包含边界，圆括号表示不含边界。先在纸上判断 100 和 200 属于哪一组。另建 `product_counts.py`，用生成器逐件提供商品，统计器只保留三个计数。

完成判断：结果为低价 2、中价 2、高价 1；空输入各为 0；负价格应清楚报错；统计过程没有把商品保存进列表。提示：使用 `if/elif/else` 依次判断互不重叠的区间，`elif` 表示前面的条件不成立时再检查这一条件。

> [!example]- 迁移练习参考答案与解析
> ```python
> def generate_products():
>     for price_yuan in (0, 99, 100, 199, 200):
>         yield {"price_yuan": price_yuan}
>
> def count_price_ranges(products):
>     counts = {"low": 0, "medium": 0, "high": 0}
>     for product in products:
>         price_yuan = product["price_yuan"]
>         if type(price_yuan) is not int or price_yuan < 0:
>             raise ValueError("价格必须为非负整数元")
>         if price_yuan < 100:
>             counts["low"] += 1
>         elif price_yuan < 200:
>             counts["medium"] += 1
>         else:
>             counts["high"] += 1
>     return counts
>
> print(count_price_ranges(generate_products()))
> print(count_price_ranges(iter(())))
> ```
> 在本单元示例工程运行 `..\..\..\.venv\Scripts\python.exe product_counts.py`。依次输出 `{'low': 2, 'medium': 2, 'high': 1}`、`{'low': 0, 'medium': 0, 'high': 0}`。圆括号构造元组，`()` 是空元组，`iter(())` 创建没有记录的迭代器。五个价格只是固定的小样本，统计器不会保存每件商品。
>
> `type(value) is int` 检查恰为整数类型，连布尔值也拒绝；`or` 表示任一条件满足即报错，若左侧成立则不再计算右侧。`elif price_yuan < 200` 已隐含价格至少为 100，因为前面的 `<100` 不成立。输入缺少字段会 KeyError，本题规定每条必须有 `price_yuan`，尚未设计完整导入校验。
>
> 再将生成器中的 99 改为 −1，重新运行，应报上述 ValueError，且本次第一条统计结果不会打印，因为函数尚未返回。这是预期失败；改回后再继续。100 属于中价、200 属于高价，不能同时落入两组。
>
> 若另建字典保存所有商品详情，其大小仍随商品数增加。当前统计只保留三个类别的计数，没有按记录数增长的详情集合；但整数计数本身的字节数也会随数值极大而增长，不能把“固定三个计数器”说成任意规模严格固定字节。真实货币若含小数，可另约定使用整数分，本题无需引入浮点金额。

## 9. 本讲小结

- 列表适合需要保存并反复访问的一组数据；迭代器适合逐项获取。
- 生成器用 `yield` 在需要时产生数据，函数会暂停并在下次继续。
- 流式输入可以减少同时保存在内存中的记录数量，但下游仍可能把数据全部保存起来。
- `with` 负责资源的进入和退出；提前停止生成器时用 `closing` 确保文件关闭。
- 实验记录趋势、口径和环境，不把某台电脑的数值当成普遍保证。
