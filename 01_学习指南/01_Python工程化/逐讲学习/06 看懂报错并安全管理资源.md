## 1. 什么是异常

异常是 Python 在程序无法按当前方式继续时发出的错误信号。比如把文字除以数字、打开不存在的文件、从字典里读取不存在的键，都可能产生异常。

```python
number = int("十二")
print(number)
```

`int` 负责把文字转换为整数；因为“十二”不是这种转换能识别的数字文本，Python 会抛出 `ValueError` 并停止当前路径。异常信息会指出出错类型和位置，是排查问题的线索。

异常不总是程序员写错。文件损坏、服务暂时不可用、输入缺少字段也可能是正常运行环境中的失败。关键是判断哪一层知道如何处理它。

## 2. try、except、else、finally

`try` 把可能失败的操作括起来；匹配的 `except` 决定遇到这种错误要怎样回应；`else` 只在没有错误时运行；`finally` 无论成功失败都会运行，常用于清理。

```python
text = "12"
try:
    count = int(text)
except ValueError:
    print("请输入数字")
else:
    print(f"转换成功：{count}")
finally:
    print("转换步骤结束")
```

因为 `"12"` 能转换，结果为“转换成功：12”，然后打印“转换步骤结束”。把 `text` 改成 `"十二"`，会进入 `except`，不会进入 `else`，但仍会进入 `finally`。

只捕获你知道如何处理的错误。例如读取数字时捕获 `ValueError` 有明确含义；写一个空的 `except:` 会把键盘中断等各种错误也吞掉，让问题更难发现。

> [!warning] 不要在 finally 里随意 return
> `finally` 负责最后的清理。如果它又返回另一个值，可能覆盖原来的返回结果；如果它抛出新异常，也可能遮住原本正在处理的异常。

## 3. 抛出自己的错误

当输入违反程序规则时，可以主动用 `raise` 发出错误。示例工程定义了 `DataError`，意思是“数据不能按本项目的规则解释”。

```python
class DataError(ValueError):
    pass

def require_status(status):
    if status not in {"open", "closed"}:
        raise DataError("status 必须是 open 或 closed")
    return status
```

`class DataError(ValueError)` 定义一种更具体的错误，它仍属于值不合法的错误。函数发现状态不合法就 `raise`；调用者可以专门捕获 `DataError`，也可以让它继续往上报告。

## 4. 异常链：增加上下文但保留原因

读文件时，底层 JSON 解析器知道“哪一个字符无法解析”，但它不一定知道这是文件的第几行。数据层知道行号，于是可以补充业务语境，同时保留底层错误。下面是一段可独立运行的最小示例：

```python
import json

class DataError(ValueError):
    pass

def parse_json_line(line: str, line_number: int):
    try:
        value = json.loads(line)
    except json.JSONDecodeError as error:
        raise DataError(f"第 {line_number} 行不是有效 JSON") from error
    return value

print(parse_json_line('{"status": "open"}', 1))
```

运行后会打印 `{'status': 'open'}`。若把 JSON 文本改成不完整的 `'{"status":'`，函数会抛出 `DataError`，说明行号；`from error` 把原始解析异常连接到新的 `DataError` 上。这样报错既告诉我们文件的行号，也保留 JSON 解析失败的技术原因。这种“一个错误带着它的原因”叫异常链。

在 `except` 中只写 `raise DataError("数据错了")`，Python通常仍会保留隐式异常上下文；`raise ... from error` 则明确标出新异常由哪个原始异常引起。如果日志只记录新异常的文字，没有记录异常链，排查者仍可能看不到底层原因。示例工程只补行号并显式保留技术原因，不把整行敏感数据放进错误文字。

## 5. with 怎样保证资源清理

文件需要打开，也需要关闭。如果中间发生异常，手工调用 `close()` 很容易被跳过。`with` 把进入和退出过程联系起来，离开代码块时会执行清理：

```python
from pathlib import Path

path = Path("notes.txt")
with path.open(encoding="utf-8") as stream:
    first_line = stream.readline()

print(first_line)
```

`path.open(...)` 打开文件并返回文件对象；`as stream` 给这个对象起一个临时名字；缩进块结束后，Python 会关闭文件，即使读取时发生异常也一样。

`with` 本身不会自动吞掉所有异常。普通文件上下文管理器会做清理，然后让异常继续向外传递。上下文管理器可以选择抑制异常，但那是它的明确行为，不能从 `with` 这个词推断。

### 上下文管理器的进入与退出

`with manager as value` 可以粗略拆成两步：进入时调用管理器的 `__enter__()`，把返回值交给 `value`；离开时调用 `__exit__()`。实际语法还会处理异常信息，所以平时优先使用 `with`，不必手工调用这两个特殊方法。

如果需要定义“进入时计时、离开时写日志”，可以用 `contextmanager` 把生成器转换成上下文管理器。进入准备写在 `yield` 前，调用者的代码在 `yield` 处运行。只把清理写在 `yield` 后，块内异常可能使它被跳过；希望正常结束和异常结束都执行，应把 `yield` 放在 `try` 中、清理放在 `finally` 中。示例工程的 `timed_block` 使用这个结构。这里的清理承诺以成功进入和正常的Python退出／异常展开为前提，不能用于保证进程被强制终止后的清理。

```python
from ticketkit.resilience import timed_block

try:
    with timed_block("parse"):
        raise ValueError("演示错误")
except ValueError:
    print("调用者仍然收到了 ValueError")
```

`timed_block` 会记录失败堆栈并重新抛出异常，因此外层的 `except` 仍能收到它。日志处理和异常处理各司其职：记录不等于处理，打了日志不代表程序就能安全继续。

## 6. 请求范围与 ContextVar

日志常常需要知道当前操作属于哪个请求。最简单的办法是把 `request_id` 作为参数传给每一层函数，但层数多时会让许多函数都带着它。

`ContextVar` 是 Python 为当前执行上下文保存值的工具；在异步任务之间，它可以提供比普通全局变量更合适的隔离。示例工程提供 `request_scope("task-001")`：进入范围后，日志会带这个请求编号；离开时恢复之前的值。

```python
from ticketkit.observability import request_scope

with request_scope("task-001"):
    # 在这里运行的代码会使用 task-001
    pass
# 离开后恢复进入前的请求编号
```

它适合保存当前请求这样的上下文，不是数据库，也不能让多个进程共享数据。忘记恢复上下文会让下一次操作带上错误编号，因此示例使用 `finally` 保证恢复。

## 7. 本讲练习

**跟做：** 把 `int("十二")` 改为 `int("12")`，说明输出为什么经过 `else`。再改回“十二”，说明 `finally` 为什么仍执行。

**独立：** 编写 `parse_count(text)`。输入可转换为 0 或正整数时返回整数；输入无法转换或是负数时抛出 `ValueError`。不要捕获所有异常。

> [!example]- 独立练习参考答案与解析（先完成再展开）
> ```python
> def parse_count(text: str) -> int:
>     count = int(text)
>     if count < 0:
>         raise ValueError("数量不能为负数")
>     return count
> ```
> `int(text)` 已经会在文字不是整数时抛 `ValueError`，所以不必再捕获后无条件重抛。负数虽是合法整数，却不符合本函数的业务规则，因此单独检查。可分别用 `"0"`、`"3"`、`"-1"` 和 `"abc"` 检查四种情况。

**迁移：** 把解析失败转换成 `DataError`，错误信息包含记录行号，并用 `from` 保留原始异常。完成标准是调用者能读到行号，调试信息仍包含底层解析原因。

## 8. 常见问题

- **为什么我写了 except 仍然报错？** 可能捕获的异常类型不匹配。读错误最后一行的异常名称，再决定要捕获什么。
- **加了日志之后为什么程序还是停止？** 日志只是记录。要继续运行必须在合适层级处理异常，或明确接受它继续抛出。
- **with 里的变量离开后还能用吗？** 有些对象仍可访问，但文件已经关闭。应把文件读取结果保存下来，而不是离开后继续读文件对象。
- **为什么要写 `from error`？** 它保留根因，让人既看得懂业务上下文，也能追查技术失败位置。

## 9. 本讲小结

- 异常是错误沿调用层级传递的信号；只捕获自己知道如何处理的错误。
- `finally` 适合清理；`with` 把资源的打开与关闭绑定起来。
- `raise ... from ...` 补充上下文，同时保留原始原因。
- 日志记录错误，错误处理决定程序下一步；两者不能互相替代。
- 请求上下文需要在退出时恢复，避免污染后续任务。
