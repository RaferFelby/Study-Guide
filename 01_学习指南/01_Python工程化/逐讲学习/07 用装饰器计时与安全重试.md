## 1. 函数也是一种值

我们常把数字、文字赋给变量。函数也可以赋给变量、传给另一个函数：

```python
def say_hello():
    print("你好")

action = say_hello
action()
```

这里没有括号的 `say_hello` 表示“函数本身”；`say_hello()` 才表示“现在运行函数”。`action` 现在指向同一个函数，所以调用 `action()` 也会打印你好。

这种能力让我们可以写一个“外层函数”，接收另一个函数并在前后增加行为，例如计时、日志或重试。

## 2. 闭包：函数记住创建时的数据

内部函数可以使用外部函数里的变量。即使外层函数已经结束，返回的内部函数仍能记住那个变量，这种组合叫闭包。

```python
def make_counter():
    count = 0

    def next_number():
        nonlocal count
        count += 1
        return count

    return next_number

counter = make_counter()
print(counter())
print(counter())
```

`make_counter` 每次创建一份 `count` 和一个内部函数。`return next_number` 返回函数本身，没有立即执行它。`nonlocal count` 告诉 Python：接下来要修改的是外层函数中的 `count`，不是创建一个新的同名局部变量。结果依次为 1、2，因为这个函数记住了上次的数字。

闭包适合保存一份小范围的配置或状态。它不是数据库，也不是自动线程安全的共享存储。若同一闭包被多个线程同时更新状态，需要另外考虑同步。

## 3. 装饰器最简单的形状

装饰器是接收一个函数、返回另一个函数的函数。被返回的新函数可以在运行原函数之前或之后增加行为。

```python
def announce(func):
    def wrapped():
        print("开始")
        result = func()
        print("结束")
        return result
    return wrapped

def greet():
    print("你好")

greet = announce(greet)
greet()
```

输出顺序是“开始、你好、结束”。`func` 是原来的 `greet`；`wrapped` 负责包住它；`result = func()` 实际运行原函数；最后把结果交回调用者。此例的函数没有参数，为了讲清过程先从最简单的情况开始。

Python 提供 `@` 语法来简写这项赋值：

```python
@announce
def greet():
    print("你好")
```

它等价于先定义 `greet`，再执行 `greet = announce(greet)`。

真实项目里的函数通常有参数和返回值。`functools.wraps` 可以让包装后的函数保留原函数的名称和说明；`ParamSpec`、`TypeVar` 则让 mypy 知道装饰前后的参数与返回类型仍一致。阅读 [resilience.py](../示例工程/src/ticketkit/resilience.py) 时看到这些名字，先知道它们负责“保留函数信息和类型”即可，不需要现在自己重新实现类型系统。

## 4. 给装饰器增加配置

重试次数和等待时间需要按不同场景配置，因此会看到 `@retry(attempts=3)`。这比 `@announce` 多一层：先用参数创建装饰器，再用装饰器包住目标函数。

```python
def repeat(times):
    def decorate(func):
        def wrapped():
            for _ in range(times):
                result = func()
            return result
        return wrapped
    return decorate

@repeat(times=3)
def say_ping():
    print("ping")
```

这里 `repeat(times=3)` 先产生 `decorate`；`decorate(say_ping)` 再产生 `wrapped`。最终 `say_ping()` 实际指向 `wrapped()`，每次调用会运行原函数三次。这个例子只是展示语法，它不会判断失败，实际不要用它重复有副作用的操作。

带参数装饰器常见三层名称：外层负责接收策略参数，中间层接收目标函数，最内层在调用时包住原函数。看代码时可以从最里面开始读：目标函数真正运行在哪儿？外层参数保存在哪里？发生异常后流程到哪里？

## 5. 为什么需要重试

有些失败只是暂时的，例如短暂网络中断；等一会再试可能成功。另一些失败是确定性的，例如密码错误、没有权限或输入格式不对，重复请求不会让它们自动变好。

有限重试至少要说清四件事：

1. 哪些异常可以重试。
2. 总共最多调用多少次。
3. 两次调用之间等待多久。
4. 最终失败时怎样把错误交给调用者。

示例工程定义 `TransientError` 表示可暂时恢复的问题，并默认只重试这种错误。策略简化代码如下：

```python
for attempt in range(1, attempts + 1):
    try:
        return func()
    except TransientError:
        if attempt == attempts:
            raise
        sleep(delay)
        delay = min(delay * 2, max_delay)
```

`range(1, attempts + 1)` 让次数从 1 开始，并包括最后的 `attempts`。例如 `attempts=3` 最多调用三次，即第一次调用加两次重试。每次可重试失败后等待，再将等待时间翻倍，但不超过 `max_delay`。到最后一次仍失败时，裸 `raise` 把当前异常重新抛出。

等待时间逐次加长叫指数退避。比如基础等待为 0.2 秒、上限为 0.3 秒，等待序列是 0.2 秒、0.3 秒。延长间隔可以减少对正在恢复的服务继续施压。生产服务还常加随机抖动，避免许多客户端同时重试；那属于后续可靠性内容。

### 重试到底安全不安全

读取操作通常比较容易重复。写入、扣款、发邮件等操作可能有副作用。假设请求已经到达服务器并成功扣款，只是回复途中网络断开；客户端看到超时后再试一次，就可能扣两次。超时表示“我没有及时收到结果”，不必然表示“服务器没有完成操作”。

对有副作用的操作，通常要有幂等键、操作状态查询、去重机制或人工确认，才能安全重试。初学时先记住：只重试明确的暂时错误；次数有限；不要默认任意函数都能重复执行。

### 用成功与失败例子读懂策略

```python
from ticketkit import TransientError, retry

calls = 0

@retry(attempts=3, base_delay=0, max_delay=0)
def load_value() -> int:
    global calls
    calls += 1
    if calls < 3:
        raise TransientError("暂时不可用")
    return 42

print(load_value())
print(calls)
```

将等待设置为 0 是为了教学演示不需要真的等待。前两次抛出可重试异常，第三次返回 42，所以输出为 42 和 3。`global calls` 表示函数会修改模块最外层定义的 `calls`。因为 `calls += 1` 会给变量重新赋值，没有 `global` 时 Python 会把它当作局部变量，读取时会触发 `UnboundLocalError`。这里用 `global` 是为了让最小例子容易逐行跟读；示例工程使用闭包里的 `nonlocal`，避免把计数状态放在模块级。

若把 `TransientError` 换成 `ValueError`，它不会被默认捕获，程序会立刻把错误交给调用者。这是预期行为，不是漏重试。

## 6. 装饰器顺序会改变计时含义

示例工程这样组合计时与重试：

```python
import logging
from ticketkit import retry, timed

logging.basicConfig(level=logging.INFO)

@timed
@retry(attempts=3, base_delay=0, max_delay=0)
def load_summary() -> int:
    return 42

print(load_summary())
```

在示例工程目录运行这段代码，先打印 `42`，并在日志中看到 `load_summary` 的耗时。装饰器从靠近函数的那一层开始应用。它等价于 `timed(retry(attempts=3, base_delay=0, max_delay=0)(load_summary))`。因此 `timed` 包住完整的重试过程，测量值包括失败调用和等待时间。本例第一次就成功；前一节的例子展示了失败后重试。

如果顺序换过来，可能变成每次尝试各自计时。选择哪一种取决于你想知道“整个操作花了多久”还是“每一次尝试花了多久”。使用计时结果前，先说清计时边界。

同步装饰器假设目标函数运行后立即返回结果，因此不要直接把它套在 `async def` 上。异步函数调用通常先返回一个协程对象；普通同步计时可能只量到创建对象的时间，而不是等待操作完成的时间。

## 7. 在不等待的情况下检查退避

真正等待数秒会拖慢测试。示例 `retry` 允许传入一个替代的 `sleep` 函数。你可以给它一个只记录秒数、不暂停的函数：

```python
from ticketkit import TransientError, retry

calls = 0
waits = []

def record_wait(seconds):
    waits.append(seconds)

@retry(attempts=3, base_delay=0.2, max_delay=0.3, sleep=record_wait)
def load_value():
    global calls
    calls += 1
    if calls < 3:
        raise TransientError("暂时不可用")
    return 42

print(load_value())
print(calls)
print(waits)
```

在示例工程目录运行后，结果依次是 `42`、`3` 和 `[0.2, 0.3]`。当基础等待为 0.2、上限为 0.3、共尝试三次时，只等待两次，因为最终一次调用之后没有下一次调用。`global calls` 仍是在修改模块级计数器；运行多个示例或测试时要重置它，避免上一个调用留下的状态影响下一个。传入的 `record_wait` 会记录等待时长而不真的暂停，所以练习很快就能完成。

这种“把等待动作作为参数传入”的方式叫依赖注入：外部提供具体动作，算法内部只负责调用。它让正式运行可以真的等待，测试可以立刻记录。

## 8. 练习与答案解析

**跟做：** 把 `attempts` 改为 2，目标函数前两次都失败。解释为什么只等待一次，并说明最终异常会不会消失。

**独立：** 为一个只重试 `TransientError` 的函数记录尝试次数与等待序列。给定 `base_delay=0.2`、`max_delay=0.3`、`attempts=3`，目标函数第三次成功。完成标准：结果正确、调用三次、等待两次，普通 `ValueError` 不被重试。

> [!example]- 独立练习参考结果与排错（先完成再展开）
> 结果应为 `42`，调用次数为 `3`，等待列表为 `[0.2, 0.3]`。第一次失败后等 0.2 秒，第二次失败后等到上限 0.3 秒，第三次成功后不再等待。若等待列表有三项，检查最后一次调用后是否又执行了 `sleep`；若 `ValueError` 也触发重试，检查捕获范围是否过宽。

**迁移：** 设计一个查询工单的重试策略，并设计一个“更新工单状态”的策略。解释更新请求超时时为什么先查询结果更安全。

## 9. 常见错误

- 把 `attempts=3` 理解成“三次重试再加首次”，实际此实现含首次一共三次调用。
- 捕获所有 `Exception`，导致配置错误、权限错误也重复发生。
- 无限重试，没有上限，程序可能一直挂住。
- 每次失败后都等待，包括最后一次；最后一次之后已经不会再调用。
- 把同步重试装饰器用于异步函数。
- 重试写入操作，却没有考虑第一次可能已经成功。
