## 学完后你会做到什么

你会区分 format、lint、测试和 CI；能在本地运行 Ruff；理解 pre-commit 为什么能在提交前阻止一部分问题；能读懂示例工程的 GitHub Actions 工作流。自动检查的目标是减少重复人工检查，不是替代思考。

## 1. 四种检查各自负责什么

- **format（格式化）：** 统一缩进、换行和引号等排版，让代码容易阅读。它通常会直接改文件，或在检查模式下报告需要修改的文件。
- **lint（代码检查）：** 根据规则发现未使用导入、明显错误和不一致写法。它通常只报告问题，不替你判断业务逻辑。
- **测试：** 运行程序的一部分并断言行为是否符合预期。
- **CI（持续集成）：** 在远程平台的干净环境中自动运行这些检查，避免“我本机能过”成为唯一证据。

它们解决的问题不同：格式不好看不等于业务错；测试通过也不代表没有未使用导入。常见顺序是 format → lint → test，但具体项目可以调整。

## 2. 在本地运行 Ruff

示例工程的 `pyproject.toml` 已配置目标 Python 版本和规则。运行：

```powershell
..\..\..\.venv\Scripts\python.exe -m ruff check .
..\..\..\.venv\Scripts\python.exe -m ruff format --check .
```

第一条检查 lint；第二条只检查格式，不修改文件。成功时会返回命令提示符而没有错误，退出码为 0。要让 Ruff 自动整理格式，可运行：

```powershell
..\..\..\.venv\Scripts\python.exe -m ruff format .
```

执行自动修改前先查看编辑器中的改动；格式化通常安全，但仍应把变化纳入自己的代码审查。

## 3. pre-commit 做了什么

根目录的 `.pre-commit-config.yaml` 指定了 Ruff 的提交钩子。pre-commit 是一个在 Git 提交前运行检查的工具；它和 Ruff 已列入根目录共享环境的开发依赖。第一次使用时：

```powershell
..\..\..\.venv\Scripts\python.exe -m pre_commit install
..\..\..\.venv\Scripts\python.exe -m pre_commit run --all-files
```

`install` 会把钩子登记到当前 Git 仓库；以后执行提交时，检查失败就会阻止提交。`--all-files` 用于第一次检查已有文件。若当前目录不是 Git 仓库，先在自己的练习仓库中操作；不要为了运行这一项删除现有文件或历史。

pre-commit 不是 CI 的替代品：它依赖开发者本机愿意运行，而 CI 在远程干净环境再次检查。两者应使用相近规则。

## 4. 读懂 CI 工作流

在 VS Code 中，从仓库根目录打开 `.github/workflows/quality.yml`。它做的事情按顺序是：

1. 在 push 或 pull request 事件发生时启动。
2. 使用 Ubuntu 和 Python 3.11 的干净环境。
3. 把工作目录切换到示例工程。
4. 安装开发依赖，再安装当前示例工程。
5. 运行 pytest、Ruff lint 和格式检查。

安装当前工程使用 `python -m pip install --no-build-isolation -e .`，与本单元 README 中的本地安装步骤一致。这里的 `.` 是 CI 已切换到的示例工程目录；`-e` 表示以可编辑方式安装，让 Python 能导入 `src/reprokit` 中的代码；`--no-build-isolation` 表示使用刚才准备的环境和构建工具。开发依赖中的 pytest 等工具能运行测试，但安装工具不会自动把当前工程安装进去。

CI 的关键价值是环境相对干净，能发现遗漏依赖、路径大小写错误和“本地安装过某工具所以没问题”等问题。工作流文件本身也是代码，应像其他配置一样被审查。

## 5. 如何处理检查失败

看到失败时按顺序做：

1. 先读失败命令和文件行号，不要只看最后一句红色文字。
2. 判断是格式、lint、测试还是环境/依赖失败。
3. 在本地单独重跑失败命令，缩小范围。
4. 修复原因，再运行完整检查。
5. 若是规则不适合项目，先说明理由再修改配置，不要用忽略规则掩盖不理解的问题。

例如测试失败应先看断言实际值；Ruff 报未使用导入则删除导入或确认它是否真的需要。不同类型问题的修复路径不同。

## 6. 动手操作

1. 运行 `ruff check .` 和 `ruff format --check .`，记录结果。
2. 在一个 Python 文件中故意增加未使用导入，观察 lint 报告，再修复。
3. 故意增加多余空格，运行格式检查，再用 `ruff format` 修复。
4. 阅读 CI 文件，用自己的话写出它在什么事件、什么 Python 版本、哪个目录中运行哪些命令。

## 7. 常见错误

- **只在编辑器里看到绿色波浪线就当作检查通过：** 编辑器扩展与项目 CI 可能版本不同，仍要运行项目命令。
- **format 与 lint 混为一谈：** 一个主要统一排版，一个主要报告代码问题。
- **直接忽略所有 lint：** 这会降低自动检查价值；先理解规则和真实误报。
- **CI 找不到文件：** 常见原因是工作目录或相对路径写错，检查 workflow 的 `working-directory`。
- **CI 报 `ModuleNotFoundError: No module named 'reprokit'`：** 先确认工作目录是本单元示例工程，再检查测试前是否执行了安装当前工程的命令。不要只安装 pytest 后就运行测试；本地已经装过的包不会自动出现在 CI 的干净环境中。

## 8. 练习与答案解析

**跟做：** 在示例工程运行三条检查命令并记录退出结果。

**独立：** 在自己的小项目中写一个最小 CI 任务，让它安装依赖并运行测试。

**迁移：** 为 CI 增加“实验命令能生成结果文件”的检查；思考如何避免把生成物污染源码仓库。

> [!example]- 参考思路（先完成再展开）
> CI 需要先切到正确目录，再安装依赖，最后运行测试和质量工具。实验结果可写入临时目录，并只断言命令成功和关键字段存在；不要把带环境路径的输出直接提交。

完成标准：能解释四种检查的职责；能独立运行本地 lint 和 format；能从 CI 文件中定位依赖安装、测试和格式检查步骤。

## 本讲小结

format 统一外观，lint 发现代码问题，测试检查行为，CI 在干净环境重复这些检查。下一讲把“能重复运行代码”进一步扩展为“能复现一次实验结果”。
