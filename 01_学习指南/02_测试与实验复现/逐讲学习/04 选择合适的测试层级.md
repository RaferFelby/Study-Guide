## 学完后你会做到什么

你会用“范围、依赖、速度和定位难度”区分单元测试、集成测试和端到端测试，并为一个小项目选择合理组合。你不会再把“用了 pytest”误认为“已经做了完整测试”。

## 1. 三种层级先用一句话记住

| 层级 | 主要检查 | 依赖 | 速度与定位 |
|---|---|---|---|
| 单元测试 | 一个函数或小组件的规则 | 尽量替换外部依赖 | 快，失败原因通常清楚 |
| 集成测试 | 两个或多个真实组件如何连接 | 使用真实文件、数据库或本地适配器 | 中等，能发现连接问题 |
| 端到端测试 | 从用户入口到最终结果的完整路径 | 尽量接近真实系统 | 慢，失败定位最难 |

“单元”不是固定大小的文件，而是你选择隔离检查的行为边界；“真实组件”也不等于一定要访问生产服务，可以使用本地临时目录、内存数据库或测试服务。

## 2. 单元测试：先把规则测稳

`count_statuses`、`parse_tool_response` 都适合单元测试：输入可以直接构造，输出和异常明确，不需要网络。单元测试数量通常最多，因为它们运行快，改代码后可以频繁执行。

单元测试的边界是：不需要证明 HTTP 客户端、数据库驱动和你的业务规则同时能连接起来。若把所有依赖都 mock 掉，测试可能很稳定，却漏掉真实字段名、序列化格式或连接配置错误。

## 3. 集成测试：检查组件之间的真实连接

本工程的实验写入 JSON 文件。可以写一条集成测试，检查实验函数产出的字典经过 JSON 写入和读取后仍保留关键字段：

```python
import json

from reprokit.experiment import run


def test_experiment_result_can_be_saved_and_loaded(tmp_path) -> None:
    path = tmp_path / "run.json"
    path.write_text(json.dumps(run(7, "demo-v1")), encoding="utf-8")

    saved = json.loads(path.read_text(encoding="utf-8"))
    assert saved["config"]["seed"] == 7
    assert saved["data_version"] == "demo-v1"
```

这里 `run` 和文件系统一起参与测试；`tmp_path` 是 pytest 提供的临时目录，测试结束后由 pytest 管理清理。这个测试不会访问真实云存储，但比只测 `run()` 多检查了一条“结果能保存并重新读回”的集成边界。

## 4. 端到端测试：验证完整用户路径

端到端测试可以从命令行入口启动实验，检查结果文件出现且内容可读。它关心的是用户动作，不关心中间用了哪个函数：

```text
执行命令 → 解析参数 → 运行实验 → 创建目录 → 写入结果 → 读取主要字段
```

端到端测试很有价值，但数量应少。若它失败，你可能不知道是参数解析、业务计算还是文件权限出了问题，所以先用单元测试和集成测试定位，再用少量端到端测试确认整条路径。

## 5. 如何决定测试放哪一层

问自己四个问题：

1. 这个测试只想验证一个明确规则吗？是的话优先单元测试。
2. 是否要验证两个真实模块之间的格式或文件/数据库连接？是的话加集成测试。
3. 是否要模拟用户从入口开始的完整操作？是的话考虑端到端测试。
4. 测试失败后，维护者能否快速知道要修哪里？如果不能，先拆成更小的测试。

同一个重要行为可以有多个层级的证据，但不要机械重复。比如“非法 JSON 被拒绝”用单元测试就足够；“命令行生成结果文件”适合再加一条端到端测试。

## 6. 覆盖率该怎样理解

覆盖率表示运行测试时，源码中有多少比例被执行到。它能提醒你“哪些行从未走过”，但不能说明断言是否有意义。执行了错误分支却没有检查输出，覆盖率可能很高，测试仍然很弱。

可以安装 coverage 插件后运行：

```powershell
..\..\..\.venv\Scripts\python.exe -m pytest --cov=reprokit --cov-report=term-missing
```

报告中的缺失行是补测试的线索，不是必须追求的数字。优先覆盖业务规则、失败恢复和数据边界；不要为了百分比写只执行代码却不验证行为的测试。

## 7. 动手操作

1. 在 `tests/test_experiment.py` 增加保存/读取 JSON 的集成测试。
2. 列出本工程的一条单元边界、一条集成边界和一条端到端边界。
3. 任选一个函数运行覆盖率（没有安装插件时先记录“尚未安装”并继续其他练习）。
4. 找到一个未覆盖的失败分支，补一条有明确断言的测试。

## 8. 常见错误

- **所有测试都 mock：** 可能漏掉模块之间真实的字段和序列化问题。
- **所有测试都端到端：** 运行慢，失败时很难定位。
- **把覆盖率当质量分数：** 覆盖了代码行不等于检查了正确行为。
- **集成测试使用生产数据：** 容易泄露或修改真实数据；优先使用隔离的测试资源。

## 9. 练习与答案解析

**跟做：** 把“JSON 能写入再读出”的示例改成测试，运行它。

**独立：** 为 `fetch_many` 写一条单元测试，再设计一条集成测试，说明两者的真实依赖差异。

**迁移：** 写出 `reprokit.experiment` 的端到端验收步骤，但先不实现：明确命令、输入、输出文件和最小断言。

> [!example]- 参考思路（先完成再展开）
> 单元测试直接传入列表或 Fake；集成测试让实验和 JSON 文件真实协作；端到端测试从 `python -m reprokit.experiment` 开始并检查生成文件。三者都要有断言，不能只看命令没有报错。

完成标准：能为一个测试选择层级并解释理由；能说出覆盖率的用途和限制；能写一条不依赖网络的集成测试。

## 本讲小结

测试层级是不同范围的证据：单元快而精确，集成检查连接，端到端检查用户路径。合理组合比追求某一种测试数量更重要。下一讲把这些检查接到格式、静态检查和提交后的自动流程上。
