## 本讲任务与前置

建立真实或明确模拟的投递记录，区分当前状态、历史转化和反馈。前置是比例、日期和上一讲Counter。投递是实际提交申请，本例五条全部模拟，没有替你发送任何简历，也没有收到真实招聘反馈。

## 快照和漏斗不是一回事

快照记录某观察日每个申请当前处于pending、screen、technical、offer或rejected。pending是尚未得到明确阶段结果；screen是筛选阶段；technical是技术阶段。当前被拒的记录可能之前经过筛选或技术，但没有历史就不知道。

因此当前technical2/5不等于“技术面转化率40%”。漏斗转化需记录每条申请曾进入哪些阶段、时间窗口、渠道、重复申请规则，以及分母是全部提交还是已收到决定。还在等待的不能自动当拒绝；不同观察窗口也不能直接比。

## 最小示例：模拟快照汇总

新建 `lesson_applications.py`：

```python
import json
from pathlib import Path
from career import summarize_applications

records = json.loads(
    (Path(__file__).parent / "fixtures" / "applications.json").read_text(encoding="utf-8")
)
result = summarize_applications(records, "2026-10-11")
print(result["n"], result["stages"])
print(result["pending_days"])
print(result["feedback_counts"])
print(result["priorities"])
```

预期n5，screen1/technical2/rejected1/pending1；A04已等待7天；coding3、project_explanation2；优先两个为coding与project_explanation。字典显示顺序不影响计数，待处理天数从模拟发送日到固定观察日，不是自动提醒或追踪真实招聘者。

## 代码顺序与日期

date.fromisoformat把YYYY-MM-DD变为日期对象，相减得到天数。函数拒绝未来发送日，避免等待负数；唯一ID避免一条重复算两次；未知stage或feedback明确报错。当前实现只接受origin=simulated，专供教材；不能把真实记录塞进去然后删来源校验骗过检查。

真实个人记录可独立建学习表，保留岗位链接/日期、简历版本、渠道、提交状态/时间、每次阶段变化、反馈原文与解释、下一步。只存必要个人数据，别把招聘者联系方式或私密材料上传给无关服务。

## 从反馈到行动，不偷换因果

三条提到coding说明这是本组模拟反馈的重复信号，不能证明所有未录用都因代码水平，更不能预测加练后录用率。反馈可能模糊、选择性或只反映一题；无回复也可能与时间/资格/岗位暂停有关。先保留原说法，再分已知、推断、待证。

挑一到两项重复缺口，设计可观察的改进。例如现场编码：独立完成一个有边界的函数并解释；项目表达：将一个指标连接到日志/分母。下周比较自己的操作和解释质量，不编造招聘结果来证明学习有效。

## 动手与错误排查

建五条模拟记录，保证唯一ID和日期；或只建你的真实数量，不为凑数制造投递。等待状态写未定。日期解析失败用标准格式；stage拼错对照五个允许值；未来日期核观察日是否写错，不随意修改真实提交日。

## 练习与答案

跟做：解释A04七天的计算。独立：五当前阶段为何不能算筛选到技术转化？迁移：设计一个带阶段历史的记录结构，说明每项漏斗分母与未结案如何报告。

> [!example]- 参考答案
> 10月11日减10月4日=7；只是模拟日历差。当前rejected不知道曾经进入哪些阶段，当前technical也可能多次变化；需历史events和统一窗口。可记录submitted/screen_entered/technical_entered/decision时间，再按同一批提交与可观察完成情况汇总，pending独立列出，不默认0成功。

完成判断：记录真实状态与证据，不把快照比例、反馈频次或等待天数写成录用概率。
