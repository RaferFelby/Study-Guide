# 第 1 讲：用结构化日志记录一次任务

## 本讲任务与前置

用户报告“这次又失败了”，我们需要知道哪次、哪一步、什么错误。乱写print能临时看到文字，但难以稳定筛选。本讲把事件写成有字段的日志，学习JSONL与记录边界。前置是字典、json、文件with；不懂with先回单元01资源管理。

## 日志、轨迹和指标先分清

日志是离散事件记录，例如“某工具超时”；轨迹trace把同一次任务的多个步骤串起来；指标metrics把很多任务汇总成数量/比例/分布。它们互相补充：总错误率告诉我们是否异常，trace找到某次调用，日志提供具体错误类别。

结构化日志是字段固定的记录，不只是带标点的自然语言。类似表格的一行，但每行可用JSON对象表达。JSONL的L指lines：一个JSON对象占一行，适合逐行读。它不是一个外层大JSON数组，json.load整份文件可能失败。

## 最小示例：自己写一行

在本单元示例工程新建`lesson_log.py`：

```python
import json
from pathlib import Path

event = {
    "request_id": "request-demo-1",
    "event": "tool_finished",
    "tool": "search_policy",
    "status": "error",
    "error_code": "upstream_timeout",
}
path = Path(__file__).parent / "lesson-event-01.jsonl"
with path.open("x", encoding="utf-8") as stream:
    stream.write(json.dumps(event, ensure_ascii=False) + "\n")
with path.open(encoding="utf-8") as stream:
    for line in stream:
        saved = json.loads(line)
        print(saved["tool"], saved["error_code"])
```

运行共享解释器：`..\..\..\.venv\Scripts\python.exe lesson_log.py`。预期search_policy upstream_timeout，文件出现一行JSON。`x`模式仅创建新文件，已有同名会报FileExistsError；第二次练习改为lesson-event-02.jsonl，避免把旧证据覆盖。

`ensure_ascii=False`保留中文可读字符；`\n`结束一行；json.loads解析这一行。Path(__file__).parent以脚本所在目录为基准，不会因为另一个终端当前目录不同写到未知位置。

## 记录什么，为什么不写全部正文

应记录稳定ID、组件、事件类型、结果类别、模型/工具版本、耗时和必要数量。原始question、模型完整上下文、Authorization、数据库连接串可能含个人信息或秘密，不应默认写入日志。脱敏不等于“打印后用正则随便删几个词”；先选择最小字段更容易检查。

工程telemetry.py对attributes使用白名单和简单标量，禁止新增password/authorization/原始正文键，退出span时再次验证。错误只记录异常类型，不记录可能含凭据的异常消息。白名单不是能识别所有秘密的安全系统：若开发者把秘密填进model字符串，仍是误用，需代码审查和日志权限。

任务ID/run_id关联整次业务，request_id关联一次HTTP尝试；提交后轮询会有多个request_id但同job_id。当前离线工程采用trace_id关联任务，没有真实HTTP请求。不要把这些不同ID全部叫“请求编号”。

## 动手：检查工程输出

在示例工程运行：

```powershell
..\..\..\.venv\Scripts\python.exe demo.py --output-dir report-01
```

`--output-dir`指定一个新报告目录；目录已存在时换report-02。打开baseline-trace.jsonl，找name=tool、status=error、error_type=TimeoutError。它们来自合成超时，不含原始问题或用户凭据。每行有trace_id、span_id、parent_span_id，下一讲解释关系。

先手工数一两个事件，不要直接根据“行数很多”判断系统繁忙：一个任务会产生多个事件，日志行数不是任务数量。

## 常见错误

- JSONDecodeError “Extra data”：你把多行JSONL当一个JSON对象读；逐行loads。
- 文件出现转义乱码：确认UTF-8和ensure_ascii=False；终端显示问题可设置PYTHONIOENCODING。
- 日志没有错误消息就说无法排错：先错误code/type与trace查阶段；需要详细消息时按批准用途去敏后记录，不能无界输出。
- 相同ID关联所有任务：最小示例的固定ID只是教学；真实运行用每次唯一ID，重试/任务ID另保存关系。

## 练习与答案

跟做：写一行JSONL并读回，指出五个字段用途。完成判断：没有任何真实用户名、密码或完整问题正文。

独立：用户ID需要排查时，是直接写邮箱还是写内部关联ID？还需要什么访问限制？

迁移：为“模型调用解析失败”设计一条日志，列模型版本、错误code和trace关系，不把模型原文直接放进去。

> [!example]- 参考答案与解析
> 使用最小必要内部关联ID，必要时受控映射到用户；日志仍需权限、保留期和删除策略，ID并非天然匿名。
>
> 可记录event=model_output_invalid、model/version、error_code=schema_missing_field、trace_id/span_id及输出字节数；原文若确需人工复核另存受控样本，不默认进入普通日志。

能用字段记录离散事件并说明隐私边界，接着把同一次任务的事件组成父子轨迹。
