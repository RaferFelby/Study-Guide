## 本讲任务与前置

读第 4 讲生成的报告，逐层比较 Base 与微调模型，再核对目录变化和工具不可用。需要格式、语义、真实执行与最终答案的区分。计数、分母和比率基础见 [[01_学习指南/07_传统机器学习与数据分析/00 传统机器学习与数据分析学习地图|机器学习评估]]，本讲直接用“成功个数／任务总数”。

完成标准：能给每层写出判定条件和共同分母，能说明宿主拦截贡献；能解释工具执行成功但回答错误，以及工具不可用时正确拒答为什么仍不是完成查询。

## 要解决什么问题：一句成功率会遮住哪一步

模型写出漂亮调用，可能选错工具；工具读到数据，模型可能答旧值。只统计最后答案又无法定位调用错在哪里。我们保留同一任务从动作到答案的全部结果，在多个层次分别计数。

“端到端”是从请求开始，经过模型、宿主、工具、观察，再到正确答案的整条流程。它不只评价模型的一段文字。记录每层不是把一个成功重复算成多次任务，而是观察同一批任务在各检查点的状态。

## 概念与判定：所有层都用同一分母

| 报告键 | 通过条件 |
| --- | --- |
| `format_valid` | 动作能按六 token 允许语法解析 |
| `plan_correct` | 计划属性与请求一致 |
| `tool_correct` | 工具是该属性对应的工具 |
| `argument_correct` | 对象 ID 与请求一致 |
| `semantic_valid` | 计划、工具、参数三项同时正确 |
| `execution_success` | 通过校验后的真实工具调用返回观察 |
| `end_to_end` | 以上流程完成，最终答案严格等于当前观察对应答案 |

每层都除以 `n`，正常集 n=12；不要把工具正确计数除以可解析动作数，然后又与 end_to_end/n 混比。格式失败时三项语义也记不通过。计划／工具／参数三个分项彼此不一定大小有序，但语义交集不会超过任一分项。执行成功不能超过语义有效，最终成功不能超过执行成功。

`tool_calls` 是实际尝试次数，包括调用后工具不可用；它不是成功次数。本例每任务最多一次，语义不符零次，执行故障一次。没有远程调用、无限重试或多步规划，本例只用生成八 token 和一次工具调用约束本地流程，不声称提供真实服务的硬超时保障。

## 最小示例：打印前后计数与故障响应

在本单元示例工程新建 `lesson_05.py`；先完成第 4 讲的 CPU 实验。

```python
import json
from pathlib import Path

with (Path("report-my-cpu-01") / "report.json").open(encoding="utf-8") as file:
    report = json.load(file)
for name, result in report["evaluations"].items():
    normal = result["normal"]
    keys = ("format_valid", "semantic_valid", "execution_success", "end_to_end")
    print(name, normal["n"], [normal[key] for key in keys])
    print("变化目录", result["changed_catalog"]["end_to_end"])
offline = report["evaluations"]["tool_only"]["offline"][0]
print(offline["status"], offline["tool_calls"], offline["answer"])
```

```powershell
..\..\..\.venv\Scripts\python.exe lesson_05.py
```

作者 CPU 预期：Base n=12、四层全 0，变化目录 0；两个微调分支 n=12、四层全 12，变化目录 12。最后为 `unavailable 1 ['refuse', 'unavailable', '<eos>']`。这段只读已保存报告，不重新训练。`.items()` 顺序对应写入的分支；`keys` 是要展示的字段名，列表逐项读取计数，不是新评估逻辑。

## 逐步跟踪一条任务

打开 [evaluation.py](../示例工程/evaluation.py)，从 `run_episode` 阅读。第一步 `generate` 真的运行模型，生成 action；这里没有规则替模型填写工具名或对象。解析失败立即返回 invalid_format。

第二步宿主根据任务声明检查语义，不通过返回 semantic_rejected，保留模型原动作。**此例宿主知道请求的结构化意图和正确对象，有较强的参考检查条件。** 安全执行计数体现模型提案与宿主共同作用，不能把错误调用没执行全部归功于模型权重。真实系统需要自身业务约束和权限验证，通常没有完整答案判定器可直接照搬。

第三步通过校验后调用 `execute_tool`，把返回观察存入结果。第四步把请求+模型原动作+`observation 本次值` 作为第二次输入；生成的 final 必须与本次值一致才计完成。程序不会把最终答案替换成观察，也不会补 `<eos>` 帮模型通过。

## 变化目录：检查是否读本次观察

在 `make_catalog(changed=True)` 中，red 与 blue、small 与 large 交换；请求与对象不变。这样固定旧答案会失败，遵循当前观察的模型仍可通过。作者两个分支各 12/12，提供了本次反事实变化探针的行为证据。

它仍然只有两个值的交换，模板和对象已见过；不能据此证明模型在任意工具返回、长文本或新格式都能可靠取证。完成标准是知道探针改变了什么、哪些因素没变，而不是把“变化目录”直接称为全面泛化测试。

## 工具不可用：拒答与任务成功分开

离线探针给前两条测试请求模拟工具不可用，抛出 `ToolUnavailable`。宿主把 `error unavailable` 输入模型；作者两个分支都生成正确拒答，执行成功和最终成功仍为 False，因为没有查到当前资料。

正确拒答是失败处理行为通过，不是查询任务完成。即使模型此时输出 `final red <eos>`，宿主也不能记 end_to_end=True；没有成功观察就没有完成证据。测试专门检查了这种“故障后假装给答案”的路径，防止评估错误奖励。

## 动手操作与常见错误

在自己的 `report.json` 找 `evaluations→tool_only→normal→details` 的第一条，抄下 action、observation、answer、status 和 tool_calls。再对照 changed_catalog 的同条，观察值与最终答案应随目录变化。不要只看终端摘要。

如果 `execution_success` 大于 `semantic_valid`，检查统计或宿主逻辑是否先执行后校验。若把正确拒答算为最终成功，改为单独报告故障处理，并保留查询失败。若报告中找不到 expected 字段，正常任务按实际 observation 构造严格答案，旧 chat 则单独存 expected，不要混用两种任务结构。改输出格式时要同步判定标准，不仅修改打印。

## 分级练习与答案解析

### 跟做练习：写比率

正常集 12 条，格式 12、语义 10、执行 9、最终 8。写出四层比率。提示：同一个分母。

> [!example]- 参考答案
> 12/12、10/12、9/12、8/12，约为 100%、83.3%、75%、66.7%。若另外计算最终／执行=8/9，要标明它是条件比率，不能冒充端到端成功率。完成标准：写清分母。

### 独立练习：执行了但答错

item-0 的 get_color 返回 blue，final 输出 red。哪些层通过、哪个结果不通过？提示：先假设动作三项都正确。

> [!example]- 参考答案
> 格式、计划、工具、参数、语义、执行均通过；最终 end_to_end 不通过，status=answer_wrong。应检查观察是否进入第二次输入以及模型是否利用它，不是先把工具执行改成失败。完成标准：准确定位最后阶段。

### 迁移练习：拆分模型与宿主贡献

模型经常输出错误对象，但宿主全拦住，因此没有错误外部操作。能否写“模型完全可靠”？写一句准确报告。

> [!example]- 参考答案
> “模型参数提案有错误，宿主语义检查阻止了这些调用；执行边界有效，但模型任务成功率仍受错误提案影响。”本例没有外部操作，真实部署另需验证。完成标准：保留模型错误和宿主拦截两个事实。
