# 第 1 讲：把工具任务拆成计划调用观察与答案

> [!nav] 页面导航
> [[01_学习指南/34_规划与工具使用微调/00 规划与工具使用微调学习地图#学习顺序|单元 34：规划与工具使用微调]] · [[01_学习指南/34_规划与工具使用微调/逐讲学习/02 过滤错误轨迹并构造正确拒答样本|下一讲]]

## 本讲任务与阅读顺序

先理解一次“查 item-0 的颜色”的过程，再运行轨迹，最后把任务改成查大小。你需要列表、字典与函数基础；陌生时先回 [[01_学习指南/01_Python工程化/00 Python 工程化学习地图|Python 学习地图]]。本讲不训练模型，先确定要教给模型什么行为。

完成标准：能把请求、计划、工具名、参数、观察和最终答案分别指出；能解释“工具执行了”为什么不等于“任务完成了”。

## 要解决什么问题

语言模型会生成文字，但“目录中这个物品现在是什么颜色”需要查目录。若只训练它回答 `red`，它可能记住旧值；目录变成蓝色后仍答红色。我们希望它先生成调用，程序真的查目录，再把当前结果放回模型输入，最后生成答案。

这里的“工具”是程序提供的一项明确功能。`get_color` 读取颜色，`get_size` 读取大小，参数 `item-0` 指定对象。“参数”就是告诉工具具体处理哪个对象的输入。工具不会自己猜请求，程序也不会把模型文本当任意 Python 命令运行。

## 概念与直觉：四个阶段

一次轨迹是一次任务从输入到输出的完整记录，像保存操作录像，但实际保存的是结构化字段，并不包含人的思考全过程。

| 阶段 | 本例文本或值 | 谁负责 |
| --- | --- | --- |
| 请求 | `query color item-0 case-00` | 数据提供者 |
| 简短计划 | `plan color` | 训练时提供示范，推理时由模型生成 |
| 调用 | `call get_color item-0 <eos>` | 模型生成，宿主程序先校验 |
| 观察 | `red` | 工具读取目录返回 |
| 答案 | `final red <eos>` | 模型读到观察后生成 |

`query` 表示查询，`color` 是颜色，`case-00` 是案例编号；编号方便分组，不代表物品编号。`<eos>` 是回答结束标记，一个独立 token。token 是本例模型认识的一小段文本；这里手工把整个 `item-0` 当一个 token，真实 tokenizer 往往会切得不同。

计划在本例只选属性，并没有多步依赖。它让“要查颜色”和“选择 get_color”能分别检查；重复并不神奇地增加推理能力。自然语言模型的多步规划需要更丰富的任务和验证。

[ReAct 原论文](https://arxiv.org/abs/2210.03629)讨论推理记录、动作和环境反馈相互衔接。我们借用动作后读取反馈的结构，用短标签作为可检查的教学计划，没有抽取隐藏思维链，也没有复现论文的完整实验。[Toolformer 原论文](https://arxiv.org/abs/2302.04761)研究怎样学会选择 API 调用及利用结果；本单元使用人工规则构造的监督样本，不是它的自动数据发现流程。

## 最小示例：先查看一条正确轨迹

在 VS Code 的资源管理器展开 `01_学习指南/34_规划与工具使用微调/示例工程`。右键此目录选择在集成终端打开；使用 PowerShell。新建 `lesson_01.py`，保存下面完整代码。源码入口见 [[01_学习指南/34_规划与工具使用微调/示例工程/README|代码导航]]。

```python
from data import make_tasks, make_trace
from tools import parse_call, semantic_checks

task = make_tasks("train")[0]
trace = make_trace(task)
print(task["prompt"])
print(trace["action"])
print(trace["observation"], trace["answer"])
call = parse_call(trace["action"])
print(semantic_checks(call, task))
```

在该工程目录运行：

```powershell
..\..\..\.venv\Scripts\python.exe lesson_01.py
```

前面的三个 `..` 逐层返回“示例工程→本单元→学习指南→工作区根”；随后找到共享 Python。最后的文件名表示要执行当前目录里的脚本。不要在根目录直接运行这条相对命令。

预期输出：

```text
['query', 'color', 'item-0', 'case-00']
['plan', 'color', 'call', 'get_color', 'item-0', '<eos>']
red ['final', 'red', '<eos>']
{'plan_correct': True, 'tool_correct': True, 'argument_correct': True}
```

## 逐步理解代码与执行边界

`make_tasks("train")` 返回训练任务列表；`[0]` 取第一条。它只定义要查什么。`make_trace(task)` 按明确规则构造示范，并调用本地工具查出观察。**此时 action 由规则生成，用来制作训练答案；第 4、5 讲推理时 action 才由神经网络生成。** 不把生成示范的规则误当已训练模型。

`parse_call` 是解析函数，把固定六个文本 token 转成有键名的字典。它检查长度、允许的计划标签、工具名、对象 ID 与结束标记；它不会理解完整任务目的。`semantic_checks` 再对照请求：计划属性对吗、工具对吗、对象对吗？语义就是内容是否符合任务含义。

打开 `tools.py` 的 `execute_tool`：先检查工具与对象在允许范围内，然后从目录字典取属性值。目录是 `make_catalog()` 创建的七个虚构物品，不读取个人数据，也不访问网络。像图书馆查询一样只读资料；类比的局限是此例数据完全由脚本构造，真实库还涉及权限、过期、网络失败等。

例如 `plan color call get_size item-0 <eos>` 可以解析，工具也存在，但颜色请求用了查大小的工具。第 5 讲宿主会拒绝执行这条语义错误的调用；拒绝不会偷偷把 `get_size` 改为 `get_color`。

## 动手操作与常见错误

把任务索引由 0 改为 1，重新保存、运行。预期计划变为 `size`、工具 `get_size`、观察 `small`，对象仍为 `item-0`。`make_tasks` 每个案例先列颜色、再列大小，所以索引 2 才进入 item-1。能解释顺序才算跟做完成。

报 `ModuleNotFoundError: data`：检查脚本是否放在本单元示例工程旁边，不要放到教材目录；也不要把别的单元的 `data.py` 加入全局路径。报找不到解释器：运行 `Get-Location` 核对目录，或使用根共享解释器绝对路径。输出乱码：确认文件保存为 UTF-8；必要时在终端设 `$env:PYTHONIOENCODING='utf8'`。不要通过改写轨迹来掩盖目录错误。

## 分级练习与答案解析

### 跟做练习：查大小

按上面的索引修改，圈出与颜色查询不同的三个字段。提示：计划、工具、观察分别看。

> [!example]- 参考答案
> `color→size`、`get_color→get_size`、`red→small`；答案也跟着观察变为 `final small <eos>`。对象没变，因为还是同一案例。完成标准：能说出观察来自工具，答案来自示范构造。

### 独立练习：可解析但做错

纸上写一条六 token 的调用，查颜色却用查大小工具。预测三个语义布尔值，再用 `parse_call` 与 `semantic_checks` 检查。提示：只改工具，不改计划和对象。

> [!example]- 参考答案
> 对第一条任务使用 `plan color call get_size item-0 <eos>`。计划正确为 True，工具正确为 False，参数正确为 True。格式验证只证明字段符合语法，不证明任务达成。完成标准：预测与实际字典一致，不把 False 解释为工具不存在。

### 迁移练习：目录变化

若工具现在返回 `blue`，但模型最终输出 `final red <eos>`，在哪个阶段失败？提示：分开看读取与回答。

> [!example]- 参考答案
> 执行可以成功，最终答案错误，端到端任务失败。不能用旧示范里的 red 覆盖实际观察。完成标准：能提出“把本次观察放入第二次模型输入，再检查答案是否对应它”的修复方向，而不是修改评估答案迎合模型。
