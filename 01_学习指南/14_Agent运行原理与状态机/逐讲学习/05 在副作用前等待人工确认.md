# 第 5 讲：在副作用前等待人工确认

## 要解决什么问题

读政策与创建工单不一样：前者只读，后者改变系统状态。**副作用**指函数除返回值外，还改变外部或共享状态，例如写文件、建工单、发消息、扣款。执行前需要依据权限和已获得授权决定是否确认。

本讲的人工确认是示例系统中的控制点，不表示你每次操作都必须弹窗。用户已经授权、动作可逆且范围清楚时，产品可以直接执行；高影响或授权不明的动作应让用户看到具体动作再确认。当前工具注册将create_ticket标为需确认，用来学习机制。

前置是上一讲pending_action与动作键。副作用等级/幂等性在下一单元展开，本讲先确保“批准的是哪个动作”清楚。

## 确认不能由决策器自己宣称

`tools.py`里Tool有requires_confirmation。控制器读取可信注册表，不读取模型说“我已经获准”。如果Action自行带approved=True，不能据此视为真实用户批准。

第一轮提出create_ticket后，控制器保存完整Action副本，进入waiting_confirmation并返回。此时ticket_store仍为空。工具名、标题、实际目标和影响应该展示给用户；现实工单还要包括项目、收件人、优先级等。

运行：

```powershell
..\..\..\.venv\Scripts\python.exe demo.py --scenario confirmation --output results/pending.json
```

预期waiting_confirmation、steps1、内存工单0、答案None。trace包含confirmation_required及动作参数，没有tool_observation。待确认是正常暂停，不是工具失败。

## 具体批准绑定具体参数

`approve_pending_action`要求当前确有待办Action，再把动作键保存为approved_action_key，进入ready。继续时控制器比较当前pending的工具名/参数与批准键；参数变化就failed，不执行。

为什么不直接保存一个approved布尔值？因为“同意创建标题A的工单”不能自动授权标题B，也不能自动授权另一个工具。通用布尔值容易被后续动作复用。

当前键只包含名称和参数，真实系统还应绑定用户身份、授权范围、目标资源版本、过期时间和工具版本；若用户确认期间资源变化，需要重新检查前提。JSON字符串也不是防篡改签名，进程内可信边界仍须设计。

## 批准后怎样继续

运行演示：

```powershell
..\..\..\.venv\Scripts\python.exe demo.py --scenario confirmation --approve --output results/approved.json
```

`--approve`只批准本次内存夹具，不会创建真实工单或向任何人发送消息。预期completed、steps2、内存工单1，最终文本DEMO-1。

顺序是：第一次决策提出写动作 → 等确认 → approve绑定动作 → ready执行pending → 保存结果 → 第二次决策输出final。恢复pending不重新decide，也不重复扣一次决策步数，否则可能变成另一个未获准动作。

工具执行后清空pending和approved键，把动作加入executed_actions。再调用已终态的state不会重复写入。**这只保证当前控制器单进程演示的一次执行，不能当作跨网络“恰好一次”保证**。进程崩溃后写已成功但记录未保存，仍需幂等键/对账。

## 自己写确认操作脚本

在示例工程创建 `inspect_confirmation.py`：

```python
from agent import approve_pending_action, run_agent
from policy import policy_ticket
from state import AgentState
from tools import make_tools

tickets = []
tools = make_tools(tickets)
state = AgentState("创建演示工单", "confirm-demo")
run_agent(state, policy_ticket, tools)
print(state.status.value, len(tickets))
approve_pending_action(state)
run_agent(state, policy_ticket, tools)
print(state.status.value, len(tickets))
```

预期waiting_confirmation 0，然后completed 1。代码中的approve是本地跟做步骤，不代表产品应自动替真实用户确认。将其换成 `cancel_pending_action(state)`，预期cancelled且工单仍0。

## 拒绝、修改与失败的差别

拒绝动作进入cancelled，pending清空；修改参数需要形成新具体方案并重新确认，不能先approve后偷偷改；工具执行返回失败应如实记录，不能为“用户已批准”而声称执行成功。

已批准不代表输入合法，执行器仍检查title不是空字符串。当前只做简单标题校验，不含真实权限认证；下一单元把schema、执行前提和错误协议分开讲。

## 常见错误与练习

确认前工单已有记录：查控制器有没有先execute再询问。点击一次出现两条：查重复请求和重启恢复，增加幂等机制。用户拒绝仍生成final“创建成功”：策略必须读实际结果和终态，不能把计划当结果。

**跟做：** 对比pending和approved两份trace，找到执行发生在哪里。完成标准：pending没有工具观察，approved恰好一条。

**独立：** 描述批准后标题改变的处理，解释为什么不能沿用批准。自动测试已经包含该场景，你应先预测结果再运行。

**迁移：** 设计退款确认页需要展示的字段、批准有效期、重复点击处理和结果回查。完成标准：确认对象具体，失败/未知结果不会误报成功。

> [!example]- 参考答案与解析
> 参数变化导致approval_mismatch，store仍为空。确认字段至少有订单号、金额/币种、原因、账户/目标、权限、资源版本和影响。重复点击宜携带同一幂等键；网络超时后先查执行状态，不能直接再扣一次款。当前内存示例未实现这些生产能力。
