## 要解决什么问题

循环跑第二次时，程序怎么知道第一步已经做过？用户任务、工具结果、待确认动作和结束状态放在哪里？本讲把信息分成职责不同的结构，避免只用一个字符串装全部上下文。

**状态**是当前任务继续执行所需的信息；**消息**是面向决策器/界面的内容序列；**工具记录**保留动作参数与实际返回；**trace**记录控制流事件和状态变化。这些数据有联系，但用途不同。

前置是数据类和列表/字典。`state.py`使用 `@dataclass` 自动生成初始化等方法；类型标注帮助读代码，不自动验证运行时值。[Python数据类文档](https://docs.python.org/3.13/library/dataclasses.html)也明确这一点。

## 从一个最小状态看起

在示例工程新建 `inspect_state.py`：

```python
from state import AgentState

first = AgentState("查存储政策", "run-1")
second = AgentState("另一任务", "run-2")
first.messages.append({"role": "user", "content": first.task})
print(first.status.value, first.steps)
print(len(first.messages), len(second.messages))
```

预期 `ready 0`、`1 0`。两个状态各有自己的列表，没有串任务。`field(default_factory=list)`每次创建新列表；若错误使用共享可变默认值，多个任务可能共用消息。数据类会阻止一些直接可变默认值写法，但你仍需理解对象所有权。

`run_id`是轨迹关联编号，不是秘密token。demo固定demo-run方便比较；真实并发任务要使用唯一编号，并检查日志不混入别的任务。

## 各字段解决什么问题

| 字段 | 职责 | 错放会怎样 |
|---|---|---|
| task | 初始用户请求 | 与工具内容混写会丢指令边界 |
| status | 当前阶段/终态 | 无法判断是否允许继续 |
| steps | 已做决策次数 | 无法执行预算 |
| messages | 用户、工具观察、最终答复 | 只存它可能缺少控制状态 |
| tool_records | 工具名、参数、返回、耗时 | 无法复查工具是否真运行 |
| pending_action | 等待确认的动作 | 批准时可能执行错动作 |
| approved_action_key | 批准绑定的参数指纹 | 原批准可能被滥用于新参数 |
| executed_actions | 已执行动作指纹集合 | 相同动作可能无限重复 |
| trace | 事件、状态、步骤、耗时 | 很难定位是哪一步卡住 |

`final_text`只在成功接受最终答复后设置。取消、步数限制和失败时可能为None，界面应展示终态与原因，而不是假装得到了正常答案。

## 动作和结果要分开

Action有kind、tool_name、arguments、final_text。tool动作提出一次执行；final动作提出结束。ToolResult有ok、data、error_code；它是执行器反馈，而不是模型自己声称“工具成功”。

工程使用统一数据类来减少阅读负担，没有做复杂判别联合类型。你应约定tool动作不使用final_text，final动作不使用tool参数；下一单元将用更严格协议校验。`frozen=True`只阻止字段重新赋值，内部dict仍可变，不能把它当深度不可变。

所以控制器对参数、状态和记录用 `deepcopy`：递归复制列表/字典，减少同一对象被后续改动污染记录。它不是安全沙箱：恶意Python决策函数仍能访问进程资源；这里防的是意外改状态，真实隔离需更强边界。

## 消息不是供应商API载荷

当前messages中的role=user/tool/assistant是内部教学记录，tool content可以是字典。真实模型API可能要求字符串内容、工具call_id、assistant的tool_calls和指定role顺序；不能原样把本列表发给任何API就宣称兼容。

本单元policy直接读取tool_records，没有重新序列化Prompt。之后“工具调用协议”会讲模型提出调用、控制器执行和按call_id回传。当前先掌握记录责任。

## 逐条观察运行

在脚本中运行默认Agent，再打印摘要：

```python
from agent import run_agent
from policy import policy_lookup
from state import AgentState
from tools import make_tools

state = AgentState("查询", "inspect")
run_agent(state, policy_lookup, make_tools([]))
for message in state.messages:
    print(message["role"])
print(state.tool_records[0]["result"])
```

保存为 `inspect_observation.py`。预期role顺序user、tool、assistant，result包含ok=True、retention=30 days和citation。关键：policy只在工具结果记录后才读取最后一项，不应对空列表使用[-1]。

若你重用同一state跑第二个新任务，已有终态会使run_agent直接返回。新任务应创建新state，不能只改task字段。任务状态与工具环境也要区分：同一个工具列表可能服务多个任务，但每个任务记录独立。

## 常见错误与练习

消息太长：不要未经设计删除关键观察；可保存完整工具记录并给模型摘要，确保摘要保留证据与错误。日志含隐私：trace示例只含虚构数据，真实工具参数和结果需要脱敏、访问控制和保留期。

**跟做：** 创建两个state，只向第一个messages添加内容，解释为什么第二个仍为空。

**独立：** 把字段按“控制器必须用”“决策器需要看”“仅诊断”分组。允许一字段多用途，但说明边界。

**迁移：** 设计长任务上下文：保留哪些完整结果、模型读取哪些摘要、如何按run_id回查。完成标准：不把摘要说成原始结果，不泄露授权外数据。

> [!example]- 参考答案与解析
> status/steps/pending_action/approved_action_key主要用于控制；task和tool_records用于策略；trace用于诊断，控制也可读取它但本工程没有依赖。工具记录不能由模型臆造。default_factory产生独立对象；deepcopy只能减少意外共享，不能阻止进程内恶意代码访问真实资源。
