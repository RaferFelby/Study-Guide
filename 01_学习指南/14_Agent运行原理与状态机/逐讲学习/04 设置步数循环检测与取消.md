## 要解决什么问题

Agent可能一直查相同资料、用完预算后仍继续，或用户已取消却开始下一项写操作。控制器需要明确的结束条件；不能把“模型应该知道停下”当资源和权限保障。

本讲的三个机制是决策步数预算、完全相同动作检测、协作取消。它们互相补充，不能互相代替。前置是集合、函数回调和状态机；回调就是“把函数交给另一函数，之后需要时调用”。

## 决策预算怎样计数

`steps`在调用decide前加1。默认查询需要第1步提出工具、第2步生成final。max_steps=1时工具成功返回，下一轮ready已达到预算，进入step_limit。

```powershell
..\..\..\.venv\Scripts\python.exe demo.py --scenario limit --output results/limit.json
```

在示例工程运行，预期状态step_limit、决策步数1、答案None、没有工单。打开记录仍能看见查询工具成功。这种终态应告诉用户“达到执行预算，已查到什么，未完成什么”，不能丢掉中间成果或伪装正常答案。

max_steps不是秒数、token数或费用上限。真实系统通常还要有总时限、每个工具时限、输出大小、token/费用预算。这些单位不同，应分别命名；同步示例本节只实现决策预算。

## 相同动作怎样识别

Action中工具名和参数转成排序键固定的JSON字符串：

```python
from agent import action_key
from state import Action

first = Action("tool", "lookup_policy", {"service": "storage", "version": 1})
second = Action("tool", "lookup_policy", {"version": 1, "service": "storage"})
print(action_key(first) == action_key(second))
```

保存 `inspect_action_key.py`，运行预期True。`sort_keys=True`使字典键顺序不影响指纹；工具名也纳入，避免两个不同工具参数相同被误判。这里指纹是规范JSON文本，不是加密签名，也不是幂等键。

`executed_actions`保存已经实际执行的键。在第二次相同请求执行之前，控制器返回loop_detected。

```powershell
..\..\..\.venv\Scripts\python.exe demo.py --scenario loop --output results/loop.json
```

预期loop_detected、步数2、只有1条tool_observation。第二次decide有发生，但工具没有第二次执行。检查观察数量比只看终态更可靠。

这是保守教学规则：合法刷新可能也重复相同读动作，轮询任务需要不同策略；两种动作交替A→B→A同样会在再次A时被挡住，但参数每次改变的无意义循环可能绕过它。真实系统需结合进展判定、重复阈值、允许刷新策略和预算。不要无脑允许所有重复写动作。

## 协作取消在什么位置检查

`is_cancelled`是一个不接参数、返回布尔值的函数。控制器在每轮开始和决策后工具执行前检查。测试用可预测函数，不需要线程。

```powershell
..\..\..\.venv\Scripts\python.exe demo.py --scenario cancel --output results/cancel.json
```

预期cancelled、steps=0、无工具观察、无工单。它演示“开始前取消”。自动测试还模拟“决策后取消”，保证已提出Action不一定执行。

你可在个人脚本中写：

```python
from agent import run_agent
from policy import policy_lookup
from state import AgentState
from tools import make_tools

cancel_requested = True
def is_cancelled():
    return cancel_requested

state = AgentState("查政策", "cancel-demo")
run_agent(state, policy_lookup, make_tools([]), is_cancelled=is_cancelled)
print(state.status.value)
```

函数读取当前布尔值，控制器调用它来询问“现在取消了吗”。这不是系统级强制中断。同步工具已经阻塞执行时，取消函数不会自动抢占；工具返回后才能再次检查。后续异步可靠性单元会讲取消传播与超时。

## 终态与暂停状态别混淆

completed、failed、cancelled、step_limit、loop_detected都是终态；当前run_agent再次调用会直接返回，不重新执行。waiting_confirmation是暂停状态，未经approve或decline也直接返回。

要开始新任务创建新AgentState。要在跨进程恢复中继续任务，需要存储状态、工具幂等/结果和批准，不能简单把steps改小或删executed_actions；这会破坏预算和重复保护。

取消也不等于撤销：一个工具已经写入外部系统，之后取消不会自动删除它。应记录是否已执行、是否有补偿办法、是否需要人工处理。当前只用内存演示，避免把现实撤销难度藏起来。

## 常见错误与练习

达到预算却没有最终文本：这是可预期终态，界面应展示原因与中间结果。loop检测后仍出现第二条工单：检查检测是否放在执行之后；正确应执行前检测。取消时系统仍花时间：先定位阻塞的工具/模型请求，设置各阶段时限，而不是增加一个布尔字段就宣称解决。

**跟做：** 运行limit/loop/cancel三种场景，写steps和tool_observation数量。完成标准：能解释计数差异。

**独立：** 设计一个合法重复读场景和一个不应重复写场景，说明简单集合检测的局限。

**迁移：** 为真实工单Agent定义总决策预算、总时限、单工具超时和用户取消行为。完成标准：明确取消发生在写前、写中、写后时如何报告，不声称都能撤销。

> [!example]- 参考答案与解析
> limit：steps1、观察1；loop：steps2、观察1；cancel：steps0、观察0。每分钟刷新订单状态可能需要重复读取；重复提交退款不应直接执行。只读工具通常可安全重试，写操作要有确认和幂等/事务设计，后续工具协议单元详讲。
