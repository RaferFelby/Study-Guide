## 从技术数字回到用户任务

本讲将技术指标映射到业务目标。指标是按约定计算的数量；目标是希望它达到的水平；结果是实际测量记录。前置是单元19的评估分母与单元20的P95。若忘记：准确率的分母是被评估任务总数，P95是排序后按约定取95%位置的时长，不是平均值。

“回答时间短”不等于员工处理时间短。员工可能花很久检查来源、纠正错误、重新提问。要解决的是完整任务，而服务时长只解释其中一段。本例业务目标是少翻资料且不误答、减少人工含复核总时间、避免越权、可维护并控制成本。

## 为每个目标写四项

业务目标写受益者和工作变化；技术指标写可统计事件；测量方式写数据、环境、分母和复核；验收写阈值与失败处理。以下是计划，不是已达结果。

| 业务目标 | 技术/过程指标 | 计划测量 | 候选验收 |
|---|---|---|---|
| 查准政策 | 带来源事实准确率 | 50条多样任务，预先标预期，人工复核来源与适用条件 | 至少45/50正确；另报拒答/冲突类 |
| 降低处理时间 | 人工含复核时长、服务P95 | 同任务人工/辅助对照，保留失败与纠错时间 | 中位数降30%；服务P95≤1000ms |
| 保护可见范围 | 越权读取次数与内容泄露 | 预定义跨用户/伪造权限输入，检查实际读取与输出 | 定义测试中读取/泄露均0 |
| 可持续维护 | 月消耗与维护人时 | 记录范围、版本、费率依据和维护操作 | 运行消耗≤100虚构单位；真实项目重估 |

50条是这份模拟MVP的小规模目标，不是统计保证。至少45条正确仍可能漏掉关键高风险类别；要分别查看无证据、冲突、权限边界，并对安全失败单独停止。平均数、分位数和分组结果各有用途，不要用总准确率掩盖某类全错。

## 最小例子：同样响应时间，业务时间不同

假设人工查资料90秒。系统响应2秒、员工复核70秒、修改回答20秒，总计92秒；系统响应快，完整任务仍没有节省。若系统响应2秒、复核25秒、答复18秒，总计45秒，才有可能达到本例的节省假设。

这两个数字都是演算。真实对照需减少任务难度、顺序和熟练度的影响：同一类任务、交错顺序、记录是否用过同题、不要挑容易的题。失败、重试和转人工也要计入，不能只对成功任务计时然后对所有任务声称收益。

## 动手：读指标映射

在示例工程创建 `lesson_metrics.py`：

```python
import json
from pathlib import Path

plan = json.loads(
    (Path(__file__).parent / "fixtures" / "plan.json").read_text(encoding="utf-8")
)
for metric in plan["metrics"]:
    print(metric["business_goal"])
    print("测量：", metric["measurement"])
    print("验收：", metric["acceptance"])
```

共享解释器运行后会显示四组目标、测量和验收。`print` 的多个参数用空格连接显示；字典的字段名与源码验证规则一致。检查输出中是否含“未执行”“未测”，避免在报告中删除证据状态。

再在学习记录建立一行：任务ID、类别、预期事实、来源版本、人工秒数、辅助秒数、复核结论、失败原因。本轮只设计记录表，不编造真实客户数据。

## 常见错误与修复

没有分母：补任务总量、过滤条件和失败数量。引用存在但内容不支持答案：复核来源实际条款与版本，不能把“有一个链接”当事实正确。权限测试零泄露就宣称系统绝对安全：写“本组用例覆盖的条件下”，列出未测并发、凭证泄露、真实身份系统等边界。

## 练习与判断

跟做：计算90秒到45秒的节省比例。独立：说明为什么只记录模型生成时间不足以验收。迁移：代码助手场景里，把“生成代码多”改成一个用户任务指标。

> [!example]- 参考答案与过程
> 节省比例=(90−45)/90=50%，是假设值，不是本例已测收益。模型生成只占任务一段，检索、等待、复核、纠错和重试都会影响用户完成时间。代码助手可测“含人工审查和测试后完成指定修复的时间”，同时报告正确率与回归失败；生成行数不能直接代表任务成功。

完成判断：每个指标都能找到对应用户目标、测量记录和未达目标时的处理方式；能说明一次结构检查无法证明这些结果。
