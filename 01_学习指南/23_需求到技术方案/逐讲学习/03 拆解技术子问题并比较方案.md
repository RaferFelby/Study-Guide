## 要解决的问题与前置

把“用AI解决”拆成至少五个可以分别比较的技术问题。本例有八个。你已写场景和约束；先复习单元20的日志/成本、单元21的权限、单元22的检索失败。关键词检索按词匹配资料；稠密检索把文本转换成向量再找相近项，可能支持同义表达，但需要模型与质量评估。这里先理解取舍，不新增模型依赖。

方案矩阵是一张“问题—候选—代价—选择—理由”的表。它帮助别人检查决策，不能用候选数量证明方案优秀。每个选项都要说在哪些条件下合适，并记下何时重新考虑。

## 八个子问题的两个候选

| 子问题 | 候选一 | 候选二 | 本轮选择及依据 |
|---|---|---|---|
| 资料导入 | 固定文件：易审查，更新需受控 | API同步：及时，需凭证分页重试 | 文件；先验证来源和版本 |
| 检索 | 关键词：可解释，同义覆盖有限 | 稠密向量：语义潜力，需模型索引评估 | 关键词；先建立基线与失败样本 |
| 回答 | 模板：事实可控，表达有限 | LLM：表达灵活，需费用与事实评估 | 模板；当前输出事实与来源即可 |
| 权限 | 同库逐条过滤：维护集中，易漏过滤 | 按权限分库：边界直观，索引维护多 | 统一服务端过滤，并测越权 |
| 工具能力 | 只读：副作用小，不能代办 | 确认后写入：能办事，需幂等恢复 | 只读；用户场景不含退款写入 |
| 服务方式 | 同步请求：简单，长任务占连接 | 异步任务：可追踪，需队列状态 | 同步；先测真实查询时长 |
| 存储 | SQLite：单机易起步，写并发有限 | PostgreSQL：服务型并发，需运维 | 单实例SQLite，扩容时重评 |
| 观测 | JSONL：离线简单，实时关联弱 | SDK与平台：自动追踪，依赖维护增多 | JSONL；先确定字段与隐私 |

表中的“统一过滤”必须实现到服务端检索/读取边界；仅在页面隐藏按钮不算权限。SQLite选择不是“永远无需数据库服务”，单实例原型与生产并发是不同约束。实际权限模型复杂时，也可能需要多层隔离，不能把这两种选项看成穷尽所有方案。

## 把理由变成可复查决策

以检索为例：需求是查固定公开政策，约束是不装新模型、30人时。关键词实现成本低，能提供基线；代价是“退钱窗口”可能召回不到“退款期限”。验证方式是多样措辞任务与无证据任务。重新决策触发条件是：在确认数据正确后，关键词召回仍达不到目标，并且稠密方案在同一批保留任务上确有收益且预算允许。

不能只写“向量更先进”，也不能为维护简洁而忽略已观察到的失败。合理选择需要将约束、失败证据和候选试验连接起来。还未做实验时，理由应写“计划依据”而不是“证实更优”。

## 最小示例：查看机器可读的选择

在示例工程创建 `lesson_options.py`：

```python
import json
from pathlib import Path

plan = json.loads(
    (Path(__file__).parent / "fixtures" / "plan.json").read_text(encoding="utf-8")
)
for problem in plan["technical_problems"]:
    option_ids = [option["id"] for option in problem["options"]]
    print(problem["id"], problem["name"], option_ids, problem["selected"])
```

循环中的 `problem` 是一个子问题字典。列表推导式把每个选项的 `id` 收集成列表，等价于创建空列表、逐个 `append`。第一次会显示 `P01 资料导入 ['files', 'api'] files`；共八行。标识符用于稳定追踪，不代替中文理由。

用共享解释器运行这个脚本，检查八行都有两个不同候选，选择属于候选列表。再在 VS Code 阅读 `planning.py` 的 `validate_plan`：集合去重检查ID，`selected` 校验选择合法，`reason` 和 `tradeoff` 校验非空。函数并不认识业务含义，写“好”也可能通过，因此仍需人工评审。

## 动手：补一条重新决策条件

在自己的学习记录写：问题P02、当前选择、已知代价、拟测样本、变更条件。保留原夹具不变。本例不启动任何云API、不安装向量模型；未来需要具体实验时再检查共享环境与审批依赖。

## 错误与排查

子问题重复：给导入、检索、回答分别写输入输出，检查是否同一职责重复命名。只写选项名：补质量、时延、成本、维护、隐私等相关代价，不必每项填无关维度。选择不在候选中：对照ID改正拼写，或明确增加第三候选及理由，而不是删校验。

## 三类练习

跟做：解释为什么本例不增加退款写入。独立：为“资料更新”写两个方案及一个可验证的选择理由。迁移：用户要求长时间批量审核时，重新比较同步请求与任务队列。

完成判断：能解释至少五个子问题，每个都有两种明确候选、选定原因、代价及改选条件。

> [!example]- 参考答案
> 当前用户只查政策，写退款会增加副作用、确认与幂等负担，也超出验收范围。资料更新可选人工审核后发布文件或经授权API同步；固定低频资料先文件，更新遗漏成为高频失败时再测API成本。批量审核可能超请求时限，任务队列能分离提交和执行，但要持久保存状态、定义重试/取消和去重，先用单元18/21已有机制验证边界后决定。
