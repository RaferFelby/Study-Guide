# 第 1 讲：把模糊想法变成用户场景

> [!nav] 页面导航
> [[01_学习指南/23_需求到技术方案/00 需求到技术方案学习地图#学习顺序|单元 23：需求到技术方案]] · [[01_学习指南/23_需求到技术方案/逐讲学习/02 写清约束假设与成功标准|下一讲]]

## 现在要完成什么

把“想做一个智能客服”改写成一个可以讨论、测量和划定边界的场景。本讲不要求懂产品管理。你需要知道：用户是实际使用系统的人；需求是他在具体条件下要完成的事情；功能是系统提供的动作。三者有关，但不是同一个词。

先准备 Obsidian 阅读本讲，VS Code 打开本单元的 `示例工程` 文件夹。本单元示例全部是虚构场景，尚未访谈客户、测量业务或实现客服系统。前面单元的技术经验可以帮助判断方案，不能替你确认用户到底要什么。

## 为什么一句想法不够

“做智能客服”可能指查政策、处理退款、追踪物流，也可能指给客服员工提供参考。不同任务需要不同数据、权限和验收。本单元选择：内部客服员工查公开退款政策，看到来源，自己复核后对客户答复。系统不代办真实退款。

一个可操作的场景包含五项：谁使用、何时触发、输入什么、需要得到什么、怎样判断任务完成。可以把它当作一段工作过程；它不是功能按钮清单，也不能代表所有用户。

最小场景：员工收到“退款期限是多少”的问题，输入政策查询，系统返回“30天”及政策版本和来源。员工打开来源确认适用条件，再完成答复。如果资料缺失或冲突，系统说明无法确认，员工转人工核查。

这里“30天”是合成例子的数字，不是任何商家的真实政策。“完成答复”仍由员工负责。失效场景也属于需求：用户问没有资料支持的VIP条款时，编造一个期限不能算成功。

## 从想法逐步写成场景

第一步，写使用者而不是采购者。本例使用者是客服员工，政策维护者负责资料，技术维护者负责运行。一个人可能兼任多个角色，但权限仍按职责判断。

第二步，写当前过程：收到问题→搜索政策→打开来源→核对条件→答复。先画出现有过程，才能知道要节省哪一步；不要把当前人工时间假装成已测数据。

第三步，写系统介入后的过程：输入问题→权限范围内检索→显示事实和来源→员工复核→答复。把“人工复核”留在时间统计中，才能比较完整工作时间。

第四步，写失败分支：无来源、过期版本、矛盾条款、权限不足、服务不可用时分别怎样做。拒答在某些输入上是正确行为，在本应可答的任务上则可能是召回失败；要由样本预期判断。

第五步，给每项说法标证据状态。`simulated` 表示模拟，`unverified` 表示待验证；不是“测试通过”。真实项目可以记录访谈日期、匿名任务样本和授权范围，但本例没有这些证据。

## 动手：读取场景记录

在 VS Code 的示例工程中创建 `lesson_scenario.py`。打开“终端→新建终端”，确认当前目录是 `23_需求到技术方案\示例工程`。下面用 `pathlib` 按脚本位置找文件，避免终端位置改变时意外读错资料。

```python
import json
from pathlib import Path

plan_path = Path(__file__).parent / "fixtures" / "plan.json"
plan = json.loads(plan_path.read_text(encoding="utf-8"))
print(plan["scenario_origin"])
print(plan["scenario"])
for assumption in plan["assumptions"]:
    print(assumption["id"], assumption["status"])
```

`Path(__file__)` 是当前脚本路径，`.parent` 是父目录，`/` 拼接路径。`read_text` 按UTF-8读取完整文本；`json.loads` 把 JSON 文本转换成字典和列表。方括号按键取值；循环一次处理一条假设。这里没有向模型发送资料。

在终端运行：

```powershell
& ..\..\..\.venv\Scripts\python.exe lesson_scenario.py
```

`&` 是 PowerShell 调用运算符；后面的路径选择工作区共享 Python；三个 `..` 从示例工程向上回到工作区根目录。最后一个参数是要运行的脚本文件。

预期第一行 `simulated`，之后是虚构场景说明，最后三行是 `A01 unverified`、`A02 unverified`、`A03 unverified`。这说明读到了方案记录，不能说明业务需求成立。

## 常见问题与排查

找不到 `fixtures/plan.json`：检查脚本是否确实保存在示例工程，与 `demo.py` 同级；不要把文件放进逐讲学习目录。JSON解析报错：先运行原始夹具确认正常，再检查你是否删掉逗号、用了中文引号。把输出误写为“已经访谈”：把记录改回待验证，并另写准备访谈的方法。

## 练习：从跟做到迁移

跟做：写出本例的输入、输出、人工动作。独立：补一条“资料冲突”的失败流程，不能只写“报错”。迁移：把场景改为内部报销制度查询，说明哪些数据需要授权。

完成判断：另一个人读你的场景，能知道谁在什么条件下做什么，也能知道系统失败后由谁处理。不要用“准确”“高效”两个词代替流程。

> [!example]- 参考答案与思路
> 跟做：输入是政策问题，输出是有版本/来源的事实或明确无法确认；人工打开来源复核并答复。独立：检索到两份冲突条款→标出两个版本→停止自动给期限→交政策维护者确认，员工按既有人工流程处理。迁移：报销制度涉及员工身份与部门可见范围，需要确认资料使用权、版本及检索前权限过滤；不能直接把真实员工资料装进模拟夹具。
