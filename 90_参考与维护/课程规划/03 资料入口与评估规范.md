## 十四、可复制的评估规范与示例

本节先给默认 Agent/知识助理的完整起步规范，再给其他岗位的替换口径。字段和阈值是本项目约定，应在运行前固定；示例中的产品、文档、工单与结果全部为教学构造，不是已完成的项目实验。

### 数据集与运行配置

- 第一轮 20 条全部作为开发/回归样例：可按 10 条有证据问答、4 条无答案、3 条工具正常、3 条工具异常起步。
- 后续可形成 30 条开发/回归 + 20 条保留测试，共 50 条；按任务类型分层，近重复问题或同一模板变体放在同一侧。完整文档可按评估目的供检索使用，但最终测试题、标准答案及结果不得用于调参。
- 一旦依据保留测试结果修改方案，该批样例转入开发/回归集；若需要新的独立估计，另建未见测试集。所有报告注明 `dev` 或 `test`，不能把开发集效果写成未见泛化能力。
- 每次运行固定代码提交、数据/语料版本、Prompt/schema 版本、模型版本、生成配置、检索 K、随机种子（若支持）、并发和超时。种子不保证所有后端逐字可复现。
- 各方案使用同一组样例和预算；随机模型需要多轮比较时，先规定轮数，按完整 run 分别报告，不只挑最好的一轮。

起步配置示例，数值可根据真实后端调整，但运行后不得为某方案单独更改：

```json
{
  "run_id": "demo-baseline-001",
  "dataset_version": "toy-dev-v1",
  "corpus_version": "toy-corpus-v1",
  "split": "dev",
  "backend_mode": "real",
  "top_k": 3,
  "concurrency": 1,
  "tool_timeout_ms": 2000,
  "task_timeout_ms": 30000,
  "max_tool_attempts": 1,
  "generation": {"do_sample": false, "max_new_tokens": 128}
}
```

正式运行还需在结果元数据中补实际 `code_commit`、`model_id/revision`、`prompt_version` 和计费/硬件信息；上面的 `demo` 名称仅为示例。mock 的 `backend_mode` 必须为 `mock`，不能与真实模型结果混算。

### 样本字段与三个具体样例

每条样本必须有唯一 ID、任务类别、输入、预期结果、判分条件和超时预算。检索样本带证据 ID；工具样本带允许工具、预期参数和可控故障。标准答案与故障设置只交给评估器，不能加入模型提示。

教学语料 `manual-v1#export` 的内容固定为“本示例产品支持导出 CSV 和 JSON”。它没有说明在线保存期限。工具 `get_ticket` 在第三条样例被评估器设置为超过 2 秒不返回；这是模拟故障，不是真实业务数据。

```json
[
  {
    "id": "rag-001",
    "category": "answerable",
    "input": "支持导出哪些格式？",
    "expected_outcome": "answer",
    "required_facts": ["CSV", "JSON"],
    "evidence_ids": ["manual-v1#export"],
    "allowed_tools": [],
    "pass_checks": ["两种格式均正确", "引用存在且支持答案", "不增添未说明的格式"],
    "task_timeout_ms": 30000
  },
  {
    "id": "rag-002",
    "category": "unanswerable",
    "input": "导出文件在线保存多少天？",
    "expected_outcome": "no_answer",
    "required_facts": [],
    "evidence_ids": [],
    "allowed_tools": [],
    "pass_checks": ["说明资料未提供保存期限", "不编造天数或引用"],
    "task_timeout_ms": 30000
  },
  {
    "id": "tool-003",
    "category": "tool_fault",
    "input": "查询工单 T007 的状态。",
    "expected_outcome": "tool_error",
    "expected_tool": {"name": "get_ticket", "arguments": {"ticket_id": "T007"}},
    "allowed_tools": ["get_ticket"],
    "fault": {"type": "timeout", "tool_timeout_ms": 2000},
    "pass_checks": ["正确请求工具和参数", "识别模拟超时", "说明暂时无法查询且不编造状态"],
```

第一条不以机械字符串包含作为最终答案判定：例如“既不支持 CSV，也不支持 JSON”含有关键词却是错误答案。格式和 ID 可自动检查，语义先人工核验。

### 判分规则与失败归属

每条先记录实际运行，再进行规则/人工评分。可分别记录内容正确、证据支持、工具正确、权限边界、预期降级五个维度；不适用项记为 `null` 并排除该维度分母。所有适用的必需检查通过，且在任务期限内，才记为该样例通过；额外的重要错误不能被其他维度平均分抵消。

| 结果标签 | 判定 | 是否进入任务成功率分母 |
|---|---|---|
| `passed` | 达到预期结果并通过所有必需检查 | 是，计入成功数 |
| `failed` | 已返回但答案、引用、工具行为或边界检查不通过 | 是，不计成功 |
| `timeout` | 整个任务超过预设期限，无论之后是否返回 | 是，不计成功 |
| `error` | 崩溃、无法解析或未处理异常导致不能完成 | 是，不计成功 |

模拟工具超时被正确处理时，第三条可以是 `passed`：它验证的是故障恢复行为。必须把正常任务成功率与异常处理通过率分开报告，不能借大量容易拒绝的异常题抬高正常业务效果。正常任务中发生工具故障后只返回“无法查询”，一般仍算任务未完成，除非该样本运行前明确允许这一结果。

系统内部重试属于同一任务，其时间、调用数和成本全部累加。评估脚本自身损坏、人工中断或数据损坏时，记录原因并将整个相关 run 标为不完整；修复后重跑，不能静默删除失败行再报告完整成功率。

示例结果记录：

```json
{
  "run_id": "demo-baseline-001",
  "case_id": "tool-003",
  "observed_outcome": "tool_error",
  "status": "passed",
  "checks": {"content": true, "evidence": null, "tool": true, "permissions": true, "fallback": true},
  "latency_ms": 2410,
  "tool_attempts": 1,
  "input_tokens": 180,
  "output_tokens": 24,
  "cost_amount": null,
  "judge_method": "human_and_rules",
  "reason": "参数正确，模拟超时后说明无法查询，未编造工单状态"
}
```

示例的耗时与 token 数仅用于说明格式。真实报告中，未知费用或 token 数填 `null` 并注明原因，不填 0 伪装为零成本。

### 指标口径与报告

| 指标 | 固定口径 |
|---|---|
| 任务成功率 | `passed / 全部已计划且完成评估的样本数`；timeout/error 都在分母；不完整 run 不给正式整体结论 |
| 分类型成功率 | 对有答案、无答案、工具正常、工具故障分别报告成功数/总数；类别比例同时公开 |
| Recall@K | 对有标准证据的查询，计算 Top-K 中命中的相关证据数 / 该题标准相关证据总数，再按查询取平均；无答案题不进入分母 |
| 引用准确率 | 正确且支持对应断言的引用数 / 已给出的引用数；另报“应引用却缺失”的比例，防止靠不引用规避检查 |
| 工具正确率 | 分开报告“首轮工具/参数正确的任务数 / 需要工具的任务数”和“正确调用次数 / 所有调用次数”；另统计不需要工具却调用的次数 |
| 无答案表现 | 正确不作答数 / 无答案题数；误拒数 / 有答案题数；避免仅报告拒答率 |
| 延迟 | 客户端提交到收到最终结果的总墙钟时间，包含重试；成功请求报告 P50/P95，同时单列超时数、阈值与失败耗时 |
| 资源与成本 | 单次任务累计模型/工具请求、token、可测费用；自托管报告 GPU 时间/显存等，不自动折算为免费 |

20 条结果只适合起步排错，不能据此宣称生产可靠。需要比较时同时给计数、变化样本 ID；样本增多后再报告适合比例指标的置信区间。相同问题重复采样是模型波动测试，不等于增加独立问题数。

**算术示例（虚构数据）**：20 条样例中 14 条通过、3 条错误回答、2 条任务超时、1 条程序错误，则成功率是 `14/20 = 70%`，不能排除超时和错误后写成 `14/17`。若第一轮 14/20、改动后 15/20，应报告新增通过和新增失败的 ID，并说明仅多通过一题不足以支持广泛收益结论。

**通过规范的含义**：原型验收要求数据、评分、结果可追溯，且规定的正常/失败行为已被测试；模型效果是否达标由运行前声明的任务目标决定。没有统一的“成功率达到某个百分比就能就业”标准。若模型未提升但对照严谨，实验可以完成，产品质量目标仍应如实标记未达到。

### 人工与 LLM-as-Judge 一致性

1. 第一轮人工按同一 rubric 给出通过/失败、原因与证据；数值答案、schema、工具参数优先规则检查。
2. 引入 Judge 时固定模型、Prompt、rubric 和参考证据；不让它看到方案名称和预期胜者，候选比较时随机化顺序。
3. 起步抽取约 20 条覆盖通过与失败的样例，人工先独立标注，再比较 Judge；不要直接接受其解释作为标准答案。
4. 报告标签一致数/总数、混淆矩阵和争议 ID；可补 Cohen's kappa。若类别单一、样本太少或 kappa 不可定义，要说明限制，不据此宣称高一致性。指标接口参考 [scikit-learn Cohen's kappa](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html)。
5. 争议样本按证据复核，保留原始标签与最终裁决；没有第二位人工时标为单人复核，不能写“多人一致”。改过 rubric 后用新的样本检查，避免只适配已知例子。

建议报告最少包含：运行配置、数据分布、各类成功数/总数、超时/错误、延迟与成本、相对基线变化、争议样例、失败根因、限制和下一步。Judge 调用本身的成本与被评估系统运行成本分开记录。

### 非 Agent 岗位的替换口径

| 岗位 | 数据/输入 | 必需指标与验证 | 不需要继承的 Agent 要求 |
|---|---|---|---|
| 传统算法 | 按时间/用户/分层规则切分的完整数据集 | 预处理只拟合训练集；分类或回归主指标、基线、完整保留集预测、错误切片；阈值在开发集选择 | 引用、工具调用、20 条问答与注入测试 |
| LLM 训练 | 明确模板与 label 的训练/开发/测试数据 | 有效监督 token、训练/验证 loss、任务指标、Base/SFT 同条件对照；错误和退化样例 | 必须具有 RAG/多工具界面 |
| 推理系统 | 固定模型、精度、硬件、输入长度、生成策略、输出上限与并发 | 先预热；记录实际输入/输出 token 数；TTFT、TPOT、吞吐、错误率、显存及质量检查；客户端与服务器计时分开 | 知识库召回率、Judge 必选 |
| FDE | 事先确认的用户流程与 UAT 场景 | 各流程通过/失败、数据对接与权限、恢复行为、用户反馈及交接可操作性；模拟需求如实注明 | 必须训练模型或跑公开模型榜单 |

推理计时示例：TTFT 从客户端发出请求到收到第一个生成 token；TPOT 可按 `(末 token 时间 - 首 token 时间)/(生成 token 数 - 1)` 计算，单 token 输出记为不适用。生成 token 吞吐按同一测量窗口内总生成 token 数/窗口秒数计算。若接口只按文本块流式返回而非逐 token 回调，应标为首块/块间延迟或使用服务端 token 时间，不能把网络分块直接当 token。

训练/传统 ML 的数据集规模由任务和数据决定；人工抽查 20 条只是检查数据或错误样例，不能替代完整保留集评估。各分支最后都应能回答：基线是什么、在哪些输入上改善或退化、结论在什么条件下成立。
